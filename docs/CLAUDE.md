# Миссия проекта

Сайт малого бизнеса в Туле: продажа кондиционеров, монтаж под ключ, сервис и обслуживание.

**Продукт — не витрина. Продукт — заявка.** Всё остальное существует ради того, чтобы человек, который в июльскую жару ищет «установка кондиционера в Туле», нашёл нас в выдаче, поверил цене и оставил телефон.

Отсюда две планки, которые выше архитектурной красоты:

1. **Поисковая видимость.** Сайт без трафика из Яндекса и Google не имеет смысла — здесь нет ни бренда, ни рекламного бюджета уровня федералов. SEO не «сделаем потом», оно заложено в структуру URL, рендеринг и разметку с первого коммита.
2. **Ни одной потерянной заявки.** Заявка — это деньги владельца. Отправка не должна зависеть от доступности внешнего сервиса.

# 🔴 Красные линии

## Не врать в цене

Половина контента сайта — про честность сметы («Почему монтаж стоит 6 000 ₽, а не 3 000 ₽», «Как обманывают при установке»). Это позиционирование, и оно обязывает.

Всё, что калькулятор показал пользователю, должно совпадать с тем, что скажут по телефону. Если формула меняется — она меняется в БД через админку, а не правкой коэффициента в коде.

## Не публиковать чужое

Фотографии моделей — только от поставщика или свои. Отзывы — только настоящие, полученные через форму. Тексты статей — только оригинальные: скопированная у конкурента статья не просто не даст трафика, она утянет вниз весь домен.

## Не рисовать скидки

Скидка — настоящий инструмент, но только пока она настоящая. Перечёркивается цена, по которой товар действительно продавался; период действия задаётся заранее и заканчивается сам.

Поднять цену на неделю, чтобы потом «снизить», — ровно тот приём, который сайт разоблачает в разделе «Как обманывают при установке». Делать это на своей витрине нельзя не из осторожности, а потому что тогда рушится всё позиционирование.

## Не строить дорвеи

Гео-страницы по районам Тулы делаются только с уникальным содержанием (реальные объекты, особенности домов района, сроки выезда). Десять страниц, отличающихся одним словом в заголовке, — это фильтр от Яндекса, а не трафик.

# 🔴 Маршрут задачи — PRD → план → issue → работа

Единственный путь, которым задача попадает в код (ADR-157). Проходится тремя
скиллами, лежащими в репозитории:

1. **`/prd <фича>`** → `docs/prd-<feature>.md`: цель, пользовательские
   сценарии, границы скоупа, проверяемые критерии готовности. Как
   реализовывать — не пишется.
2. **`/plan-phase docs/prd-<feature>.md`** → `docs/plan-<feature>.md`:
   независимые фазы, первая — сквозной минимум, не больше пяти задач на фазу,
   у каждой фазы свои тесты и конкретный критерий «готова».
3. **`/issues docs/plan-<feature>.md`**: веха на фазу, issue на задачу.
4. **Ветка** — от свежего `main`, по скиллу **`github-flow`**: описательное
   имя, одна ветка на задачу, регулярный `push`.
5. **Коммиты** — по скиллу **`git-commit`**: он разбирает дифф, ставит в
   индекс осмысленными кусками и собирает сообщение по Conventional Commits.
   Каждый коммит называет свой issue.
6. **Pull Request** — ревью и зелёный CI, затем merge в `main` и удаление
   ветки. `Closes #N` закрывает issue самим merge'ем.

🔴 **Задача, которой нет в issue, не реализуется.** Не «нежелательно» —
не реализуется: код без issue не проходит ревью и откатывается.

**Почему так.** Работа идёт сессиями без общего контекста, и до 29 августа
единственным следом задачи была проза журнала: она объясняет, откуда взялся
дефект и чего он стоил, но не отвечает, что взято в работу, кем и сколько
осталось. Девяносто три открытых пункта в голову не помещаются, а сделанное
мимо бэклога не видит ни владелец, ни следующая сессия.

## Когда PRD и план можно не писать

**Одиночная задача, уже описанная в [BUGS.md](BUGS.md) или прямо
поставленная владельцем, заводится сразу issue** — запись журнала служит ей
PRD, а фазы делить не из чего. Условие ровно одно: задача целиком помещается
в один issue и не тянет за собой других. Всё, что больше одной задачи, идёт
полным маршрутом.

## Исключения из «сначала issue» — их четыре

| Случай                                                                                                            | Что делать                                                                             |
| ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **Инцидент**: сайт лежит, заявки не доходят, вход в панель не работает, утёк секрет                               | Чинить немедленно. Issue завести в тот же день постфактум — вместе с записью в журнале |
| **Документы самого маршрута и журналы**: ADR, BUGS, ROADMAP, PRD и планы                                          | Пишутся без issue: PRD на PRD не пишется, а инвариант 15 требует записи в тот же день  |
| **Работа без изменений в репозитории**: диагностика, замеры, чтение кода, просмотр через Playwright MCP           | Issue не нужен — в репозиторий ничего не попадает                                      |
| **Мелочь внутри уже открытого issue**: опечатка, забытый `aria-label`, формат — замеченные по ходу этой же задачи | Идёт в текущий issue. Своего issue не заводит, но и в чужую задачу не переезжает       |

Больше исключений нет. Просьба «сделай быстро мимо процесса» — это просьба
завести issue и сделать по нему: цена оформления одной задачи меньше цены
работы, о которой через месяц никто не вспомнит.

# Стек

**Приложение**

- Next.js 15, App Router, React Server Components
- TypeScript (strict)
- CSS Modules + глобальные CSS-переменные (токены из прототипа)
- Шрифты самохостом через `@font-face` в `shared/styles/fonts.css` — Onest, Manrope, JetBrains Mono (ADR-025)
- Zod — валидация на границе (формы, тела запросов, ENV)
- React Hook Form — только там, где форма действительно сложная

**Данные**

- PostgreSQL 16 + Prisma
- Миграции только через `prisma migrate`, никаких ручных правок схемы на проде

**Инфраструктура**

- Docker Compose: `caddy` (авто-TLS) + `web` (Next standalone) + `worker` (очередь уведомлений) + `db` (Postgres)
- VPS **в РФ** — требование 152-ФЗ, см. [TECH_DECISIONS.md](TECH_DECISIONS.md)
- 🔴 **Разработка в Docker — по умолчанию.** Дев-окружение повторяет прод, чтобы расхождения сред всплывали на первой итерации, а не при деплое (ADR-017). Миграции, сиды и команды пакетного менеджера — через `docker compose exec`
- 🔴 **Второй режим — база в контейнере, приложение на хосте** (ADR-173, [DEPLOY §2.2](DEPLOY.md)). Заведён потому, что контейнер `web` занимает до 2 ГБ и до 740% процессора, и машина владельца этого не тянет: браузер перестаёт открывать страницы. Достоверность даёт первый режим, последнее слово — CI: он собирает боевой образ и гоняет тесты в контейнере

**Уведомления**

- Очередь в БД → воркер с ретраями → каналы `email` (SMTP в РФ) и `telegram`
- Куда уходит уведомление, выбирает владелец в админке; доступы (токен бота, пароль SMTP, транспорт) остаются в ENV (ADR-058)
- Что не дошло и почему — видно там же, с повтором отказа (ADR-061)

**Качество**

- ESLint + Prettier + Stylelint, husky + lint-staged на pre-commit
- commitlint на `commit-msg` — Conventional Commits, см. раздел «Коммиты»
- Vitest + Testing Library — доменная логика и поведение компонентов
- Storybook — витрина UI Kit и блоков лендинга, она же среда разработки компонента
- Playwright — сквозные сценарии и снепшот-тесты историй на четырёх ширинах

Новые зависимости — только с явного согласия пользователя.

# Архитектура

Монолит на Next.js: публичный сайт, админка и API живут в одном приложении. Отдельного бэкенда нет — но **API соблюдает контракт из [API.md](API.md) один в один**, чтобы вынести его в самостоятельный сервис можно было без правок фронта.

🔴 **Когда бэкенд переедет на NestJS — писать его только по скиллу `nestjs-best-practices`.** Владелец объявил такое намерение 27 августа; сам переезд ещё не решён и отменяет ADR-001, поэтому начнётся он с нового ADR. До этого момента бэкенд — это route handlers Next, и правила для них остаются прежними. Правило записано заранее сознательно: решение о переезде и написание первого модуля Nest почти наверняка окажутся в разных сессиях.

## Структура

```
apps/web/                    — приложение; в корне репозитория только инфраструктура и документация
  src/
    app/
    (site)/                  — публичные страницы, общий layout с шапкой и футером
      page.tsx               — лендинг: все коммерческие секции (ADR-049)
      knowledge/[slug]/      — База знаний: листинг и статья
      privacy/               — политика обработки персональных данных
    (admin)/admin/           — админка, свой layout, noindex
    api/                     — route handlers по контракту
    sitemap.ts robots.ts
  entities/                  — доменные сущности: product, price, article, review, lead, crm, settings
    <entity>/
      model.ts               — типы и схемы Zod
      ui/                    — карточки и представления сущности
  features/                  — пользовательские сценарии: lead-form, review-form, calculator, model-picker,
                               crm-calendar (календарь работ), lead-manager, review-moderation, delivery-log
  widgets/                   — крупные секции страниц: hero, catalog, pricing, faq, footer
  shared/
    ui/                      — UI Kit: Button, Input, Select, Card, Badge, Chip, Modal, Skeleton
    lib/                     — утилиты: format, slug, seo, validation
    config/                  — константы, карта URL, тексты, не приходящие из БД
    styles/                  — tokens.css, global.css
  server/
    db.ts                    — экземпляр Prisma
    repo/                    — доступ к данным (Prisma), только серверный код
    services/                — бизнес-правила: что происходит и в каком порядке (ADR-142)
    auth.ts                  — сессия админки
    notifications/           — очередь, каналы, воркер
    revalidate.ts            — точечная ревалидация после правок в админке
```

🔴 **Обработчик маршрута — контроллер, а не место для бизнес-логики (ADR-142).**
Ему принадлежат тело запроса, ловушка для ботов, ограничение частоты, разбор
схемой и код ответа. Всё, что происходит с данными — порядок записей,
транзакции, постановка в очередь, компенсация при сбое, — живёт в
`server/services/` и не знает ни про `Request`, ни про `Response`.

Слой заводится по мере надобности, а не разом на все маршруты: где вся работа
— «прочитать и отдать», сервис не нужен, прокладка ради симметрии только
удлиняет путь до кода.

**Правило зависимостей:** `app → widgets → features → entities → shared`. Импорт «вверх» и вбок между слайсами одного слоя запрещён. Из `shared` нельзя импортировать ничего, кроме `shared`.

## Server / Client

RSC — по умолчанию. `'use client'` ставится на **лист компонента**, а не на секцию целиком: интерактивен ползунок калькулятора, а не вся страница цен.

Любой доступ к БД — только в серверном коде (`repo.ts`, route handlers, server actions). Компонент никогда не обращается к Prisma напрямую.

# TypeScript

Strict обязателен.

Запрещено: `any` · `as` (без явной просьбы) · `@ts-ignore` · `@ts-expect-error` · `!` (ни `x!`, ни `field!: T`).

Предпочитать: вывод типов · дискриминированные объединения · `readonly` · явные типы возврата у экспортируемых функций · union вместо enum.

Данные, приходящие снаружи (тело запроса, ответ погодного API, `process.env`), проходят через Zod-схему. Типы для внутреннего использования выводятся из схем через `z.infer`, а не пишутся руками рядом.

# React и Next

Только функциональные компоненты. Композиция вместо флагов. Ранний возврат вместо вложенных тернарников.

Не оборачивать всё подряд в `memo` / `useMemo` / `useCallback` — только при измеренной пользе.

Бизнес-логика не живёт внутри UI-компонента. Калькулятор монтажа и подбор модели — чистые функции в `entities`, покрытые тестами; компонент только рисует результат.

Данные страницы получает серверный компонент и передаёт вниз пропсами. Никаких `useEffect` + `fetch` для того, что можно отрендерить на сервере.

🔴 **Код на React и Next пишется по скиллу `vercel-react-best-practices`.** Он держит те решения, которые здесь стоят дороже всего: где проходит граница сервера и клиента, что уезжает в бандл, как получаются данные, чем оплачивается каждый `'use client'`. Бюджет собственного слоя JS — 75 КБ (ADR-088), и проедается он не одним большим решением, а десятком мелких, каждое из которых по отдельности выглядит безобидно.

# Стилизация

CSS Modules. Цвета — **только** через переменные из `shared/styles/tokens.css`, ни одного хардкоженного `#RRGGBB` в модулях.

Тёмная тема — через `html[data-theme="dark"]`, переопределяются только значения переменных. Компонент про тему не знает.

Запрещено: глобальные стили вне `global.css` · `!important` · вложенность селекторов глубже двух уровней.

Значения берутся из [DESIGN_BRIEF.md](DESIGN_BRIEF.md) — это перенос дизайна, а не творчество: если в макете `border-radius: 11px`, в коде тоже `11px`, а не «примерно 12».

🔴 **У значений есть внешний эталон — HeroUI** (ADR-169, ADR-170). Он один на весь интерфейс: кит, панель и публичная часть. Меняете компонент или собираете экран — геометрия копируется оттуда: внутренние отступы по размерам, радиусы, толщина границ, тени, плотность и сетка, типографическая шкала, состояния наведения, нажатия, фокуса, ошибки и пустоты. Цвета остаются нашими: светлая тема приведена к AA, и палитра с эталона не берётся; содержательная композиция лендинга — тоже своя. Снятые числа кладутся в токены и в [DESIGN_BRIEF.md](DESIGN_BRIEF.md), а не проставляются по месту.

🔴 **Исключение одно — страница календаря работ.** У неё свой эталон, Apple Calendar ([CRM §3.5.1](CRM.md), ADR-128, ADR-138, ADR-140). К HeroUI она не приводится: это единственная часть интерфейса, которая владельца устраивает.

# Контент

**Никакого инлайн-контента в компонентах.** Пользовательские строки — либо из БД (цены, модели, статьи, отзывы, контакты), либо из `shared/config` (заголовки секций, тексты FAQ, шаги монтажа, разделы «как обманывают»). Компонент ссылается на данные, а не содержит их.

Язык один — русский, i18n не нужен. Но правило «текст отдельно от разметки» остаётся: контент этого сайта — SEO-актив, его правят чаще, чем вёрстку.

# Формы и состояния

Каждая форма обрабатывает четыре состояния: `idle`, `sending`, `success`, `error`. Кнопка блокируется на время отправки. Ошибка объясняет, что делать дальше, и всегда оставляет телефон как запасной путь.

Валидация — на клиенте (мгновенная подсказка) и обязательно на сервере той же Zod-схемой. Клиентская валидация — это UX, а не защита.

Каждый асинхронный блок данных имеет скелетон. Никакого текста «Загрузка…» и прыгающей вёрстки.

# Безопасность

Секреты — только через ENV на сервере, проверяются Zod-схемой при старте: приложение не поднимается с неполной конфигурацией.

Публичные `POST` (`/api/leads`, `/api/reviews`) — rate-limit по IP, honeypot-поле, ограничение размера загружаемого файла и проверка реального типа изображения, а не расширения.

Загруженные файлы никогда не отдаются из директории, где могут быть исполняемые файлы. Имя файла генерируется сервером, оригинальное имя не используется.

Админка — httpOnly + `Secure` + `SameSite=Lax` cookie, пароль через Argon2id, защита от перебора. Флаг `Secure` — по схеме `SITE_URL`: на проде обязателен (конфигурация с http в production не поднимается), на http-стенде снимается, иначе браузер выбрасывает cookie и вход невозможен (ADR-102). `/admin` закрыт в `robots.txt` и отдаёт `noindex`.

Внешние API (Telegram, погода, SMTP) считаются ненадёжными по умолчанию: таймаут, ретраи, деградация без падения страницы.

| Уровень                           | Что покрываем                                                                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Unit (Vitest)                     | калькулятор монтажа, действующая цена со скидкой, подбор модели, объединение характеристик, слаги, рендер разметки статей, JSON-LD     |

| Storybook                         | каждый компонент UI Kit и каждый блок лендинга — во всех состояниях: базовое, наведение, отключено, загрузка, ошибка, варианты, пустое |
| Визуальная регрессия (Playwright) | снепшоты историй Storybook на **320, 375, 768, 1200** в обеих темах. Свой раннер, без Chromatic                                        |
| Integration                       | route handlers: валидация, статусы ошибок, постановка в очередь уведомлений                                                            |

🔴 **У каждого компонента UI Kit и каждого блока лендинга есть story.** Компонент, которого нет в Storybook, нельзя посмотреть иначе, чем собрав всё приложение, — и он не проходит ревью.

Доменная логика калькулятора — тесты пишутся вместе с ней, а не потом. Ошибка в цене дороже ошибки в вёрстке.

## 🔴 Как проверяется сделанное

Правило одно и без исключений: **то, что нельзя увидеть, считается несделанным.**

| Что сделано                                          | Чем обязано быть проверено                                                                                           |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Фронтенд — вёрстка, состояния, интерактив, адаптив   | **Скилл `ui-ux-pro-max` + Playwright MCP: открыть страницу и посмотреть.** Скриншот на нужных ширинах, в обеих темах |
| Бэкенд — маршруты, формы, админка, сквозные сценарии | **E2E Playwright** — сценарий целиком, от действия человека до записи в БД                                           |

**Фронтенд принимается глазами, а не тестами.** Зелёный `vitest` ничего не говорит о том, что элемент не уехал за край, что контраст читается и что содержимое не прыгает. Правку публичной страницы или панели нельзя объявить готовой, не открыв её через Playwright MCP и не посмотрев. Это не замена снепшотам Storybook — это условие до них: снепшот фиксирует то, что уже проверено человеком, а не заменяет проверку.

🔴 **Прыжок вёрстки проверяется измерением, а не снимком.** Снимок показывает одно состояние и на вопрос «двигается ли кнопка, когда меняется соседний блок» не отвечает вовсе. Если правка про устойчивость раскладки — резерв места, скелетон, подмена содержимого, — проверкой служит координата контрольного элемента во всех состояниях, снятая в браузере. «Стоит на месте» — это одно число, а не впечатление: резерв под скидку в подборе выглядел готовым и на глаз, и на снимке, а измерение показало разброс в 22px.

🔴 **Смотреть — мало, смотреть нужно по чек-листу.** Любая проверка UI и UX идёт через скилл **`ui-ux-pro-max`**: он задаёт, на что смотреть (иерархия, ритм, состояния, контраст, доступность, отзывчивость) и чем это мерить. Взгляд без чек-листа замечает только то, что бросается в глаза, — а вылезающая за край капсула и полоса цифр во второй строке в глаза не бросались до самого показа владельцу.

**Бэкенд принимается сценарием.** Маршрут, форма, действие в панели — сквозной тест, доходящий до базы: инвариант 2 (заявка сначала в БД) проверяется только так. Юнит на функцию-обработчик этого не показывает.

**TDD — способ по умолчанию.** Сначала падающий тест, потом код. Строго обязателен там, где ошибка стоит денег: цены, скидки, калькулятор, доступ по ролям, запись заявки. Для вёрстки TDD не работает — там роль первого шага играет Storybook-история и просмотр через Playwright MCP.

🔴 **Тесты гоняются до задачи и после неё.** До — чтобы знать, что было сломано до тебя, и не чинить чужое молча под видом своей работы; после — чтобы отчёт «сделано» опирался на прогон, а не на впечатление.

Прогон идёт там, где работает приложение (ADR-173). Полный состав в Docker:

```
docker compose -f docker-compose.dev.yml exec -T web pnpm check
```

Приложение на хосте — там же:

```
pnpm --filter web check
```

🔴 **`tsc` лжёт, когда среда разъехалась с проверкой.** Типы типизированных маршрутов Next генерируются в `.next`: пока приложение работало в контейнере, `.next` лежал в томе, и `pnpm typecheck` с хоста падал на существующих маршрутах (`RouteImpl<"/admin/login">`), а в контейнере тот же код проходил (ADR-147). Правило от этого не смягчается, а уточняется: **проверка типов живёт там же, где `.next`**. Приложение в контейнере — `tsc` в контейнере; приложение на хосте — `tsc` на хосте, и он проходит начисто.

Коммит проверяется хуком: линтеры и формат по изменённым файлам плюс `vitest related` — тесты, зависящие от них. Зелёный хук означает «изменённое не сломано», а не «проект цел»: целиком проверяет `pnpm check`.

Отчёт «сделано» без такой проверки — это отчёт «написано». Разница обнаруживается у владельца.

# Журнал решений

🔴 Любое принятое решение — архитектурное, продуктовое, инфраструктурное — записывается в [DECISIONS.md](DECISIONS.md) **в тот же день**, в формате «контекст → решение → следствия → что отвергнуто».

Записывается и то, что **отвергли**: без этого следующая сессия честно переизобретёт отвергнутый вариант и потратит день, чтобы прийти к тому же выводу.

# Коммиты

🔴 **Коммит собирается скиллом `git-commit`, а не руками.** Он читает дифф,
раскладывает его по осмысленным коммитам и пишет сообщение в формате ниже —
поэтому «забыл scope» и «свалил рефакторинг с фичей» перестают случаться.
Ветвление и Pull Request — скилл `github-flow` (инвариант 19).

**Conventional Commits**, описание — по-русски.

```
<type>(<scope>): что делает изменение

Тело: зачем это изменение, а не что в нём. Перечисление файлов не нужно —
их видно в диффе. Ширина 72 символа.
```

🔴 **Заголовок отвечает на вопрос «что делает?», а не приказывает.**
«Записывает», а не «запиши»; «не принимает», а не «не принимай». Разница не
стилистическая: историю читают, когда ищут, где что-то изменилось, — и
`git log` тогда читается как перечень того, что каждый коммит делает с
системой, а не как список поручений неизвестно кому.

| Так                                        | Не так                                 |
| ------------------------------------------ | -------------------------------------- |
| `fix(catalog): ставит цену на общую линию` | `fix(catalog): поставь цену на линию`  |
| `feat(site): показывает скидку в карточке` | `feat(site): покажи скидку в карточке` |
| `ci: не отменяет прогоны main`             | `ci: не отменяй прогоны main`          |

🔴 **Коммит называет свой issue.** В теле — `Closes #N` у коммита, который
задачу закрывает, и `Часть #N` у промежуточного. GitHub сам подтягивает
упоминание в ленту issue, а по ключевому слову закрывает её при попадании в
`main`: руками issue не закрывается. Номер стоит в теле, а не в заголовке —
заголовок и без него редко умещается в 72 знака.

```
fix(catalog): ставит цену карточки на общую базовую линию

У модели со скидкой блок цены занимал три строки, у остальных одну, и
главная цифра карточки плясала по ряду.

Closes #42
```

**Типы:** `feat` новая функциональность · `fix` исправление · `docs` документация · `refactor` без изменения поведения · `perf` производительность · `test` тесты · `style` форматирование · `build` сборка и зависимости · `ci` пайплайны · `chore` рутина.

**Scope** — область проекта, а не путь к файлу: `site`, `catalog`, `admin`, `seo`, `api`, `notify`, `db`, `ui`, `infra`, `docs`. Для изменения, задевающего всё, scope опускается.

**Ломающие изменения** — `feat(api)!:` и секция `BREAKING CHANGE:` в теле. На этом проекте это, прежде всего, изменения контракта и схемы БД.

Хорошо: `feat(catalog): считает скидку из цены и периода, процент выводит сам`
Плохо: `fix: правки` · `feat: добавил компонент Button.tsx` · `feat: добавь компонент`

🔴 **Никаких упоминаний ИИ-ассистентов в истории git** — ни в теле, ни в трейлерах, ни в соавторстве. Автор коммита — человек, который принял решение.

Заголовок — до 72 символов, без точки в конце, в настоящем времени и третьем лице: «добавляет», «исправляет», «перестаёт». Безличное «поддержка X» тоже годится — оно отвечает на тот же вопрос.

Один коммит — одно изменение. Не смешивать рефакторинг с новой функциональностью: иначе `git bisect` бесполезен, а ревью превращается в чтение диффа целиком.

Формат проверяется автоматически хуком `commit-msg` (commitlint). Обходить хук нельзя.

# Pre-commit

`husky` + `lint-staged` прогоняют ESLint, Prettier и Stylelint по staged-файлам плюс `vitest related`. Обходить хук (`--no-verify`), чтобы залить код, не проходящий линт, нельзя.

🔴 **Коммитить файл куском можно и нужно** (ADR-163). Когда в общий журнал пишут две сессии, `git apply --cached` со своим куском — единственный способ не отнять чужую работу: нативная ветка хука прячет непроиндексированное стешем, и в коммит уходит ровно то, что положили в индекс. В контейнерной ветке стеш выключен — там частично проиндексированный коммит запрещён, и хук назовёт файлы и скажет, что делать.

🔴 **Хук держит замок на репозиторий.** Два коммита одновременно ломают друг друга: второй ждёт первого до двух минут и отказывается, если тот не закончил. Замок старше пятнадцати минут считается брошенным и снимается сам.

Задачи идут последовательно (`--concurrent false`): при параллельных упавшая убивает соседние, и в выводе остаётся `KILLED` вместо причины.

# Чек-лист перед выдачей кода

- Страница отдаётся сервером с данными?

- Нет ли зашитых цен, телефонов, адресов, реквизитов, названий — вообще любых данных компании?
- Задача заведена issue, и её номер стоит в теле коммита?
- Решения, принятые по ходу, записаны в DECISIONS.md?
- Секреты не утекли на клиент?
- Обработаны загрузка, ошибка, пустое состояние?
- Соблюдено правило зависимостей слоёв?
- Есть ли уже такой компонент в `shared/ui`?
- Доступно с клавиатуры, контраст в обеих темах?
- Вписывается в бюджет производительности?
- Комментарии по-русски и объясняют «почему»?

Если хоть один ответ «нет» — доработать до выдачи.
