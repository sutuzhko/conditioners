# PRD: Разметка задач по осям — понятно, чего касается, не открывая issue

**Дата**: 2026-09-07
**Статус**: Draft

## Цель

Сделать так, чтобы по строке ярлыков было видно, **чего задача касается**, и
чтобы бэклог читался срезами, а не списком из 88 строк. Сегодня ярлыки лежат
на одной плоской оси и смешивают «что делаем» с «чем это пахнет технически»,
а самый частый из них — `ui`, 29 задач из 88 — одинаково стоит и на публичной
части, и на панели, то есть ровно там, где различие нужно, его нет.

## Пользовательские сценарии

- Владелец открывает список задач → по ярлыкам видно часть продукта и раздел,
  заходить внутрь не нужно
- Владелец хочет видеть только склад → один фильтр `label:раздел/склад`
  вместо чтения заголовков
- Владелец открывает таблицу бэклога → задачи сгруппированы по разделу, у
  каждого раздела счётчик, видно перекос
- Агент заводит issue по плану → словарь осей лежит в репозитории, и ярлыки
  берутся из него, а не выдумываются
- Агент открывает Pull Request → ярлык раздела ставится сам, по изменённым
  путям, и расходиться с кодом не может
- Агент ставит две «части» или ни одной → проверка пишет комментарием, что
  ось нарушена, до того как задача уедет в бэклог
- Владелец ищет, где копился долг по доступности → `label:качество/доступность`
  поперёк всех разделов

## В скоупе

**Словарь из четырёх осей.** Значения выведены из маршрутов приложения и
слоёв `entities` / `features` / `widgets`, а не придуманы:

- **`часть/`** — где в продукте. Обязательна, ровно одна. Семь значений:
  `сайт`, `панель`, `api`, `общее`, `инфра`, `процесс`, `документы`
- **`раздел/`** — что именно. Ноль или больше. Двадцать значений по разделам
  панели и сайта: `каталог`, `характеристики`, `прайс`, `скидки`, `заявки`,
  `клиенты`, `наряды`, `календарь`, `склад`, `монтажники`, `отзывы`,
  `знания`, `настройки`, `уведомления`, `доступ`, `лендинг`, `сравнение`,
  `кит`, `медиа`, `погода`
- **`тип/`** — что делаем. Обязательна, ровно одна. Шесть значений:
  `дефект`, `улучшение`, `аудит`, `рефакторинг`, `проверка`, `решение`
- **`качество/`** — сквозное требование, поперёк разделов. Ноль или больше.
  Семь значений: `доступность`, `производительность`, `безопасность`, `seo`,
  `адаптив`, `тёмная-тема`, `пд`

Плюс служебные плоские: `vr:accepted` (его читает CI в двух местах
`ci.yml`, имя менять нельзя), `blocked`, `duplicate`, `wontfix`.

Цвет — один на ось: строка ярлыков читается за полсекунды, потому что
GitHub оси не рисует.

**Словарь живёт в репозитории.** `scripts/labels.mjs` — источник правды,
скрипт синхронизации приводит GitHub к файлу. Новый ярлык приезжает Pull
Request'ом и обсуждается, а не заводится втихую в вебе. Сегодня словарь
существует только на GitHub и в `docs/` не описан ни строкой.

**`docs/LABELS.md`** — что означает каждая ось, где проходят границы между
похожими ярлыками, какому пути в коде соответствует раздел.

**Разметка 88 открытых задач** по новому словарю; старые `ui`, `data`,
`infra`, `process`, `calendar`, `design`, `test`, `audit`, `bug`,
`enhancement`, `security`, `accessibility`, `documentation` снимаются —
две конкурирующие разметки хуже одной плохой. Закрытые 407 не трогаем.

**Ярлык ставится машиной, а не памятью:**

- `.github/labeler.yml` — карта «путь → раздел», ярлык на Pull Request по
  изменённым файлам
- проверка осей на событие issue: ровно одна `часть/`, ровно один `тип/`;
  нарушение — комментарий боту, а не молчание
- скилл `issues` учится словарю: сегодня в нём написано `--label "..."` без
  словаря вообще

**Витрина:** проект с таблицей и срезом по `раздел/`, пять-шесть
сохранённых видов на частые запросы.

**ADR** в [DECISIONS.md](DECISIONS.md) — оси, границы, что отвергнуто.

## Не в скоупе

- **Перенос репозитория в организацию и нативные issue types.** Отдельное
  решение со своей ценой (защита `main` на приватном репозитории — тариф
  Team, минуты Actions — от $270 в месяц при нынешних 725 прогонах). Словарь
  делается так, чтобы ось `тип/` позже конвертировалась в нативные типы без
  переразметки
- **Приватность репозитория и свой раннер** — своим ADR
- **Sub-issues** вместо задач «Проверка: …» — просится, но это правка
  структуры бэклога, не разметки
- **Разметка 407 закрытых задач** — цена есть, пользы нет
- **Приоритет как ось** — сегодня его роль играют вехи, второй источник
  правды не заводим
- **Статус в ярлыках** («в работе», «на ревью») — это поле проекта

## Технические ограничения

- **GitHub не знает про оси.** Нельзя объявить «ровно одна `часть/`» — он не
  мешает поставить три или ноль. Держится проверкой на событие issue, а не
  настройкой
- **`vr:accepted` читает CI** — `ci.yml:609` и `ci.yml:1111`. Переименование
  ломает приём визуальных расхождений
- **Issue Forms ставят фиксированный набор ярлыков на шаблон**, а не по
  ответу в выпадающем списке. Ответ превращает в ярлык отдельный workflow
- **Сохранённых видов — 25 на репозиторий**, вид на каждый ярлык не сделать;
  срез по полю даёт проект, а не виды
- **Разделов больше, чем частей**: у задачи может быть два раздела (расход
  материалов в наряде — это `наряды` и `склад`), и это норма, а не ошибка
  разметки

## Критерии готовности

- [ ] `scripts/labels.mjs` описывает все четыре оси и служебные ярлыки;
      у каждого ярлыка есть описание и цвет своей оси
- [ ] Скрипт синхронизации приводит ярлыки репозитория к файлу и повторный
      запуск ничего не меняет
- [ ] `docs/LABELS.md` объясняет каждую ось и границы между похожими
      ярлыками; на каждый `раздел/` указан путь в коде
- [ ] У всех 88 открытых задач ровно одна `часть/` и ровно один `тип/`
- [ ] Ни на одной открытой задаче не осталось ярлыков старого набора,
      кроме `vr:accepted`
- [ ] Pull Request, тронувший `apps/web/src/app/(admin)/(panel)/stock/`,
      получает `раздел/склад` без участия человека
- [ ] Issue, заведённая без `часть/` или с двумя `тип/`, получает
      комментарий проверки
- [ ] Скилл `issues` ставит ярлыки только из словаря
- [ ] Проект показывает бэклог таблицей со срезом по `раздел/`
- [ ] Решение записано в [DECISIONS.md](DECISIONS.md)
