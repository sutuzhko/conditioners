## 1. Откуда это

25 августа 2026 владелец прислал новый handoff из Claude Design. В нём — файл
`Админка CRM.dc.html` и его мок-хранилище `crm-data.js` (ключ `tk-crm-v3`).
Прототипы лежат в `design/` и версионируются вместе с кодом (ADR-185).
Исключение — два ранних файла с действующим токеном Telegram-бота: они
остались в `.gitignore` поимённо, потому что git ничего не забывает.

Прежний прототип `Админ-панель.dc.html` знал шесть разделов: Цены, Модели,
Контакты, Юрлицо, База знаний, Отзывы. Новый — тринадцать, и шесть из них
описывают то, чего в приложении нет вовсе: **работу компании после того, как
заявка получена**.

Панель перестаёт быть редактором содержимого сайта и становится рабочим
инструментом: кто выехал, что везёт, сколько взял с клиента, сколько должен
получить сам.

## 2. Что панель умеет сейчас

Восемь разделов (`widgets/admin-shell/content.ts`): Календарь работ, Компания,
Каталог, Цены на монтаж, База знаний, Отзывы, Заявки, Уведомления — плюс сводка
на `/admin`.

Три несвязанные плоскости данных:

| Сущность       | Роль                                  | Связи                         |
| -------------- | ------------------------------------- | ----------------------------- |
| `Lead`         | входящий поток с сайта, 4 статуса     | → `CrmEvent.leadId` (необяз.) |
| `CrmEvent`     | график работ, клиент вписан строками  | ← `Lead`                      |
| `Notification` | исходящая доставка владельцу, очередь | нет                           |

Между ними одна необязательная связь и один мостик в интерфейсе — кнопка
«В календарь» на карточке заявки.

Один пользователь без роли (`AdminUser`), проверка доступа бинарная: вошёл или
нет.

## 3. Что появилось в новом дизайне

### 3.1. Роли и второй тип пользователя — монтажник 🆕

Главное изменение, от которого зависит всё остальное. В прототипе вход
разводит по логину: владелец видит тринадцать разделов, монтажник — три
(«Мои заказы», «Календарь», «Профиль»).

Монтажник — это учётная запись: имя, логин, телефон, дата начала работы,
признак активности, пароль, выдаваемый владельцем. Отключение закрывает вход,
удаление убирает аккаунт — выполненные заказы остаются в истории.

Что монтажник **не видит**: сумму заказа (кроме случая оплаты наличными на
объекте — там сумма нужна, чтобы её принять), внутренние заметки владельца,
штрафы, чужие наряды, все разделы про сайт.

### 3.2. Клиенты 🆕

База клиентов, отдельная от заявок: имя, телефон, адрес, заметка, дата
появления. Поиск по имени, телефону и адресу, страницы по 8 записей.

Карточка клиента показывает две вещи, которых сейчас взять неоткуда:

- **Установленная техника** — появляется сама после выполненного монтажа, с
  фотографией установки и подсказкой «ТО через год от даты монтажа»;
- **История заказов** — все наряды этого человека с суммами и статусами.

Дедупликация по телефону: заявка от уже известного номера привязывается к
существующему клиенту, а не плодит второго.

### 3.3. Заказы (наряды) 🆕

Центральная новая сущность. Наряд — это работа с деньгами, датой и
исполнителем.

**Шапка:** номер (сквозной счётчик), тип (Монтаж · ТО · Ремонт), клиент,
монтажник, статус, дата, время, длительность в часах.

**Статусы:** Новый → Назначен → В работе → Выполнен, плюс Отказ. Монтажнику
доступны только два перехода: «В работе» и «Выполнен».

**Объект:** адрес, подъезд и домофон, дополнительный телефон на объекте, этаж,
признак высотных работ.

**Оборудование — список позиций,** а не одно поле. По каждой позиции: тип
(кондиционер, холодильник, компрессор, вентиляция, тепловая завеса, другое),
модель, чьё оборудование (наше — продажа с монтажом, клиента — только работы),
длина трассы, диаметр, штробление.

Это существенно: половина заказов — монтаж техники, купленной клиентом
самостоятельно, и в одном выезде может быть два блока с разными условиями.

**Деньги:** способ оплаты (клиент платит компании или наличными монтажнику на
объекте), сумма заказа, выплата монтажнику, штраф с причиной.

**Работа с нарядом — три вкладки:**

1. **Наряд** — данные выше, для владельца в правке, для монтажника на чтение;
   там же «Итог работ»: доп. работы и материалы по факту + отчёт с датой.
2. **Чеклист выезда** — «что взять с собой». Собирается автоматически из
   данных наряда: тип работ даёт инструмент, каждая позиция — свою трассу и
   диаметр, штробление добавляет штроборез, высотные работы — страховку,
   оплата наличными — строку «принять от клиента N ₽». Пункты отмечаются при
   сборах, можно дописать свои и пересобрать заново.
3. **Документы и фото** — договор, гарантийный талон, акт работ, счёт,
   замерный лист; фото места установки (до выезда, видит монтажник) и фото
   выполненных работ (загружает монтажник, остаются в истории клиента).

**История заказа** — кто и когда менял статус, кого назначили, когда заполнили
итог.

**Список заказов:** поиск по номеру, клиенту, адресу и модели; фильтр по
периоду (всё время / этот месяц / прошлый); вкладки Активные · Новые · История
· Отказы · Все; страницы по 8.

### 3.4. Обращение → клиент → заказ 🆕

Из карточки заявки два действия: «Создать заказ» и «В клиенты». Первое заводит
клиента (или находит по телефону), переводит заявку в работу и открывает
черновик наряда с подставленным адресом, комментарием и типом работ,
угаданным по теме обращения.

Сейчас из заявки можно только завести дело в календаре.

### 3.5. Календарь — расширение существующего

| Что                                        | Сейчас | В дизайне |
| ------------------------------------------ | ------ | --------- |
| Вид «месяц»                                | есть   | есть      |
| Вид «неделя» — колонки дней                | нет    | есть      |
| Вид «день» — сетка часов с линией «сейчас» | нет    | есть      |
| События без времени отдельной группой      | нет    | есть      |
| Раскрытие карточки с деталями наряда       | нет    | есть      |
| Быстрое добавление дела в выбранный день   | есть   | есть      |
| Личные цвета видов у каждого пользователя  | нет    | есть      |
| Синхронизация с Google и Яндекс Календарём | нет    | заявлена  |

Наряды попадают в календарь наравне с делами: у монтажника календарь — это его
выезды.

### 3.5.1. Эталон — календарь Apple 🆕

✅ **Сделано 27 августа.** Решения переделки — ADR-128 и ADR-140, хранение
рабочего окна и переработки — ADR-138. Вне первой версии осознанно: поиск по
календарю, горячие клавиши, многодневные записи, перетаскивание по
горизонтали.

Владелец забраковал наш календарь целиком (26 августа) и задал ориентир
прямо: «найди как устроен календарь Apple и сделай так же». Ниже разбор
эталона — он же техническое задание на переделку. Решения — ADR-128.

**Общее для всех видов**

- Календарь занимает экран целиком. **Боковой колонки с деталями дня
  нет.** Детали записи открываются всплывающей карточкой у самой записи:
  название, время, место, кнопки правки и удаления.
- Слева — список календарей с галочками: какие слои показывать. Каждый
  календарь красится своим цветом.
- Шапка: стрелки «раньше/позже», «Сегодня», переключатель видов, поиск,
  «+». 🔴 Поиск идёт по клиенту, адресу и заметке среди дел, нарядов и
  заявок и **не ограничен показанным периодом**: ищут именно тогда, когда не
  помнят, в каком месяце был выезд. Монтажник находит только свои наряды —
  условием запроса, а не фильтром после него (issue #126–#129,
  [API §9](API.md)). Выбранная находка открывает **день** записи и
  подсвечивает её кольцом на пять секунд — во всех трёх видах.
- Клик по пустому месту сетки создаёт запись на этот час; протяжка задаёт
  длительность. Готовая запись двигается перетаскиванием, края тянутся.
- Горячие клавиши на виды, «Сегодня» и переход по периодам: **D** день,
  **W** неделя, **M** месяц, **T** сегодня, **←/→** предыдущий и следующий
  период, **?** подсказка. 🔴 Читаются по **позиции** клавиши, а не по
  набранному символу: на русской раскладке те же клавиши дают «в», «ц», «ь»,
  «е», и календарь обязан слушаться их так же (issue #121–#125).

**День и неделя — часовая сетка**

- Шапка колонок: день недели и число, сегодня выделено.
- Под шапкой — **полоса «весь день»**: записи без времени и многодневные;
  многодневная тянется через колонки. Полоса растёт и сворачивается.
- Ниже — часы: подпись слева, линия на каждый час, слабая на получас.
- Запись — прямоугольник, позиция и высота строго по времени. Короткая
  запись получает минимальную читаемую высоту, но не врёт о начале.
- Пересекающиеся записи делят ширину колонки; когда их много — лесенкой с
  наложением.
- Линия текущего времени с кружком — только в колонке сегодняшнего дня.
- Прокрутка вертикальная: открывается рабочая часть суток, ночь доступна
  прокруткой.

**Месяц — обзор, а не планировщик**

- Сетка недель одинаковой высоты.
- В клетке — строки записей: цветная точка, время, название. Запись «весь
  день» — сплошная плашка через нужные дни.
- Не помещается — «Ещё N». Клик по дню открывает день.
- Вертикали времени в месяце нет: точное время рисуется там, где есть
  часы.

**Чем наш календарь отличается от эталона**

- Слои — это люди, а не календари: занятость монтажников включается
  кнопкой, каждый человек своим цветом плюс инициалы (ADR-123).
- Рабочее окно задаёт владелец, и переработка за его границами
  отмечается — у Apple такого понятия нет, у монтажной компании оно
  основное.
- Заявка с сайта живёт в полосе «весь день», пока ей не назначили время.

### 3.6. Монтажники 🆕

Список команды с показателями: выполнено заказов, заработано (сумма выплат по
выполненным), штрафы. Переключатель «Активен / Не работает» прямо в списке.

Карточка: управление аккаунтом (имя, логин, телефон, новый пароль, отключение,
удаление), четыре показателя, все заказы монтажника, разбор штрафов с
причинами и **заметки владельца** — монтажник их не видит.

### 3.7. Профиль 🆕

Личные данные (имя, телефон), логин на чтение, смена пароля, выбор темы
интерфейса. Есть у обеих ролей.

### 3.8. Обзор — расширение сводки

Пять плиток-счётчиков, каждая ведёт в свой раздел: новые обращения, активные
заказы, клиентов в базе, активных монтажников, отзывов на модерации. Ниже —
«Ближайшие дела»: наряды и дела календаря вперемешку.

Сейчас плиток четыре и они про содержимое сайта (моделей, статей), а не про
работу.

### 3.9. Чего из дизайна мы не берём

- **Демо-вход** двумя кнопками и хранение сессии в `sessionStorage` — это
  приём макета.
- **Тумблеры уведомлений** (4 переключателя + `chatId`) — в приложении уже
  богаче: выбор каналов, адресаты, готовность канала, журнал доставки с
  причиной отказа и повтором (ADR-058, ADR-061). Откат к макету был бы
  потерей.
- **Единственное фото у модели** — в приложении уже несколько с выбором
  главного.
- **Отсутствие скидки** в редакторе модели — в приложении скидка с периодом
  (ADR-011).
- **Загрузка фото в `dataURL`** — файлы уходят в том через `server/uploads`.

## 4. Модель данных — что добавляется

Существующие сущности не ломаются. `CrmEvent` остаётся: он про напоминания,
наряд — про работу с деньгами (см. §5).

```prisma
enum AdminRole { OWNER  INSTALLER }

model AdminUser {
  // + role, name, phone, active, startedAt
  // + orders, notes
}

model InstallerNote {        // заметки владельца о монтажнике; тот их не видит
  id, userId, text, createdAt
}

model Client {
  id, name, phone (@unique по нормализованному), address, note, createdAt
  orders, units
}

model ClientUnit {           // техника, стоящая у клиента
  id, clientId, model, installedAt, orderId?, photo?, warrantyUntil?
}

enum OrderType   { INSTALL  SERVICE  REPAIR }
enum OrderStatus { NEW  ASSIGNED  IN_PROGRESS  DONE  CANCELLED }
enum PaymentMode { COMPANY  CASH_TO_INSTALLER }

model Order {
  id, number (сквозной), type, status
  clientId, installerId?
  at (UTC, показывается в московском), durationH
  address, intercom, phone2, floor, heightWorks
  payment, price, installerFee
  comment          // видит монтажник
  ownerNote        // не видит монтажник
  penaltySum, penaltyReason
  extraWork, report, resultAt
  leadId?          // из какого обращения вырос
  units, checklist, docs, photos, history
}

model OrderUnit      { id, orderId, equip, model, source, trassaM, diameter, shtrob, sort }
model OrderChecklistItem { id, orderId, text, done, sort }
model OrderDocument  { id, orderId, kind, name, url, sizeBytes, createdAt }
model OrderPhoto     { id, orderId, stage /* BEFORE | AFTER */, url, sort }
model OrderHistory   { id, orderId, authorId?, text, createdAt }
```

Номер заказа — не автоинкремент Postgres: владелец видит его как «№ 1059» и
ждёт непрерывности. Счётчик живёт в `Setting` под ключом `orderSeq` и
инкрементируется в транзакции создания.

Телефон клиента хранится и в исходном виде (как ввели), и нормализованным —
поиск и дедупликация идут по цифрам.

## 5. Наряд или дело: где что заводится

В прототипе быстрое добавление в календарь предлагает пять видов, включая
Монтаж, ТО и Ремонт, — те же, что и типы наряда. Это два источника правды об
одном и том же выезде.

**Решение:** работа с исполнителем и деньгами — всегда наряд; дело в календаре
остаётся напоминанием без денег.

| Что                                 | Чем заводится     |
| ----------------------------------- | ----------------- |
| Монтаж, ТО, ремонт                  | наряд (`Order`)   |
| Звонок, замер, встреча, «не забыть» | дело (`CrmEvent`) |

Виды `INSTALL` и `SERVICE` у дела остаются ради записей, заведённых до
появления нарядов, но в форме создания дела больше не предлагаются.

Календарь показывает и то, и другое.

## 6. Разграничение доступа

| Данные                              | Владелец | Монтажник                   |
| ----------------------------------- | -------- | --------------------------- |
| Свои наряды                         | все      | только назначенные ему      |
| Сумма заказа                        | видит    | только при оплате наличными |
| Своя выплата                        | видит    | видит                       |
| Штраф и причина                     | правит   | не видит                    |
| Заметка владельца по заказу         | правит   | не видит                    |
| Комментарий монтажнику              | правит   | видит                       |
| Данные наряда (адрес, оборудование) | правит   | читает                      |
| Статус наряда                       | любой    | «В работе», «Выполнен»      |
| Чеклист выезда                      | правит   | отмечает, добавляет свои    |
| Фото «до»                           | грузит   | смотрит                     |
| Фото «после»                        | грузит   | грузит                      |
| Итог работ                          | правит   | заполняет                   |
| Клиенты, монтажники, обращения      | всё      | нет доступа                 |
| Разделы про сайт                    | всё      | нет доступа                 |
| Заметки о монтажнике                | правит   | не видит                    |

🔴 Разграничение проверяется на сервере в каждом обработчике, а не скрытием
кнопок: скрытая кнопка — это подсказка интерфейса, а не защита.

## 7. Характеристики товара — полная карточка

Отдельная просьба владельца: в карточке кондиционера должна быть **полная**
техническая информация, а не пять строк.

🔴 Ограничение — инвариант 6: фиксированного списка характеристик не бывает ни
в коде, ни в схеме БД. Владелец заводит модель с новой характеристикой и не
зовёт разработчика.

**Решение — справочник, а не колонки.** В `Setting` появляется ключ `specs`:
редактируемый владельцем список групп и полей (название, единица измерения,
подсказка, порядок). Справочник ничего не ограничивает — он:

- подсказывает названия в редакторе модели (автодополнение и кнопка «добавить
  типовые» для группы);
- задаёт **группировку** характеристик в карточке товара;
- задаёт **порядок строк** в таблице сравнения.

Характеристика, которой в справочнике нет, работает как прежде и попадает в
группу «Прочее». Таблица сравнения по-прежнему строится объединением ключей
всех видимых моделей.

Справочник сидируется набором, который закрывает потребительский и монтажный
разрез:

| Группа              | Поля                                                                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Основное            | мощность охлаждения (кВт), мощность обогрева (кВт), холодопроизводительность (BTU), потребляемая мощность (кВт), площадь (м²), тип компрессора |

Монтажные параметры (диаметры, длина трассы) в потребительских описаниях
обычно не публикуют — здесь они нужны: по ним собирается чеклист выезда и
считается смета трассы. Поэтому в карточке они лежат отдельной группой, ниже
потребительских.

## 8. Что ещё нужно бизнесу — предложения

Ниже — то, чего в присланном дизайне нет, но без чего процессы компании
остаются в голове у владельца. Порядок — по влиянию на деньги.

### 8.1. Материалы и остатки

Трасса, фреон, кронштейны, дренаж, короб, крепёж. Монтажник, уехавший без
трубы нужного диаметра, — это сорванный день и перенесённый клиент.

Минимум: справочник материалов с остатком, списание при закрытии наряда,
порог «пора заказывать». Связка с уже существующим чеклистом выезда прямая:
чеклист знает, что нужно, склад — есть ли оно.

**Принято владельцем 26 августа (ADR-111):** склад делаем — требования
развёрнуты в §11, открытые вопросы в [BUGS.md](BUGS.md).

### 8.2. Себестоимость и маржа заказа

Сейчас в наряде две суммы: сколько взяли с клиента и сколько отдали
монтажнику. Между ними — закупка техники и материалы, и без них владелец не
знает, какой заказ был прибыльным.

Нужно: закупочная цена позиции, материалы по факту, вычисляемая маржа. Это
особенно важно при позиционировании «продаём технику почти в ноль,
зарабатываем на монтаже» — проверить это утверждение сейчас нечем.

### 8.3. Расчёты с монтажниками

Оплата наличными на объекте есть флагом, но нет факта «деньги сданы». Нужен
реестр за период: начислено, удержано, выплачено, остаток — и закрытие
расчёта. Иначе это считается в блокноте.

🔴 Юридическая оговорка к слову «штраф» — см. §9.

### 8.4. Автоматические напоминания о ТО

Ежегодное обслуживание — третий источник денег и единственный, который
сглаживает сезонность. В дизайне карточка клиента уже пишет «ТО — 14 июля»,
но это просто подпись: никто не напомнит.

Нужен генератор: за N дней до годовщины монтажа заводится дело «предложить
ТО» с телефоном и адресом. Один раз настроить — дальше поток заявок зимой
появляется сам.

Это же снимает возражение из ADR-080 («уведомлять о делах, которых никто не
завёл, не о чем») — здесь дела заводятся сами.

### 8.5. Загрузка монтажников и конфликты времени

**Принято владельцем 26 августа (ADR-123):** наряд становится событием
календаря, занятость считается по нарядам и отлучкам вместе, а занятость
команды показывается слоем поверх календаря владельца — все монтажники
разом, цвет на человека, события внахлёст.

Календарь показывает события, но не отвечает на вопрос «влезет ли ещё один
монтаж к Дмитрию в четверг». Нужны: вид «по монтажникам» (колонка на
человека) и предупреждение при назначении на занятое время. Длительность в
наряде уже есть — считать есть чем.

### 8.6. География выездов

Адрес — строка. Для планирования дня нужен район, чтобы не гонять человека
через весь город дважды. Минимум — поле «район» со справочником из настроек
`area`, который уже есть.

### 8.7. Воронка и источники

`Lead` уже пишет `utm`, `referrer`, `sourceUrl` — но в панели этого не видно.
Отчёт «обращений → заказов → денег, по источникам» отвечает, куда имеет смысл
тратить рекламный бюджет. Без него бюджет тратится вслепую.

### 8.8. Гарантия и повторные выезды

Дата монтажа плюс срок гарантии отличает гарантийный случай от платного
ремонта. Нужны: срок гарантии в карточке техники, признак «гарантийный выезд»
и «переделка» в наряде со ссылкой на исходный заказ. Переделка обычно стоит
клиенту ноль — и должна быть видна в статистике монтажника.

### 8.9. Печать документов из данных наряда

Договор, акт, гарантийный талон сейчас — загружаемые файлы, то есть ручная
работа в Word и источник ошибок. Все данные для печати уже есть: реквизиты
компании в `Setting`, клиент и позиции в наряде.

### 8.10. Уведомления монтажнику

Очередь уведомлений умеет доставлять и уже работает — но адресат один,
владелец. Монтажнику, которому назначили наряд на завтра, никто не пишет.
Нужны: уведомление о назначении, о переносе и утренний список выездов.

**Принято владельцем 26 августа:** делаем — детали в [BUGS.md](BUGS.md),
запись «У уведомления нет адресата».

### 8.11. Журнал действий

История есть у наряда, но не у остального. С появлением второго пользователя
вопрос «кто снял отзыв с публикации» перестаёт быть риторическим.

### 8.12. Выгрузка

Заказы и клиенты в CSV для бухгалтерии. Простой маршрут, закрывает регулярную
ручную работу.

### 8.13. Отпуска и выходные

Чтобы наряд не назначался на день, когда человека нет.

**Принято владельцем 26 августа (ADR-115):** занятость личная — календарь
у каждого пользователя свой, выходные и блокировки он ставит себе сам.

## 9. Юридический и приватный контур

Новые данные — новые обязанности. Разбор нужен **до** внедрения, а не после.

**Клиентская база — персональные данные.** Сейчас ПДн живут в заявках и
отзывах, срок хранения ограничен смыслом. Постоянная база клиентов с адресами
и историей — другая история: нужен заявленный срок хранения, удаление по
требованию субъекта и ограничение доступа (монтажник видит адрес только
своего наряда — это уже заложено).

**Уведомление в Роскомнадзор** придётся уточнить: состав обрабатываемых данных
меняется (добавляются работники и договорные документы).

**Документы заказа** — договоры с ПДн. Они не должны отдаваться публично:
маршрут выдачи файла обязан проверять сессию и принадлежность документа
наряду, к которому у пользователя есть доступ. Существующий `/api/media/{name}`
для этого не годится — он открытый.

🔴 **«Штраф монтажнику».** Если монтажник — работник по трудовому договору,
штрафов как вида взыскания в ТК РФ нет, а удержания из зарплаты ограничены
статьёй 137. Если это самозанятый или подрядчик по договору ГПХ — уменьшение
вознаграждения законно, когда оно прописано в договоре.

Поле в CRM останется (владельцу нужно учитывать брак и срывы), но подпись в
интерфейсе — **«Удержание»** с полем «основание», а не «Штраф». Как это
оформлено в договорах — решение владельца, и его нужно принять до запуска
раздела.

## 11. Склад — требования

✅ **Сделано 27 августа.** Ответы владельца по трём открытым вопросам —
ADR-134, решения слоя данных — ADR-135, устройство экранов — ADR-136. Раздел

[API.md §14](API.md).

Принят ADR-111. Ниже — состав первой версии: чего хватает, чтобы ответить
на два вопроса владельца — «что ещё есть» и «что пора заказывать».

### 11.1. На складе две разные природы вещей

**Техника** — кондиционеры. Учёт штучный, у экземпляра есть серийный номер,
позиция ссылается на модель каталога.

**Расходники** — то, без чего монтаж не поедет. Номенклатура профильных
поставщиков даёт устойчивый набор групп:

| Группа                       | Типоразмеры                                          | Единица             |
| ---------------------------- | ---------------------------------------------------- | ------------------- |
| Медная труба, отожжённая     | 1/4″ (6,35), 3/8″ (9,52), 1/2″ (12,7), 5/8″ (15,88)  | метр, бухта 15/50 м |
| Теплоизоляция трубок         | по диаметру трубы, стенка 6/9/13 мм                  | метр                |
| Дренаж: шланг, гофра, сифоны | 16/20 мм                                             | метр, штука         |
| Межблочный кабель            | 3×1,5 · 4×1,5 · 5×1,5                                | метр, бухта         |
| Кронштейны наружного блока   | от 415×450, ставятся парой                           | пара                |
| Крепёж                       | анкеры, фасадные дюбели, дюбель-гвозди, болты, гайки | штука, упаковка     |
| Короб ПВХ и фасонные части   | 60×60, 80×60 + углы, повороты, стыки                 | метр, штука         |
| Хомуты, изолента, арм. скотч | —                                                    | штука, моток        |
| Фреон                        | R32, R410A — баллон 9,5–13,6 кг                      | килограмм           |
| Азот для опрессовки, масло   | —                                                    | баллон, литр        |
| Мелочь монтажа               | вальцовочные гайки, фитинги, помпы, герметик, пена   | штука               |

🔴 Список — **справочник в базе, а не константа в коде** (инвариант 8):
владелец заводит свои позиции сам. Кодом задаётся только набор единиц
измерения.

**Остаток дробный.** Фреон меряется килограммами, труба и кабель — метрами,
и «полбаллона» — нормальное рабочее состояние. Целочисленный остаток здесь
неверен с первого дня.

### 11.2. Зоны хранения

Остаток без ответа «где лежит» бесполезен: труба может быть, но в машине у
второго монтажника на другом конце города. Минимум зон:

- **склад** — гараж, основное место хранения;
- **машина монтажника** — зона, привязанная к человеку;
- **выдано под наряд** — уехало на объект, но ещё не списано.

Значит остаток позиции — не число, а число по зонам. Перемещение между
зонами — рядовая операция дня: утром загрузили машину, вечером вернули
остаток.

🔴 **В схеме зон две, а не три** (ADR-134). «Выдано под наряд» отдельным
местом не стало: до списания материал физически лежит в машине монтажника, и
третья зона потребовала бы, чтобы кто-то отмечал «выдал» — в реальный рабочий
день этого не делает никто. Расход наряда считается по движениям с этим
нарядом и виден в его карточке.

### 11.3. Интерфейс — таблица по зонам (запрос владельца)

Строки — позиции, колонки — зоны, в ячейке остаток, справа итог по позиции.
Строки ниже порога подсвечены — это и есть список «пора заказывать» без
отдельного экрана.

Про перетаскивание. Оно уместно ровно для одной операции — перенести
количество из зоны в зону, — и там действительно нагляднее формы. Но
перетаскивание пальцем по таблице с горизонтальной прокруткой работает
плохо, а с клавиатуры не работает вовсе, тогда как монтажник в машине
открывает панель именно с телефона. Поэтому:

**DnD — ускоритель для мыши, а не единственный путь.** Та же операция
доступна кнопкой «Переместить» с обычной формой, и раздел полностью
работоспособен без единого перетаскивания.

### 11.4. Порог «пора заказывать»

У позиции — минимальный остаток. Опустился ниже — позиция попадает в список
к заказу и в уведомление владельцу по существующей очереди. Порог задаётся
на позицию, а не общим числом: пять кронштейнов и пять метров трассы — это
разные степени тревоги.

### 11.5. Остаток — сумма движений, а не редактируемое поле

Приход, списание в наряд, перемещение между зонами, возврат, инвентаризация.
Без журнала движений вопрос «куда делись тридцать метров трассы» остаётся
без ответа, а склад превращается в число, которое все правят руками.

Правка остатка руками существует — но как **движение «инвентаризация» с
обязательной причиной**, а не как тихое переписывание значения.

### 11.6. Связка с нарядом

Чеклист выезда знает, что нужно; склад отвечает, есть ли. Закрытие наряда
списывает израсходованное по факту.

**Уход в минус не запрещаем, а помечаем.** Запрет означает, что монтажник,
у которого труба кончилась раньше, чем в системе, впишет неправду, лишь бы
закрыть наряд. Минус — сигнал «склад разошёлся с реальностью, нужна
инвентаризация», и это честнее.

### 11.7. Чего в первой версии не будет

Партии и сроки, себестоимость по FIFO, штрихкоды и сканер, резервирование
под будущий наряд. Себестоимость связана с §8.2 и решается вместе с ней, а
не отдельной половинкой.
