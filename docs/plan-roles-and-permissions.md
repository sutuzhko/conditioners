# Plan: Четыре роли и настраиваемые права

**PRD:** [docs/prd-roles-and-permissions.md](prd-roles-and-permissions.md)
**Решение:** [ADR-341](DECISIONS.md)
**Дата:** 2026-09-08

## Фазы реализации

### Фаза 1: Менеджер входит и видит свои разделы

**Цель:** Сквозной минимум — новая роль существует от схемы до экрана.
**Затрагивает:** database / backend / frontend
**Задачи:**

- [ ] Миграция: `AdminRole` получает `ADMIN` и `MANAGER`; существующие записи
      остаются в своих ролях
- [ ] Сессия несёт роль; в `server/guards.ts` появляется проверка по перечню
      ролей вместо пары «владелец / любой вошедший»
- [ ] Состав разделов навигации зависит от роли
- [ ] Раздел «Заявки» закрывается по роли: владелец, администратор, менеджер —
      да, монтажник — 403
- [ ] Тесты: guard на четыре роли, тест навигации, сквозной вход менеджера

**Когда готова:** заведённый менеджер входит в панель, видит «Заявки» и не
видит «Каталог»; монтажник на `/admin/leads` получает 403, а не разворот.

### Фаза 2: Матрица доступа закрывает все страницы и ручки

**Цель:** Ни одного маршрута без правила доступа.
**Затрагивает:** backend
**Задачи:**

- [ ] Матрица четырёх ролей записывается в [CRM §6](CRM.md) и [API.md](API.md)
- [ ] Проверка роли ставится каждой странице панели
- [ ] Проверка роли ставится каждой ручке `/api/admin/*`
- [ ] Контрактный тест: перечень «маршрут × роль» сверяется с деревом
      маршрутов и падает на маршруте без правила
- [ ] Тесты доступа: разрешённой роли 200, остальным 403, на каждой ручке

**Когда готова:** контрактный тест перечисляет все маршруты панели, у каждого
есть правило, и новый маршрут без правила красит проверку.

### Фаза 3: Менеджер не видит расходов на людей

**Цель:** Разграничение денег выполняется на сервере, а не скрытием колонок.
**Затрагивает:** backend / frontend
**Задачи:**

- [ ] Вознаграждение исполнителя и удержания вырезаются из ответов API для
      менеджера — в наряде, списках и сводке
- [ ] Экраны наряда и списков перестают рисовать пустые места на месте
      вырезанного
- [ ] Тест по телу ответа: в ответах менеджеру нет полей выплат и удержаний
- [ ] Сквозной сценарий: менеджер ведёт заявку до назначенного наряда и ставит
      сумму заказа и способ оплаты

**Когда готова:** тест по телу ответа зелёный, менеджер заводит наряд целиком.

### Фаза 4: Разрешения администратора на сервере

**Цель:** Переключатели владельца действуют, даже когда экрана для них ещё нет.
**Затрагивает:** database / backend
**Задачи:**

- [ ] Миграция: набор разрешений у пользователя — тринадцать разделов и пять
      опасных действий
- [ ] Разрешения читаются из сессии на каждый запрос: снятое действует сразу
- [ ] Проверка разрешения у страниц и ручек поверх проверки роли
- [ ] Владелец в системе один: попытка выдать вторую роль `OWNER` отклоняется
- [ ] Тесты: снятое разрешение закрывает раздел без повторного входа;
      администратор не может менять свои и чужие права

**Когда готова:** правка разрешений через API закрывает и открывает разделы
администратору без выхода из панели.

### Фаза 5: Владелец раздаёт права глазами

**Цель:** Настройка прав становится работой владельца, а не запросом в API.
**Затрагивает:** frontend
**Задачи:**

- [ ] Экран прав в карточке администратора: разделы и опасные действия
- [ ] Экран виден только владельцу; администратору его нет
- [ ] Состояния: сохранение, отказ, несохранённые правки при уходе
- [ ] Истории Storybook на все состояния экрана
- [ ] Просмотр через Playwright MCP по скиллу `ui-ux-pro-max` на 1440, 768, 390
      в обеих темах

**Когда готова:** владелец включает и выключает разделы администратору из
карточки, отчёт `ui-ux-pro-max` приложен.

### Фаза 6: Раздел «Сотрудники»

**Цель:** Один список всех людей компании вместо списка монтажников.
**Затрагивает:** frontend / backend
**Задачи:**

- [ ] Заголовок, подписи и пустые состояния раздела говорят о сотрудниках;
      адрес `/admin/team` не меняется
- [ ] Фильтр по роли в списке
- [ ] Роль правится в карточке сотрудника
- [ ] Заведение администратора и менеджера тем же путём, что монтажника
- [ ] Тесты: фильтр, смена роли, заведение; измерения историй раздела
      обновляются диффом

**Когда готова:** в списке видны все роли, фильтр по роли работает, менеджер
заводится из панели.

### Фаза 7: Приёмка

**Цель:** Роли приняты целиком, а не по частям.
**Затрагивает:** backend / frontend
**Задачи:**

- [ ] Сквозные сценарии четырёх ролей: вход, доступный раздел, закрытый раздел
- [ ] Сверка матрицы CRM §6 и API.md с кодом
- [ ] Полный гейт `pnpm check`, вывод приложен к задаче
- [ ] Расхождения с макетом записаны строками в [PIXEL_SPEC](PIXEL_SPEC.md)

**Когда готова:** гейт зелёный, матрица совпадает с кодом, сценарии проходят.
