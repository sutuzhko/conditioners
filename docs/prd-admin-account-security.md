# PRD: Аккаунт панели защищён и восстановим

**Дата**: 2026-09-04
**Статус**: Draft

## Цель

Аккаунт владельца — ключ ко всей кассе, персональным данным клиентов и
содержимому сайта. Сейчас его защищает один пароль, и **потеря пароля означает
потерю доступа навсегда**: в приложении нет ни одного способа восстановления.
Задача — сделать так, чтобы украсть аккаунт было нельзя одним подобранным
паролем, а вернуть его — можно без разработчика.

## Что уже есть — чтобы не переделывать

Проверено по коду 4 сентября, а не предположено:

- Пароль хранится через **Argon2id** (`server/auth.ts`), а не хешем-однодневкой
- Сессия — httpOnly + `SameSite=Lax` cookie, в базе лежит только **хеш токена**
  (`Session.tokenHash`), сам токен не хранится
- Смена пароля **выпускает новый идентификатор сессии** — защита от фиксации
- Защита от перебора на входе есть: `rate-limit` по ключу `login:<ip>`
- Флаг `Secure` выводится из `SITE_URL`: конфигурация с http в production не
  поднимается (ADR-102)

Это хорошая база. Не хватает второго фактора, возврата доступа и нескольких
вещей, которые человек ожидает от формы входа.

## Пользовательские сценарии

- Владелец включает второй фактор → при следующем входе после пароля просит
  код из приложения-аутентификатора
- Владелец теряет телефон → входит по одному из резервных кодов, выданных при
  включении; использованный код больше не работает
- Владелец забыл пароль → запрашивает восстановление, получает письмо со
  ссылкой ограниченного срока, задаёт новый пароль; все прежние сессии гаснут
- Владелец набирает пароль на телефоне в перчатке → нажимает глаз и видит, что
  набрал, вместо третьей попытки вслепую
- Владелец подозревает, что вошли не он → видит список своих сессий с
  устройством, адресом и временем и завершает все, кроме текущей
- Владелец меняет пароль → вводит его дважды и видит, устраивает ли новый
  пароль требованиям **до** отправки формы
- Монтажник забыл пароль → просит владельца, тот выдаёт новый из карточки
  монтажника: у монтажника нет почты в системе, и самостоятельное восстановление ему не нужно
- Злоумышленник перебирает пароли → упирается в задержку по учётной записи, а
  не только по адресу, с которого стучится

## В скоупе

**Второй фактор**

- TOTP по стандарту (RFC 6238): совместим с любым приложением-аутентификатором,
  без SMS и без внешнего сервиса
- Включение с показом QR и проверкой первого кода: нельзя включить фактор и
  остаться без доступа
- Резервные коды — десять штук, одноразовые, показываются один раз
- Выключение второго фактора требует пароля и текущего кода

**Возврат доступа**

- Восстановление по почте владельца: одноразовая ссылка ограниченного срока,
  токен хранится хешем, использование гасит все сессии
- Восстановление доступно **только владельцу**: монтажнику пароль назначает
  владелец из карточки, почты у монтажника в системе нет
- Учёт попыток восстановления: перебор адресов не должен подсказывать, заведён
  ли такой аккаунт

**Форма входа и смены пароля**

- Глаз для показа пароля с правильной доступностью: `aria-pressed`, имя кнопки
  меняется, поле не теряет фокус
- Подтверждение нового пароля вторым полем
- Понятные требования к паролю **до** отправки, а не после отказа сервера
- Защита от перебора получает второй ключ — по учётной записи, а не только по
  адресу

**Свои сессии**

- Список активных сессий: когда вошли, с какого устройства и адреса
- «Выйти на всех устройствах» — гасит все сессии, кроме текущей
- Дата и адрес последнего входа на видном месте профиля

**Журнал событий безопасности**

- Вход, неудачный вход, смена пароля, включение и выключение второго фактора,
  восстановление, завершение сессий — с временем и адресом
- Владелец видит журнал в профиле

## Не в скоупе

- **SMS как второй фактор** — платный внешний сервис, перехватываемый канал
- **Вход через сторонние аккаунты** (Google, Яндекс ID) — уводит персональные
  данные и ключ доступа за пределы контура 152-ФЗ
- **Аппаратные ключи (WebAuthn/passkeys)** — сильнее TOTP, но требуют устройства
  у каждого; возвращаемся к ним после запуска
- **Роли тоньше двух** — владелец и монтажник остаются как есть (ADR-092)
- **Второй фактор для монтажника** — обязательным не делается: он входит с
  телефона на объекте, в перчатках, и лишний шаг сорвёт наряд. Доступен по
  желанию
- **Смена почты владельца** без подтверждения на старый адрес

## Технические ограничения

- **152-ФЗ**: почта владельца и журнал событий — персональные данные, хранятся в
  РФ, как и всё остальное (ADR-016)
- **Инвариант 3**: секреты только на сервере. Ключ TOTP не попадает в клиентский
  бандл и в `NEXT_PUBLIC_*`
- **Письма уходят через тот же транспорт**, что уведомления (SMTP в РФ), и по
  инварианту 2 недоступность почты не должна ронять вход
- Секрет TOTP и резервные коды хранятся **зашифрованными или хешами**, не
  открытым текстом: база — не сейф
- Восстановление и второй фактор обязаны работать **без JavaScript-зависимостей
  на критическом пути входа**, иначе отказ бандла запирает владельца снаружи
- Библиотеки — только с явного согласия владельца (правило проекта)

## Критерии готовности

- [ ] Включённый второй фактор не даёт войти по одному паролю — проверено
      сквозным сценарием, а не вручную
- [ ] Резервный код срабатывает один раз; повторное использование отклоняется
- [ ] Ссылка восстановления одноразова, истекает по сроку и гасит все сессии
- [ ] Ответ на запрос восстановления одинаков для существующего и
      несуществующего адреса — перебором аккаунты не перечисляются
- [ ] Перебор паролей упирается в задержку и по адресу, и по учётной записи
- [ ] Глаз показа пароля работает с клавиатуры, называет своё состояние озвучке
      и не теряет фокус поля
- [ ] «Выйти на всех устройствах» гасит все сессии, кроме текущей — проверено
      двумя браузерами в сквозном сценарии
- [ ] Ни ключ TOTP, ни резервные коды, ни токен восстановления не лежат в базе
      открытым текстом
- [ ] Журнал событий пишет вход, отказ, смену пароля и действия со вторым
      фактором
- [ ] Секретов нет в клиентском бандле — проверено поиском по сборке
- [ ] `pnpm check` из корня и `pnpm e2e:stand` зелёные
