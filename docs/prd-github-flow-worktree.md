# PRD: Рабочий процесс по GitHub Flow — worktree на сессию со своим стендом

**Дата**: 2026-08-29
**Статус**: Draft

## Цель

Сделать исполнимым инвариант 19 ([ADR-164](DECISIONS.md)): работа идёт веткой
и приезжает Pull Request'ом. Сегодня это невозможно — две сессии живут в одном
рабочем каталоге, где `checkout` глобален: одна заводит ветку, вторая
коммитит в неё свою чужую задачу. Каждая сессия получает свой `git worktree`
со своим дев-стендом, а `main` — защиту и понятный путь в прод.

## Пользовательские сценарии

- Агент начинает задачу → одной командой получает свой каталог, свою ветку от
  свежего `main` и поднятый стенд, ничего не отняв у соседней сессии
- Два агента работают одновременно → у каждого свой сайт, своя база и своя
  ветка; коммит одного не задевает дерево другого
- Агент гоняет `pnpm check` → проверки идут по коду его worktree, а не по
  коду соседа
- Агент коммитит в своём worktree → замок хука виден обеим сессиям, и два
  коммита не накладываются
- Агент закончил задачу → пушит ветку, открывает PR, дожидается зелёного CI и
  ревью, merge закрывает issue
- Владелец видит `main` → там только то, что прошло проверки; история не
  черновик
- Агент снёс стенд → каталог, контейнеры и тома уходят одной командой, не
  оставляя мусора

## В скоупе

Стенд на worktree:

- **Compose-состав параметризуется**: имя проекта и смещение портов (сейчас
  `name: conditioner-dev` и порты 80/443, 3000, 6006, 5432 зашиты) — два
  стенда одновременно не поднимаются
- **Свой стенд целиком**: web, worker, storybook, caddy, db. Тома compose
  именованные, значит с новым именем проекта они изолируются сами
- **Наполнение стенда — только демо-данными** (`migrate deploy` → `seed` →
  `seed:demo`). Копировать дев-базу с настоящими заявками владельца на каждый
  стенд нельзя: это размножение персональных данных (152-ФЗ, инвариант 12)
- **Команда заведения и сноса**: `worktree + ветка + стенд` одной командой и
  обратно — вместе с каталогом, контейнерами и томами
- **Потолок**: сколько стендов машина держит одновременно, измеряется и
  записывается (ADR-045 — «не больше четырёх агентов, машина не вытягивает»)

Git и хук:

- **Замок хука общий на репозиторий**: сейчас он в
  `$(git rev-parse --git-dir)`, а в worktree это `.git/worktrees/<имя>` —
  замок ADR-163 перестанет разделяться между сессиями
- **Тесты хука идут в стенд своего worktree**, а не в чужой контейнер

Ветки, PR, main:

- **Ветка на задачу** от свежего `main`, имя описательное (`github-flow`)
- **Шаблон Pull Request**: что сделано, какой issue закрывает, чем проверено
- **Обязательный гейт до merge**: зелёный CI и прогон `/code-review`; merge —
  за владельцем
- **Защита `main`**: прямой push запрещён, обязательная проверка — CI.
  Включается **после** починки красного пайплайна (#94)
- **Порядок выкладки**: `main` собирается и выкладывается ровно так же, как
  сейчас (`infra/deploy.sh`), пока не появится VPS

Документация:

- [DEPLOY.md](DEPLOY.md) §2 и [CLAUDE.md](CLAUDE.md) описывают запуск стенда —
  оба обновляются вместе с командой заведения

## Не в скоупе

- **Авто-деплой при merge**, которого требует скилл `github-flow`: VPS ещё не
  куплен. Готовится заготовкой workflow, включается отдельным решением
- **Починка красного CI** — это issue #94, отдельная задача первой фазы
  инфраструктуры; здесь она предпосылка, а не работа
- **Ревью вторым человеком** — его нет; роль гейта играют CI и `/code-review`
- **Общий Postgres на все стенды** с отдельной базой на worktree — экономия
  памяти ценой расхождения с прод-составом
- **Перенос уже накопленных 18 коммитов в ветки** — они в `main`, история не
  переписывается (ADR-033)

## Технические ограничения

- **Дев только в Docker** (ADR-017): `pnpm dev` на хосте не поддерживается, и
  стенд worktree обязан подниматься тем же способом, что основной
- **Проверка типов только в контейнере** (ADR-147) — значит, у worktree
  обязан быть свой контейнер, иначе `tsc` проверит чужой код
- **Порты заняты основным стендом**: 80, 443, 3000, 6006, 5432 — смещение
  обязано быть предсказуемым и записанным, иначе два агента займут один порт
- **Тома `node_modules` именованные** (бинарники macOS не должны попадать в
  linux-контейнер) — у каждого стенда они свои, и первый запуск стоит
  установки зависимостей
- **Память**: каждый стенд — это web, worker, storybook, caddy и Postgres.
  ADR-045 уже ограничивает четырьмя агентами по этой же причине
- **Персональные данные владельца остаются в одной базе** — на стендах
  worktree только демо-данные
- **`gh` авторизован** под учётной записью владельца: PR и merge создаются от
  его имени, и это должно быть видно в шаблоне PR
- **Защиту `main` включать только с зелёным CI** — иначе она остановит работу
  целиком

## Критерии готовности

- [ ] Два стенда подняты одновременно, оба отвечают: основной на 3000 и
      стенд worktree на своём порту; ни один порт не занят дважды
- [ ] `pnpm check` в стенде worktree идёт по коду этого worktree — проверено
      заведомой ошибкой, внесённой только в него
- [ ] Стенд worktree наполнен демо-данными; настоящих заявок владельца в нём
      нет — проверено запросом к базе
- [ ] Заведение стенда — одна команда; снос — одна команда, после неё не
      остаётся ни контейнеров, ни томов, ни каталога (`docker volume ls` и
      `git worktree list` чистые)
- [ ] Замок хука виден из обоих worktree: одновременный коммит в двух из них
      приводит к ожиданию, а не к наложению
- [ ] Коммит в worktree гоняет тесты в своём стенде — проверено остановкой
      чужого контейнера
- [ ] Измерено и записано, сколько стендов машина держит одновременно
- [ ] У репозитория есть шаблон PR; PR открывается и закрывает issue по
      `Closes #N`
- [ ] Задача целиком проходит маршрут: issue → ветка → коммиты → PR →
      зелёный CI → merge → issue закрыт автоматически
- [ ] `main` защищён: прямой push отклоняется, обязательная проверка — CI
      (включается после #94)
- [ ] [DEPLOY.md](DEPLOY.md) и [CLAUDE.md](CLAUDE.md) описывают новый порядок
      тем же коммитом, что и код
