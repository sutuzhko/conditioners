# PRD: Панель собирается из готового кита по макету

**Дата**: 2026-09-04
**Статус**: Draft

**Макет**: [холст «Панель ТулаКлимат»](https://claude.ai/code/artifact/6283f576-0c4a-4581-99e2-a0da228858e2) · исходники `design/admin/`
**Основание**: [ADR-307](DECISIONS.md) · предыдущий заход — [prd-admin-panel-redesign.md](prd-admin-panel-redesign.md)

## Цель

Владелец открывает любой из тринадцати разделов панели на любой из трёх ширин и
видит тот экран, который ему показали на макете, — а не его предшественника,
собранного из старой вёрстки. Сегодня это не так: кит под новый облик построен
целиком, но экраны из него не собраны.

## Что установлено — это не оценка, а замер

Вехи «Панель · Фаза 4–5» (кит и токены) выполнены честно. Вехи «Фаза 8–10»
(экраны) закрыты формально. Проверка использования компонентов вне самого кита:

| Компонент                                                                                | История | Позван на экранах                          |
| ---------------------------------------------------------------------------------------- | ------- | ------------------------------------------ |
| `RowMenu`, `Tooltip`, `Alert`, `Autocomplete`, `NumberInput`, `DateField`, `AvatarGroup` | есть    | **0**                                      |
| `ChoiceGroup`                                                                            | **нет** | **0**                                      |
| `DataBlock` — загрузка, пусто, ошибка                                                    | есть    | **1** страница из 40                       |
| `Chart`                                                                                  | есть    | **1** — и не на том сегменте, что в макете |
| `StatTile`                                                                               | есть    | **2** раздела из 13                        |

Одну и ту же вкладку рисуют **семь разных компонентов**: `PanelTabLinks`,
`OrderTabs`, `ReviewTabs`, `PanelTabs`, `ArticleTabs`, `OrderWorkTabs` и сегменты
внутри `AdminSummary`. Словарь вкладок при этом один и с макетом сверен.

Отсюда следствие, важнее любого отдельного дефекта: **работа впереди — сборка из
готовых деталей, а не проектирование.** Новых примитивов заводить почти не
придётся.

## Пользовательские сценарии

- Владелец открывает раздел на 1440 → видит состав и порядок блоков макета:
  плитки показателей, панель фильтров, таблицу с колонкой действий, пагинацию
- Владелец жмёт «…» в строке любой таблицы → получает действия над этой строкой
  на месте, не открывая карточку. Необратимое спрашивает подтверждение
- Владелец открывает «Обзор» → видит приветствие, оба графика и ближайшие дела
  таблицей с фильтрами — тем сегментом, на котором их рисует макет
- Владелец переводит окно на 768 → колонка разделов ведёт себя по правилу
  диапазона, таблицы прокручиваются внутри своего контейнера, страница вбок не едет
- Владелец открывает панель на 390 → таблицы становятся карточками, главное
  действие достижимо большим пальцем, нижняя полоса не накрывает содержимое
- Владелец ждёт данные раздела → видит скелетон будущей раскладки той же высоты;
  данных нет → объяснение и следующий шаг; запрос упал → «Повторить» и живые соседи
- Владелец ищет заказ по клиенту или адресу из шапки любого раздела → находит,
  не помня, в каком разделе искать
- Владелец видит в колонке разделов, сколько заказов, заявок и отзывов ждут его
- Модератор шлёт коллеге ссылку на вкладку → та открывается сразу нужной

## В скоупе

**Оболочка**

- Приведение `AdminShell` и `AdminNav` к макету: место заголовка и главного
  действия, карточка вошедшего, счётчики у пунктов, строка значков у заголовка
- Судьба верхней полосы: макет её не имеет, а она несёт «Открыть сайт» и тему
- Подсказка значка на иконочном рельсе компонентом кита, а не `title=`

**Экраны — тринадцать разделов на 1440, 768 и 390**

Обзор, Календарь работ, Заказы, Карточка заказа, Заявки, Клиенты, Монтажники,
Склад, Каталог, База знаний, Отзывы, Настройки, Профиль — и тридцать одна
вкладка внутри них.

**Сквозные правила**

- Меню строки «…» во всех таблицах панели
- Три состояния данных (`DataBlock`) у каждого асинхронного блока
- Одна реализация вкладки вместо семи
- Глобальный поиск по клиенту, адресу и заметке
- Счётчики ожидающего в навигации

**Полнота действий над данными**

У каждой таблицы и списка: завести, открыть, изменить, убрать — с подтверждением
у необратимого. Пробел закрывается кодом, даже если в макете его тоже нет
(ADR-307).

**Дефекты самого макета**

Чинятся на ходу, в той же задаче; отступление — строкой в
[PIXEL_SPEC §«Панель»](PIXEL_SPEC.md) с причиной и номером issue.

## Не в скоупе

- **Календарь работ переделке по HeroUI не подлежит.** Его эталон — Apple
  Calendar (CRM §3.5.1, ADR-128), и владелец считает его готовым. В скоупе
  остаются только открытые дефекты вехи «Интерфейс · Фаза 11» (#47–#50)
- **Публичная часть.** Кит общий, и правка компонента её задевает: требование —
  не изменить её вид, а не улучшить
- **Переезд бэкенда на NestJS** (ADR-192) — он начинается после этой работы
- **Новые сущности и поля БД.** Если экран макета требует данных, которых в
  схеме нет, это отдельный issue со своим ADR
- **Перерисовка холста.** Дефект макета правится в коде и записывается, а не
  возвращается в `design/admin/` (ADR-307)
- **Разделы без кадра в макете** — `/admin/company`, `/admin/prices`,
  `/admin/notifications`: они приводятся к общим правилам оболочки, состояний и
  действий, но собственного кадра ждут по issue #307

## Технические ограничения

- **Бюджет JS — 100 КБ своего слоя** (ADR-184), сейчас 77,2. Семь новых
  компонентов на экранах его подвинут; замер `js-budget.mjs --strict` до и после
- **Кит общий с публичной частью**: 179 потребителей, из них 66 публичных
- **Инвариант 1** — панель отдаётся сервером; `'use client'` ставится на лист
- **Инварианты 8 и 12** — ни одного факта о компании в коде, персональные данные
  в РФ
- **Тап-зоны**: 44×44 до 900px, 24×24 выше (ADR-183); плотность панели 32px
  допустима там, где указатель, а не палец
- **Контраст AA в обеих темах**, проверяется `admin-contrast.mjs` на живом DOM
- **Кадры снимаются только в Linux-образе** — на macOS шрифты другие (ADR-230)
- **Стенд e2e один на машину**, порт 3101: прогоны сериализуются

## Критерии готовности

- [ ] Ни один компонент кита не имеет нуля потребителей среди экранов панели,
      либо его отсутствие названо строкой в PIXEL_SPEC с причиной
- [ ] `DataBlock` — на каждой странице панели, тянущей данные с сервера
- [ ] Вкладку рисует один компонент; остальные шесть удалены
- [ ] Меню строки «…» есть в каждой таблице панели; действия совпадают с теми,
      что доступны в карточке
- [ ] Тринадцать разделов сверены с макетом на 1440, 768 и 390 в обеих темах;
      каждое расхождение либо устранено, либо стоит строкой в PIXEL_SPEC
- [ ] `admin-contrast.mjs` — ноль нарушений; `admin-density.mjs` — ноль
      расхождений плотности; вывод приложен к issue приёмки
- [ ] `js-budget.mjs --strict` зелёный, число до и после в issue
- [ ] Инварианты раскладки зелёные на разделах `Админка/`; допущения — с причиной
- [ ] `pnpm check` из корня зелёный; сквозные `pnpm e2e:stand` зелёные
- [ ] Публичная часть не изменилась: снимки её историй без расхождений
- [ ] Каждый раздел проверен скиллом `ui-ux-pro-max` и просмотром через браузер —
      не тестами
