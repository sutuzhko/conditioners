> Решения: [DECISIONS.md](DECISIONS.md) ADR-020 · Стандарты кода: [CLAUDE.md](CLAUDE.md) · План работ: [ROADMAP.md](ROADMAP.md)

## Правила для агента

Агенты работают **в одном рабочем каталоге одновременно**. Это даёт им видеть код друг друга (страницам нужен UI Kit), но требует дисциплины.

🔴 **Правь только файлы из своего списка владения.** Нужен чужой файл — не правь, сообщи оркестратору в итоговом отчёте.

🔴 **Коммить только свои пути:** `git add <свои пути>`, никогда `git add -A` и никогда `git add .` — в рабочем каталоге лежат незакоммиченные файлы других агентов.

🔴 **Формат коммита** — Conventional Commits со своим scope, без упоминаний ИИ и соавторства (см. раздел «Коммиты» в [CLAUDE.md](CLAUDE.md)).

🔴 **Вопрос задать некому.** Фоновый агент не может обратиться к пользователю. Всё неочевидное решается по документации; если документация молчит — выбери разумный вариант, реализуй и **явно перечисли принятые допущения в отчёте**, чтобы оркестратор зафиксировал их в журнале решений.

**Перед началом:** прочитать `docs/CLAUDE.md` (инварианты), затем документ своей области. **Перед сдачей:** линт, типы и свои тесты зелёные; у каждого компонента и блока есть story; чек-лист из `CLAUDE.md` пройден.

**Конфигурация Storybook** (`apps/web/.storybook/**`) — общая, правит только оркестратор. Stories лежат рядом со своим компонентом и принадлежат его владельцу.

**Что делать нельзя никому, кроме владельца файла:** трогать `package.json`, `tsconfig.json`, `Dockerfile`, `docker-compose.*.yml`, `prisma/schema.prisma`, конфиги линтеров. Нужна новая зависимость — запросить у оркестратора в отчёте, не ставить самому.

## Волна 0 — фундамент · последовательно

Выполняется оркестратором в основном чате. Параллелить нельзя: отсюда импортирует всё остальное.

Каркас Next, Docker, линтеры, схема Prisma с миграцией, сиды, токены, шрифты, конфиги тестов.

**Критерий готовности:** `docker compose -f docker-compose.dev.yml up` поднимает сайт через Caddy на локальном домене, база засеяна, `pnpm lint` и `pnpm typecheck` зелёные.

## 🔴 Вентиль перед блоковой волной

Ни одна задача на блок не выдаётся, пока не влито **всё** из этого списка. Правило: агент блока не верстает переиспользуемые элементы — если блоку нужен компонент, которого нет, это блокер, а не повод его написать.

Проверено аудитом прототипа. К инвентарю из [DESIGN_BRIEF §5](DESIGN_BRIEF.md) добавлены три компонента, которых там не было:

| Компонент                                          | Кому нужен                 | Почему без него нельзя                      |
| -------------------------------------------------- | -------------------------- | ------------------------------------------- |
| **Drawer / бургер-меню**                           | Шапка                      | Мобильной навигации в прототипе нет вообще  |
| **Table со скроллом и залипающей первой колонкой** | Каталог и сравнение, Цены  | Два блока решали бы одну задачу по-разному  |
| **FileInput с превью и валидацией**                | Форма заявки, Форма отзыва | Иначе две реализации сжатия и проверки типа |

Плюс две единицы, которые выглядят как блоки лендинга, но ими не являются:

- **`features/lead-form`** — форма заявки стоит на каждой странице кластера, не только на главной
- **`features/review-form`** — нужна и на главной, и на `/otzyvy`

И хук **`useCountUp`** (анимация цифр в hero и «Почему мы») — не компонент, живёт в `shared/lib`, владелец — агент A волны 1.

## Волна 3 — блоки лендинга · worktree, по одному блоку на агента

🔴 **Режим изоляции здесь другой.** Каждый агент работает в собственном git worktree и присылает результат оркестратору. Оркестратор смотрит блок в Storybook на 320, 375, 768 и 1200 в обеих темах, прогоняет тесты и только после этого вливает в `main`.

Это возможно именно здесь: UI Kit, домен и слой данных уже в `main`, блоки друг от друга не зависят, пересечений по файлам нет.

Каждый блок — свой каталог `apps/web/src/widgets/<block>/`, свои stories, свои тесты, своя адаптивная вёрстка от 320px.

### 🔴 Блок не ходит в базу

Виджет — **представление**: принимает готовые данные пропсами и рисует их. Запрос в репозиторий делает страница, она же передаёт результат вниз. Причин две:

- правило зависимостей: `widgets` не может импортировать `@/server/*`, это проверяет линтер;
- блок обязан рисоваться в Storybook, где никакой базы нет. Блок, которому нужен живой Postgres, невозможно ни посмотреть, ни принять.

Поэтому у каждого блока в stories лежат фикстуры — они же документируют, какие данные блок ждёт.

### Сборку страницы делает оркестратор

Агент блока не трогает `app/(site)/page.tsx` — иначе девять агентов правили бы один файл. Он сдаёт виджет с его контрактом пропсов; оркестратор при вливании подключает блок к странице и связывает с репозиторием.

Отсюда порядок: **контент появляется на сайте постепенно**, по мере приёмки блоков, а не одномоментно в конце волны.

| #   | Задача             | Секции прототипа                                                        |
| --- | ------------------ | ----------------------------------------------------------------------- |
| 1   | Шапка и футер      | Шапка с логотипом, бургер-меню, переключатель темы; футер с реквизитами |
| 2   | Первый экран       | Hero, подбор по площади, живой фон, счётчики                            |
| 3   | Доверие            | Полоса доверия, Услуги, Почему в Туле выбирают нас                      |
| 4   | Каталог            | Витрина моделей со скидками, таблица сравнения                          |
| 5   | Цены               | Таблица цен по классам, калькулятор монтажа                             |
| 6   | Монтаж             | Четыре шага, таймлайн дня монтажа, экономия инвертора                   |
| 7   | Честность          | Почему монтаж стоит 6 000, Как обманывают при установке                 |
| 8   | Сервис             | Диагностика по симптомам                                                |
| 9   | Справка и контакты | Отзывы, тизер Базы знаний, FAQ, контакты с картой                       |

Задача 9 самая объёмная — при постановке может быть разделена надвое.

Форма заявки и форма отзыва в список **не входят**: они сделаны в волне 1 как переиспользуемые фичи, блоки только встраивают их.

## Между волнами

Оркестратор прогоняет линт, типы, тесты и `/code-review`, сводит допущения агентов в [DECISIONS.md](DECISIONS.md) и только потом запускает следующую волну.

Волна не считается закрытой, пока сборка не зелёная. Чинить — тем же агентом, который писал код, а не следующей волной.
