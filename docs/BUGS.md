### 🔴 P2 · Девять админских фич дублируют разбор ошибок API и уже разошлись в поведении

`shared/lib/api.ts` с `apiErrorSchema` создан ровно для этого (ADR-030), но
им пользуются только четыре фичи. Свои `readError` на каскадах `as` держат
article-form, product-form, product-photos, product-sale, prices-form,
settings-form, crm-calendar, lead-manager, review-moderation (~680 строк
почти одинаковых клиентов). Расхождение уже наступило: 401 (истёкшую сессию)
обрабатывают только article-form, product-form и settings-form — остальные
покажут владельцу «Сервер не принял изменения» вместо «войдите заново».
Заодно это внешние данные мимо Zod и запрещённые `as`.

**Что сделать:** общий хелпер запроса в `shared/lib/api.ts` (fetch +
`apiErrorSchema.safeParse` + единая ветка 401); фичи оставляют только тексты.

### 🔴 P2 · Слой shared зависит от entities и widgets — SEO-модуль живёт выше объявленного

Правило «из shared только shared» нарушено систематически:
`shared/config/nav.ts` ← `@/widgets/header`; `shared/lib/address.ts` и весь
`shared/seo/*` (product, organization, business, reviews, service, schema) ←
`@/entities/*`; тесты shared тянут `@/widgets/faq` и `@/widgets/catalog`.
Зафиксированного исключения нет — DECISIONS знает только про
entities/settings ← entities/price.

**Что сделать:** либо поднять `shared/seo` в слой entities (это доменные
сборщики, а не утилиты), либо вынести типы-контракты в shared, либо
оформить исключение ADR-ом. Тесты shared не должны проверять виджеты —
перенести к виджетам.

### 🔴 P2 · Тестовая пирамида просела: треть маршрутов и все обязательные E2E

Интеграционных тестов нет у 22 из 33 route handlers — среди непокрытых
`auth/login` (защита от перебора), `media/[name]` (отдача файлов —
безопасность), обе загрузки (`articles/[id]/cover`, `models/[id]/photos`),
все админские `[id]`-маршруты. Из трёх обязательных сквозных сценариев
CLAUDE.md («отправка заявки», «отзыв → модерация», «вход → правка цены →
цена на сайте») не реализован ни один: `e2e/smoke.spec.ts` проверяет только
SSR, якоря, 404 и sitemap.

**Что сделать:** начать с auth/login, media и загрузок; три E2E-сценария —
отдельным заходом, для заявки — с проверкой записи в БД (инвариант 2).

### 🔴 P2 · Зависший воркер невидим: ни healthcheck, ни отражения очереди в health

У `worker` в `docker-compose.prod.yml` нет healthcheck, `/api/health`
проверяет только `SELECT 1`. Цикл однопоточный: один вечно висящий `await` в
`tick()` — контейнер «running», очередь стоит, уведомления копятся, внешний
аптайм-монитор зелёный. Обнаружение — «владельцу перестали приходить заявки».

**Что сделать:** heartbeat в `tick()` (запись в БД или файл) + healthcheck
на его возраст; и/или отдавать возраст последней обработки очереди в
`/api/health`.

### 🔴 P2 · Сборка на боевом VPS без лимитов памяти — OOM-killer выберет жертву сам

`docker-compose.prod.yml` не задаёт лимитов ни одному сервису, а деплой
собирает `next build` (1,5–2 ГБ) рядом с работающими postgres+web+worker на
VPS 4 ГБ. При нехватке памяти ядро может убить postgres прямо на шаге
миграций или на живых заявках.

**Что сделать:** `mem_limit` сервисам (порядок: db 1g, web 768m, worker
768m), swap 2 ГБ на VPS, деплой не в пик.

### 🔴 P2 · Перед миграциями не снимается дамп, откат после падения не описан

`infra/deploy.sh:35`: `prisma migrate deploy` при падении оставляет миграцию
failed — старый сайт работает, но повторный деплой заблокирован до ручного
`migrate resolve`, а свежего дампа «на минуту до» нет: ночной бэкап может
отставать на сутки заявок. Процедуры разбора в DEPLOY.md нет.

**Что сделать:** дамп перед шагом `[3/5]` в deploy.sh; абзац про
`migrate resolve --rolled-back` в DEPLOY.md.

### 🔴 P3 · Упрочнение безопасности — пачкой

Фон: базовая гигиена на хорошем уровне (Argon2id, ротация сессий, загрузки
через magic bytes + sharp с вырезанием EXIF, все 26 админ-маршрутов под
`withAdmin`, Next 15.5.23 без CVE-2025-29927, XSS-путей в статьях нет).
Остались точечные упрочнения:

- **CSP отсутствует** (`Caddyfile`, next.config): остальной набор заголовков
  хороший, но даже базовая политика (`frame-ancestors 'self'; object-src
'none'; base-uri 'self'; form-action 'self'` + hash двух инлайн-скриптов)
  заметно сузила бы поверхность.
- **Нет проверки Origin на мутирующих админ-маршрутах** — единственная
  защита от CSRF: `SameSite=Lax`. Остаётся окно «Lax + top-level POST 2
  минуты после входа» (Chrome). Проверка `Origin === SITE_URL` для не-GET в
  `withAdmin` закрывает.
- **Вебхук Telegram**: секрет сравнивается `===` вместо готового `safeEqual`
  (`api/telegram/webhook/route.ts:35`), а `JSON.parse(raw)` без try/catch —
  битый JSON даёт 500 вопреки комментарию «всегда 200 при верном секрете»,
  и Telegram начинает ретраить, стопоря очередь обновлений (кнопки
  модерации).
- **Строковые поля multipart не ограничены до буферизации**
  (`server/intake/body.ts`): предпроверка только по `Content-Length`,
  счётчик суммирует лишь файлы — chunked-запрос с гигантским текстовым полем
  буферизуется целиком.
- **Rate-limit входа «падает открытым»** при недоступности таблицы
  (`server/repo/rate-limit.ts:34`): для форм это осознанный компромисс, для
  `login:*` стоит выбрать fail-closed.
- **Свести две копии `clientIp`** (`server/auth.ts:138` и
  `server/http.ts:191`) и явно закрепить доверие заголовкам. Обход подделкой
  `X-Forwarded-For` изнутри прода закрыт (Caddy 2.5+ не доверяет чужому XFF,
  порт web наружу не публикуется), но код предпочитает XFF доверенному
  `X-Real-IP`, который Caddy ставит сам, — при любой смене прокси это
  всплывёт.

### 🔴 P3 · Истёкшая скидка видна на статике до часа

Главная — ISR c `revalidate = 3600`: скидка, закончившаяся в 23:59 МСК,
показывается перечёркнутой ценой до следующей регенерации. Формально это
показ недействующей скидки (инвариант 14), окно ограничено часом. Сам расчёт
`getActivePrice` корректен. Либо считать `revalidate` до ближайшей границы
периода скидки, либо зафиксировать часовой допуск ADR-ом. Смежное: клиентский
`HeroPicker` зовёт `getActivePrice` с `new Date()` вместо переданного
страницей `now` — на границе периода возможен hydration mismatch.

### 🔴 P3 · `NOTIFY_DRIVER=log` неотличим от рабочего состояния

### 🔴 P3 · Инфраструктурная гигиена — пачкой

- Слэш-редирект в Caddy теряет query string: `/knowledge/?utm_source=…` →
  301 на `/knowledge` без параметров — UTM-разметка и `?category=` пропадают.
- Нет лимита тела запроса и таймаутов на прокси: `request_body { max_size }`
  и `timeouts` в Caddyfile.
- Дев-Caddy не повторяет прод вопреки собственному комментарию (ни
  заголовков, ни редиректов) — вынести общий сниппет и `import` в оба файла.
  Шире: прод-рантайм (standalone, healthchecks, migrate, права тома) в деве
  не поднимается никогда — один локальный прогон полного прод-компоуза до
  покупки VPS обязателен (см. P1 про деплой).
- `docker image prune -f` последней строкой deploy.sh — иначе 8–10 ГБ слоёв
  копятся до ручной чистки; решить до запуска, куда уезжают бэкапы с диска
  VPS (дефолт `/var/backups` — тот же диск); cron бэкапа ничем не
  контролируется (мониторинг возраста последнего дампа).
- Посылка ADR-062 про secret-mount неточна: `ARG DATABASE_URL` из стадии
  `build` наследуется **финальными** образами worker/migrate и виден в
  `docker inspect` на сервере. Риск локальный (реестра нет), но основание в
  журнале стоит поправить или перейти на `--mount=type=secret`.

### ✅ P2 · Не было ни одного error.tsx — падение БД отдавало голый экран Next

Найдено аудитом 23 августа. Все страницы читают БД в серверных компонентах,

### ✅ P2 · Воркер и migrate работали под root

Найдено аудитом 23 августа. Стадии `worker` и `migrate` не ставили
пользователя — постоянный процесс с выходом в сеть и rw-томом загрузок жил
под root. **Исправлено:** обе стадии работают под `nextjs`, как runner. Кеш
corepack готовится заранее под root (`COREPACK_HOME=/pnpm/corepack`) и
открывается на чтение — иначе запуск pnpm под непривилегированным

### ✅ P2 · Запись заявки и постановка уведомления не были одной транзакцией

### ✅ P1 · Сайт целиком был закрыт от индексации, и данными это было не снять

### ✅ P1 · Ни один бэкап на сервере не состоялся бы: backup.sh не передавал `.env.prod`

### ✅ P1 · Первый деплой был невозможен: образ migrate требовал уже мигрированную базу

Найдено аудитом 23 августа. Сервис `migrate` собирался из target `worker`,
наследующего стадию `build` с её `next build` — пререндером страниц с
запросами в базу. На чистом VPS база пуста → сборка образа миграций падает →
накатить схему нечем: миграции требуют образ, образ требует миграций.
Смежно: `run --rm migrate` без `--build` применял миграции образом прошлого
релиза — свежие накатывались не до сборки, как требует ADR-062, а вместе с
запуском.

**Исправлено** (ADR-089): отдельная стадия `migrate` в Dockerfile —
`FROM deps`, где уже есть Prisma CLI и каталог схемы, без `next build`;
сервис собирается из неё, `deploy.sh` запускает с `--build`. Проверено
живьём: образ собрался без какой-либо базы, все пять миграций легли на
пустой одноразовый Postgres, таблицы на месте.

### ✅ P2 · Главная не укладывалась в бюджет JS

Боевая сборка давала **170 КБ** First Load JS против порога **150 КБ**. Из них
**102 КБ — рантайм** Next 15 и React 19: он одинаков у любой страницы и не
срезается ничем, кроме смены фреймворка. Собственный код главной — 68 КБ, и
заметную часть занимает Zod: схемы форм проверяются тем же кодом на клиенте и
на сервере, как того требует раздел «Формы и состояния».

**Что проверено и не сработало.** Формы заявки и отзыва в `next/dynamic` — First
Load не изменился ни на килобайт: компонент рендерится сервером и гидратируется
сразу, поэтому его чанк остаётся в первой загрузке. Выключить `ssr` нельзя —
форма пропадёт из HTML (инвариант 1).

**Решение владельца — пересмотреть порог** (ADR-088). Бюджет разделён на
платформенный пол (105 КБ, не наш код) и собственный слой (75 КБ, сейчас 66),
общий порог главной — 180 КБ. Отказ от Zod на клиенте отвергнут: гарантия
«клиент и сервер проверяют заявку одним кодом» дороже нескольких килобайт.

🔴 Порог уплыл незаметно — 154 → 157 → 170 тремя правками. Теперь его держит
`scripts/js-budget.mjs`: считает First Load по манифестам сборки и роняет CI при
превышении.

### ✅ P2 · Кольцо фокуса не совпадало с элементом

нулевая, текстовая ссылка скругление получает, компонент со своим радиусом
сохраняет свой. Там, где элемент лежит в контейнере с обрезкой, кольцо
рисуется внутрь и берёт радиус контейнера.

### ✅ P1 · Нет браузеров для Playwright в образе

Собственных сборок Playwright под musl нет, поэтому в дев-стадию образа
поставлен системный chromium из репозиториев Alpine вместе со шрифтами (без

`CHROMIUM_PATH`, конфиги Playwright подхватывают её и запускаются вне
контейнера обычным способом. Боевой образ не изменился.

### ✅ P2 · Снимки историй не снимались с дев-Storybook

**Причина оказалась не в скорости.** Первые три истории снимались за
75–107 мс, а четвёртая — «Хлебные крошки / Главная — следа нет» —
останавливала прогон навсегда. Эта история ничего не рендерит (на главной
крошек нет, и это правильное поведение), поэтому `#storybook-root` остаётся
нулевой высоты, то есть невидимым. Раннер ждал его видимости, а у `waitFor`
без явного таймаута предела нет: прогон молчал вместо того, чтобы упасть.

**Что сделано** (ADR-064): готовность истории берётся у самого Storybook —
`sb-show-main` на `body` без `sb-show-preparing-story`; снимается область
просмотра, а не контейнер истории; `actionTimeout` и `navigationTimeout`
заданы в конфигурации, чтобы ожидание без предела стало невозможным.

**Проверено прогоном, а не рассуждением:** полный охват — 128 историй на
четырёх ширинах в двух темах — прошёл за 33,6 минуты и создал 1024 эталона
(66 МБ). Повторный прогон одного набора против готовых эталонов: 128 снимков
совпали за 3,4 минуты. Совпадение при повторе и есть главное: снимки не
дрожат, значит расхождение будет означать настоящую регрессию, а не шум
антиалиасинга.

**Осталось решение владельца:** хранить ли 1024 PNG в репозитории. Пока
эталоны в `.gitignore`, и по этой же причине снимки не гоняются в CI —
сравнивать не с чем.

Арбитраж в пользу файла логотипов: 11px / 0.06em. Замок — боевой ассет

### ✅ P3 · Две проверки готовности настроек

`findSettingGaps` удалён: его не вызывал никто, кроме собственного теста.

### ✅ P1 · Микроразметка не подключена к страницам

### ✅ P1 · Ритм отступов между блоками рваный

Замерено в браузере (`getBoundingClientRect`), а не по CSS. Зазор между
содержимым соседних секций везде ровно один шаг — 88px; двойным (176px) он
выходил только вокруг секций с собственным фоном, где к внешнему шагу
добавляется внутренний отступ полосы. Это геометрия из ADR-037, и она верна,
но разница `--bg` и `--bg-soft` в тёмной теме меньше процента: полосы не было
видно, и её внутренний отступ читался как дыра в ритме.

Границы полос переведены с `--line-soft` на видимую `--line` и заданы с обеих
сторон (у тизера Базы знаний верхней не было вовсе). Край полосы теперь
читается, ритм — тоже.

### ✅ P2 · Сетка с остатком оставляет висящий ряд

Витрина каталога и тизер Базы знаний разложены рядом с переносом, а не
жёсткой сеткой: последний ряд центрируется, а `max-width` не даёт одинокой
карточке растянуться на всю полосу. Тизер вдобавок ограничен тремя статьями —
это краткая витрина, за остальным ведёт ссылка на листинг.

### ✅ P2 · Полоса доверия переносит содержимое на вторую строку

Ряд больше не переносится ни на какой ширине. От 1100px он стоит статично по
центру; ниже — едет лентой с автопрокруткой, которая останавливается при
наведении и фокусе. При `prefers-reduced-motion` движения нет, остаётся
обычная горизонтальная прокрутка. Список продублирован (копия скрыта от
скринридера) — иначе бегущая строка идёт с разрывом.

### ✅ P2 · Ряд симптомов переносится вместо прокрутки

Шесть кнопок остаются одной строкой на любой ширине: ряд прокручивается
внутри себя со `scroll-snap`. Поле внутри контейнера и его компенсация
снаружи оставляют место кольцу фокуса, которое прокрутка иначе срезает.

### ✅ P2 · Калькулятор монтажа горизонтальный, нужен в две колонки

Раскладка «корзины»: слева параметры, справа смета с итогом и кнопкой. Итог
прижат к низу колонки, поэтому появление строки в смете больше не двигает
кнопку. Ниже 900px смета встаёт под параметрами, на телефоне итог липнет к
низу экрана внутри сметы.
