# Ярлыки задач — четыре оси

> Словарь — [`scripts/labels.mjs`](../scripts/labels.mjs), он же источник
> правды. Здесь — что означает каждая ось и как выбирать между похожими
> ярлыками.
>
> Решение и отвергнутые варианты: [DECISIONS.md](DECISIONS.md), ADR-330.
> Требования: [prd-issue-labels-taxonomy.md](prd-issue-labels-taxonomy.md).

---

## Зачем оси

До 7 сентября ярлыки лежали на одной плоской оси и смешивали «что делаем» с
«чем это пахнет технически». Самый частый из них, `ui`, стоял на 29 задачах
из 88 — и на публичной части, и в панели, то есть ровно там, где различие
нужно, его не было. Восемь задач не имели ярлыков вообще.

Разметка по осям отвечает на разные вопросы разными ярлыками, и по строке
видно, чего задача касается, не открывая её.

| Ось         | Вопрос                    | Сколько на задаче | Цвет       |
| ----------- | ------------------------- | ----------------- | ---------- |
| `часть/`    | Где в продукте            | 🔴 ровно одна     | синий      |
| `раздел/`   | Что именно затронуто      | ноль или больше   | зелёный    |
| `тип/`      | Что делаем                | 🔴 ровно один     | оранжевый  |
| `качество/` | Какое сквозное требование | ноль или больше   | фиолетовый |

Цвет один на ось не для красоты: GitHub рисует ярлыки строкой и про оси не
знает, так что группирует их только цвет.

🔴 **GitHub не умеет «ровно одна `часть/`».** Он не помешает поставить две
или ни одной — это держится ревизором `checkAxes`, а не настройкой
репозитория.

## Ось `часть/` — где в продукте

| Ярлык             | Что покрывает                                                 |
| ----------------- | ------------------------------------------------------------- |
| `часть/сайт`      | публичные страницы: лендинг, каталог, статьи, отзывы, формы   |
| `часть/панель`    | админка: разделы, оболочка, формы и таблицы                   |
| `часть/api`       | маршруты, сервисы, доступ к данным, схема БД                  |
| `часть/инфра`     | CI, Docker, сборка, бюджеты, сквозные проверки, наблюдаемость |
| `часть/процесс`   | маршрут задачи: ветки, Pull Request, стенды, хуки, скиллы     |
| `часть/общее`     | код, служащий сразу сайту и панели: кит, токены, сущности     |
| `часть/документы` | ADR, журналы, PRD и планы, PIXEL_SPEC                         |

**`инфра` или `процесс`?** Инфраструктура — то, что исполняет машина:
пайплайн, образ, скрипт замера. Процесс — то, чему следует человек или
агент: как заводится ветка, что обязано быть в Pull Request, что делает
скилл. Починка `vr:measure:pull` — инфра. Правило «после merge догнать
main» — процесс.

**`общее` или `панель`?** По тому, где лежит правка, а не чем она
пользуется. Правка компонента в `shared/ui` — `общее`, даже если поводом был
один экран панели. Замена поля в девяти формах панели на готовый компонент
кита — `панель`: кит при этом не меняется.

**`api` или `панель`?** Экран — панель, маршрут — api. Задача, которая
делает и то и другое, берёт часть по тому, где основная работа; если
поровну — по тому, что сломано у владельца.

## Ось `раздел/` — что именно затронуто

Разделов у задачи может быть больше одного, и это норма, а не ошибка:
расход материалов в наряде — это и `наряды`, и `склад`.

| Ярлык                   | Путь в коде                                                                 |
| ----------------------- | --------------------------------------------------------------------------- |
| `раздел/каталог`        | `(site)/catalog`, `(panel)/catalog`, `api/admin/models`, `entities/product` |
| `раздел/характеристики` | `(panel)/catalog/specs`, `features/specs-dictionary`                        |
| `раздел/прайс`          | `(panel)/prices`, `api/prices`, `entities/price`, `widgets/pricing`         |
| `раздел/скидки`         | `features/product-sale`, `api/admin/models/*/sale`                          |
| `раздел/заявки`         | `api/leads`, `(panel)/leads`, `features/lead-form`, `lead-manager`          |
| `раздел/клиенты`        | `(panel)/clients`, `api/admin/clients`, `entities/client`                   |
| `раздел/наряды`         | `(panel)/orders`, `api/admin/orders`, `entities/order`                      |
| `раздел/календарь`      | `(panel)/crm`, `api/admin/crm`, `features/crm-calendar`                     |
| `раздел/склад`          | `(panel)/stock`, `api/admin/stock`, `entities/stock`                        |
| `раздел/монтажники`     | `(panel)/team`, `api/admin/staff`, `entities/staff`                         |
| `раздел/отзывы`         | `api/reviews`, `(panel)/reviews`, `features/review-*`                       |
| `раздел/знания`         | `(site)/knowledge`, `(panel)/knowledge`, `api/admin/articles`               |
| `раздел/настройки`      | `(panel)/settings`, `(panel)/company`, `api/settings`                       |
| `раздел/уведомления`    | `server/notifications`, `api/telegram`, `features/delivery-log`             |
| `раздел/доступ`         | `admin/login`, `api/auth`, `(panel)/profile`, `server/auth.ts`              |
| `раздел/лендинг`        | `widgets/hero`, `honesty`, `trust`, `faq`, `installation`, `service`        |
| `раздел/сравнение`      | `(site)/compare`                                                            |
| `раздел/кит`            | `shared/ui`, `shared/styles`, `.storybook`                                  |
| `раздел/медиа`          | `api/media`, `public/`                                                      |
| `раздел/погода`         | `api/weather`, `features/weather-chip`                                      |

**`сайт` или `лендинг`?** `часть/сайт` стоит на всей публичной части;
`раздел/лендинг` — только на коммерческих секциях главной. Правка карточки
каталога — `часть/сайт · раздел/каталог`, лендинга там нет.

🔴 **Пути — не украшение.** Из них генерируется карта для `actions/labeler`,
и тест сверяет каждый путь с настоящим деревом: путь, ведущий в
несуществующий каталог, перестал бы ставить ярлык молча.

## Ось `тип/` — что делаем

| Ярлык             | Когда                                                  |
| ----------------- | ------------------------------------------------------ |
| `тип/дефект`      | работает не так, как задумано                          |
| `тип/улучшение`   | новая возможность или развитие существующей            |
| `тип/аудит`       | найдено ревью или проверкой, журнал [BUGS.md](BUGS.md) |
| `тип/рефакторинг` | внутреннее устройство без изменения поведения          |
| `тип/проверка`    | приёмка фазы: тесты, замеры, снимки, сквозные сценарии |
| `тип/решение`     | требует решения владельца и записи ADR                 |

**`дефект` или `аудит`?** Дефект видно снаружи: владелец нажал и получил не
то. Аудит нашла проверка — контраст 3.9:1, цель 39.9px, — и снаружи он ещё
никого не задел. Разница в том, кто платит за отсрочку.

**`рефакторинг` или `качество/`?** Рефакторинг меняет устройство и не меняет
поведение. Ось `качество/` — требование, по которому работу принимают; она
ставится вместе с типом, а не вместо него.

🔴 **Ось `тип/` — ярлыки, а не нативное поле issue types**, потому что типы
задач — функция организации, а репозиторий пока личный. При переносе ось
конвертируется в типы один в один: переразметки не потребуется.

## Ось `качество/` — сквозное требование

Идёт поперёк разделов. Это **не «плохой код»** — для него есть
`тип/рефакторинг`. Это нефункциональные требования, по которым считают долг
и принимают работу.

| Ярлык                         | Что стоит за ним                              |
| ----------------------------- | --------------------------------------------- |
| `качество/доступность`        | клавиатура, фокус, роли и имена, контраст AA  |
| `качество/производительность` | Core Web Vitals, бюджет JS, число запросов    |
| `качество/безопасность`       | секреты, права, ограничение частоты, загрузки |
| `качество/seo`                | каноникал, метаданные, JSON-LD, sitemap       |
| `качество/адаптив`            | поведение раскладки между 320 и 1440          |
| `качество/тёмная-тема`        | вторая тема: палитра, контраст, снимки        |
| `качество/пд`                 | персональные данные и 152-ФЗ (инвариант 12)   |

Смысл оси — в вопросе «где у нас копится долг по доступности», на который
раньше отвечать было нечем: `accessibility` стоял на двух задачах из восьми,
которые про доступность.

## Служебные ярлыки

Вне осей: они описывают не задачу, а её состояние или машинный шлюз.

| Ярлык         | Что делает                                                       |
| ------------- | ---------------------------------------------------------------- |
| `vr:accepted` | 🔴 автор принял расхождение снимков, проверка зеленеет (ADR-230) |
| `blocked`     | ждёт другой задачи или решения владельца                         |
| `duplicate`   | повторяет уже заведённую задачу                                  |
| `wontfix`     | решено не делать                                                 |

🔴 **`vr:accepted` переименованию не подлежит.** Его имя читает CI —
`.github/workflows/ci.yml`, строки 609 и 1111. Тест сверяет словарь с этим
файлом, чтобы переименование не прошло тихо.

## Как добавить или изменить ярлык

1. Правка [`scripts/labels.mjs`](../scripts/labels.mjs) в ветке, Pull Request.
2. После merge — `node scripts/labels-sync.mjs --apply`.

```
node scripts/labels-sync.mjs                 # что изменится, ничего не делая
node scripts/labels-sync.mjs --apply         # завести и поправить
node scripts/labels-sync.mjs --apply --prune # ещё и удалить лишние
```

🔴 **Удаление отделено флагом `--prune` намеренно.** Ярлык, снятый с 88
задач, обратно не возвращается: GitHub не хранит историю снятой разметки, и
восстанавливать пришлось бы руками по памяти.

## Чего в ярлыках нет

- **Статуса** («в работе», «на ревью») — это поле проекта. Два источника
  правды о состоянии задачи разъезжаются в первую же неделю.
- **Приоритета** — его роль играют вехи: задача либо в фазе, либо нет.
- **Фазы** — веха и есть фаза.
