# Plan: Доработки после аудита — данные, контракт и производительность

**PRD:** [prd-data-performance.md](prd-data-performance.md)
**Дата:** 2026-08-29

## Фазы реализации

### Фаза 1: Цена и скидка не врут

**Цель:** Витрина показывает настоящую скидку или не показывает ничего, а
прайс сохраняется целиком. Минимальный рабочий путь: чистая доменная логика,
покрытая тестами, без правок инфраструктуры.
**Затрагивает:** backend

**Задачи:**

- [ ] Убрать «−0%»: округление процента до нуля не должно давать плашку ни в
      подборе, ни в карточке, ни в проекции репозитория
      ([BUGS §3044](BUGS.md))
- [ ] Закрыть пачку краевых случаев домена: `basePriceForClass` подключить или
      удалить, перевёрнутый период и скидочную цену выше обычной отклонять на
      сервере ([BUGS §3291](BUGS.md))
- [ ] Не терять строку прайса без класса молча и показывать ошибку у своей
      строки ([BUGS §3058](BUGS.md))
- [ ] Тесты: комбинации цен без «−0%», отказ схемы на перевёрнутом периоде,
      сохранение прайса с неполной строкой

**Когда готова:** Ни одной комбинации цены и скидки, дающей «−0%»; строка
прайса без класса не исчезает; тесты цен зелёные.

### Фаза 2: Заявка не теряется и знает, откуда пришла

**Цель:** Статус заявки на экране совпадает с базой, атрибуция собирается
сервером, а истёкшая сессия не выглядит отказом сервера.
**Затрагивает:** backend / frontend

**Задачи:**

- [ ] Возвращать прежний статус заявки при отказе сервера; тот же разбор — у
      чеклиста выезда ([BUGS §3017](BUGS.md))
- [ ] Собирать `sourceUrl`, `referrer` и utm только из заголовков, как
      требует [API §8](API.md) ([BUGS §3167](BUGS.md))
- [ ] Защитить `fromLead` от гонки на уникальном ключе телефона
      ([BUGS §3224](BUGS.md))
- [ ] Перевести `profile-form` и `specs-dictionary` на `adminRequest` и убрать
      приведения типов ([BUGS §3075](BUGS.md))
- [ ] Тесты: откат статуса при отказе, игнорирование полей атрибуции из тела,
      два одновременных обращения с одного номера, истёкшая сессия в профиле

**Когда готова:** Экран и база не расходятся по статусу; атрибуция не
подменяется телом запроса; гонка по телефону не даёт пятисотки.

### Фаза 3: Схемы держат целостность нарядов и склада

**Цель:** Частичное обновление не стирает данные, статус наряда следует за
исполнителем, ошибки базы не выдаются за бизнес-ответ.
**Затрагивает:** backend

**Задачи:**

- [ ] Сделать `PATCH` склада частичным обновлением: пропущенное поле не
      сбрасывает порог и не возвращает позицию из архива
      ([BUGS §3686](BUGS.md))
- [ ] Связать `status` и `installerId` в `orderUpdateSchema`
      ([BUGS §3656](BUGS.md))
- [ ] Проверять `leadId` наравне с `clientId` и `installerId`, чтобы `P2003`
      не превращался в 500 ([BUGS §3716](BUGS.md))
- [ ] Различать в `cancelConsumption` повтор и любую другую ошибку базы
      ([BUGS §3213](BUGS.md))
- [ ] Тесты схем `order` и `stock` на частичное обновление, связку статуса и
      исполнителя, неизвестный `leadId`; тест отмены списания при ошибке базы

**Когда готова:** Ни одно поле не теряется при частичном обновлении; наряд с
исполнителем не остаётся «Новым»; отмена списания различает причины отказа.

### Фаза 4: Двое в панели не затирают друг друга

**Цель:** Параллельная работа перестаёт быть тихой потерей данных, а по
реалтайму принято решение.
**Затрагивает:** backend / database

**Задачи:**

- [ ] Не давать сохранению затирать поля, изменённые другим человеком
      ([BUGS §1864](BUGS.md); нужен ADR)
- [ ] Принять решение по реалтайму в панели: нужен ли, в каком объёме, какой
      ценой ([BUGS §1896](BUGS.md), ADR)
- [ ] Перевести `Notification.channel` и `kind` на enum миграцией с
      приведением типов ([BUGS §321](BUGS.md))
- [ ] Тесты: одновременная правка одного наряда двумя сессиями, миграция на
      существующих строках уведомлений

**Когда готова:** Второе сохранение не затирает чужие поля молча; решение по
реалтайму записано ADR; миграция уведомлений проходит на заполненной базе.

### Фаза 5: Страница не тащит лишнего

**Цель:** Публичные страницы перестают делать лишние запросы и слать в HTML
данные, которых не используют.
**Затрагивает:** backend / frontend

**Задачи:**

- [ ] Читать настройки один раз на запрос ([BUGS §3096](BUGS.md))
- [ ] Отдавать в первый экран только те поля моделей, которые он рисует
      ([BUGS §3114](BUGS.md))
- [ ] Отдавать начальные данные расхода вместе со страницей наряда, без веера
      клиентских запросов ([BUGS §3136](BUGS.md))
- [ ] Завести `loading.tsx` каталогу, сравнению и листингу статей, подключив
      уже написанные скелетоны ([BUGS §3151](BUGS.md))
- [ ] Замеры до и после: число запросов Prisma на четырёх маршрутах, вес HTML
      главной, число клиентских запросов карточки наряда

**Когда готова:** Настройки читаются один раз на запрос; в HTML первого
экрана нет неиспользуемых фотографий и характеристик; переход по фильтру
показывает скелетон.

### Фаза 6: Бюджет JS и медиа

**Цель:** Вернуть запас бюджета собственного JS и убрать трёхсекундную
задержку первой картинки.
**Затрагивает:** frontend

**Задачи:**

- [ ] Развести бочонок `shared/ui` или объявить `sideEffects`, чтобы кит
      панели не уезжал в чанк лендинга ([BUGS §1286](BUGS.md))
- [ ] Ускорить первый ответ `/api/media` и поправить `sizes` у аватаров
      ([BUGS §2346](BUGS.md))
- [ ] Замер `node scripts/js-budget.mjs apps/web/.next --strict` до и после,
      отдельным окном на стенде; замер загрузки изображений на 375

**Когда готова:** Запас бюджета не меньше 5 КБ; первый запрос `/api/media`
укладывается в 300 мс; через шесть секунд после `load` незагруженных
изображений нет.
