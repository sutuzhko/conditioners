# DEPLOY — выкладка и эксплуатация

> Обоснование решений: [TECH_DECISIONS.md](TECH_DECISIONS.md) · Чек-лист перед запуском — там же, §19

---

## 1. Что где живёт

**Продакшн:** VPS у российского провайдера (Selectel / Timeweb / REG.RU). Минимально: 2 vCPU, 4 ГБ RAM, 40 ГБ SSD.

**Контейнеры:**

| Сервис    | Что делает                                                                       |
| --------- | -------------------------------------------------------------------------------- |
| `caddy`   | TLS (Let's Encrypt автоматически), реверс-прокси, канонический хост, gzip/brotli |
| `web`     | Next.js в режиме `standalone`                                                    |
| `worker`  | разбирает очередь уведомлений; идёт из полной сборки — ему нужен `tsx`           |
| `migrate` | разовый шаг выкладки: `prisma migrate deploy`. `web` и `worker` ждут его успеха  |
| `db`      | PostgreSQL 16, данные в именованном volume, порт только на петле сервера         |

`worker` отдельным контейнером, чтобы перезапуск веба не рвал доставку уведомлений.

**Volume'ы:** `pgdata` — база · `uploads` — загруженные файлы · `caddy_data` — сертификаты.

## 2. Разработка — тот же Docker

🔴 Локальный запуск только через compose. `pnpm dev` на хосте не поддерживается: смысл в том, чтобы дев-среда совпадала с боевой (ADR-017, [TECH_DECISIONS §18](TECH_DECISIONS.md)).

```bash
cp .env.example .env.dev            # заполнить; уведомления оставить в режиме «в лог»
docker compose -f docker-compose.dev.yml up --build
```

Поднимется тот же состав, что на проде: `caddy` + `web` + `worker` + `db`, плюс `storybook`.

| Адрес                           | Что это                                                                         |
| ------------------------------- | ------------------------------------------------------------------------------- |
| **http://tulaklimat.localhost** | сайт через Caddy — так же, как будет на проде: сжатие, заголовки, проксирование |
| http://localhost:3000           | то же приложение напрямую, в обход Caddy — для отладки                          |
| **http://localhost:6006**       | Storybook: UI Kit и блоки лендинга                                              |
| http://storybook.localhost      | Storybook через Caddy                                                           |
| localhost:5432                  | Postgres, для psql и GUI-клиентов                                               |

Смотреть сайт правильно на `tulaklimat.localhost`: домены `*.localhost` браузеры резолвят в петлю сами, ничего прописывать в `/etc/hosts` не нужно. Порт 3000 оставлен как запасной вход — если что-то ведёт себя по-разному на нём и через Caddy, разница в прокси-слое, и это стоит починить до прода.

Команды выполняются **внутри контейнера**, никогда с хоста:

```bash
docker compose -f docker-compose.dev.yml exec web pnpm prisma migrate dev
docker compose -f docker-compose.dev.yml exec web pnpm seed
docker compose -f docker-compose.dev.yml exec web pnpm test
docker compose -f docker-compose.dev.yml exec db psql -U tk -d tulaklimat
```

Репозиторий — pnpm-воркспейс: приложение живёт в `apps/web`, в корне только инфраструктура и документация (ADR-027). Корневые скрипты пробрасывают команды в приложение, поэтому запускать их можно из `/app`, не переходя в каталог.

Если pnpm просит подтвердить пересборку `node_modules`, а команда идёт без TTY — добавь `-e CI=true` к `docker compose exec`.

Что это ловит до деплоя: расхождение версий Node и Postgres, регистр в путях импортов (на macOS `Button` и `button` — одно и то же, в Linux-сборке — нет), права и пути к volume с загрузками, поведение Caddy.

Версии Node и Postgres заданы в одном месте и одинаковы в `docker-compose.dev.yml` и `docker-compose.prod.yml`. Расхождение версий между средами — баг.

## 3. Первый запуск на проде

```bash
git clone <repo> /opt/tulaklimat && cd /opt/tulaklimat
cp .env.prod.example .env.prod   # заполнить все значения, включая SITE_DOMAIN и BUILD_DATABASE_URL
infra/deploy.sh
```

`deploy.sh` делает всё в единственно возможном порядке: поднимает базу, ждёт
её готовности, накатывает миграции, собирает образы и запускает состав.

🔴 **Порядок не переставляется.** Главная, политика и статьи пререндерятся с
данными (ISR), поэтому `next build` ходит в базу: собрать образ раньше, чем
появилась схема, нельзя (ADR-062). Собранный образ при недоступной базе
падает — это лучше, чем пустая главная, попавшая в кеш и в индекс.

Первое наполнение — только на пустой базе:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm migrate pnpm --filter web seed
```

DNS-записи `A` для домена и `www` должны уже вести на IP сервера — Caddy выпустит сертификат при первом обращении. `www` и адреса со слэшем на конце уводятся 301-м редиректом на канонический хост.

## 4. Обновление

```bash
cd /opt/tulaklimat && git pull
infra/deploy.sh
```

Тот же скрипт: миграции накатываются до сборки, старые контейнеры заменяются
после неё. Простой — секунды, пока поднимается новый `web`.

Автодеплой с каждого пуша сознательно не настраивается: на проекте одного разработчика он создаёт больше рисков, чем экономит времени.

## 5. Переменные окружения

Полный список с комментариями — в `.env.prod.example`. Ключевые:

| Переменная                               | Смысл                                                         |
| ---------------------------------------- | ------------------------------------------------------------- |
| `DATABASE_URL`                           | строка подключения к Postgres из контейнеров                  |
| `BUILD_DATABASE_URL`                     | она же для сборки образа: адрес базы на петле сервера         |
| `SITE_DOMAIN`                            | домен без схемы — по нему Caddy выпускает сертификат          |
| `ACME_EMAIL`                             | адрес для писем Let's Encrypt об истечении сертификата        |
| `SITE_URL`                               | канонический адрес, из него строятся каноникалы, sitemap и OG |
| `SESSION_SECRET`                         | подпись cookie-сессии админки                                 |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH`     | первый администратор (Argon2id)                               |
| `SMTP_*`, `NOTIFY_EMAIL_TO`              | почтовый канал уведомлений                                    |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | 🔴 только на сервере                                          |
| `TELEGRAM_TRANSPORT`                     | `direct` \| `proxy` \| `off`                                  |
| `TELEGRAM_PROXY_URL`                     | адрес прокси при `proxy`                                      |
| `TELEGRAM_WEBHOOK_SECRET`                | проверка входящих апдейтов                                    |
| `UPLOADS_DIR`                            | путь к volume с файлами                                       |
| `YANDEX_METRIKA_ID`                      | счётчик, единственная публичная переменная                    |

🔴 Ни одна из них, кроме `NEXT_PUBLIC_*`, не должна попасть в клиентский бандл. ENV проверяется Zod-схемой при старте: приложение не поднимется с неполной конфигурацией.

## 6. Проверка Telegram с боевого сервера

Это единственный способ узнать правду о доступности — с локальной машины (тем более через VPN) проверка ничего не значит.

Проверять надо из `worker` — в Telegram ходит именно он. `curl` в образах нет,
есть `wget` из busybox:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml exec worker \
  sh -c 'time wget -qO- --timeout=10 https://api.telegram.org/ >/dev/null && echo доступен'
```

| Результат             | Действие                                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| «доступен» за секунду | `TELEGRAM_TRANSPORT=direct`                                                                                                                 |
| таймаут или обрыв TLS | поднять WireGuard-туннель с маршрутизацией `149.154.160.0/20` и `91.108.4.0/22`, либо SOCKS5 на зарубежном VPS → `TELEGRAM_TRANSPORT=proxy` |
| решение отложено      | `TELEGRAM_TRANSPORT=off`, работает email                                                                                                    |

После включения канала — поставить вебхук (с сервера, тем же транспортом):

```
POST https://api.telegram.org/bot<TOKEN>/setWebhook
  url=https://<домен>/api/telegram/webhook
  secret_token=<TELEGRAM_WEBHOOK_SECRET>
```

🔴 Что настраивается где: **в переменных окружения — доступы** (токен бота,
пароль SMTP, адрес прокси), **в админке — выбор каналов и адресация** (раздел
«Уведомления»: включён ли Telegram, включена ли почта, в какой чат и на какой
адрес). Канал работает, только если владелец его выбрал и доступы на месте;
раздел показывает оба условия и подсказывает, чего не хватает (ADR-058).

🔴 Секрет вебхука — только ASCII: A–Z, a–z, 0–9, дефис и подчёркивание, 1–256 символов.
Кириллица в заголовок HTTP не поместится, и Telegram такой вебхук не примет.

Проверка после установки: нажать кнопку модерации под любым отзывом в чате.
Кнопки должны исчезнуть, а к сообщению — дописаться итог и имя нажавшего.
Ничего не произошло — смотреть `getWebhookInfo`: там видно последнюю ошибку
доставки. **Пока `TELEGRAM_WEBHOOK_SECRET` не задан, адрес отвечает 404 на
любой запрос** — это защита от чужих команд, а не поломка.

## 7. Бэкапы

```bash
0 3 * * * cd /opt/tulaklimat && infra/backup.sh >> /var/log/tulaklimat-backup.log 2>&1
```

`infra/backup.sh` кладёт дамп базы (`pg_dump -Fc`) и архив загрузок в
`BACKUP_DIR` (по умолчанию `/var/backups/tulaklimat`), хранит 30 дней и падает,
если дамп вышел пустым.

🔴 **Каталог назначения — на другом диске или на другой машине.** Бэкап рядом
с базой не переживёт ровно тот случай, ради которого делался.

Раз в квартал — проверка восстановления. Непроверенный бэкап бэкапом не
является:

```bash
infra/restore-check.sh /var/backups/tulaklimat/db_2026-08-22_03-00.dump
```

Скрипт поднимает одноразовый Postgres, восстанавливает в него дамп, проверяет,
что таблицы на месте, и показывает, сколько в нём заявок, отзывов, товаров и
статей. Боевую базу он не трогает вовсе.

| Дата проверки   | Дамп          | Итог                                                                        |
| --------------- | ------------- | --------------------------------------------------------------------------- |
| 22 августа 2026 | дев-база      | репетиция: дамп восстановился, схема и данные на месте (2 заявки, 4 статьи) |
| —               | боевые данные | после выкладки                                                              |

## 8. Проверка после выкладки

```bash
curl -s https://<домен>/api/health                    # {"ok":true}
curl -s https://<домен>/ | grep -c "₽"                # цены в HTML, без JS
curl -sI https://<домен>/admin | grep -i x-robots     # noindex
curl -s https://<домен>/robots.txt
curl -s https://<домен>/sitemap.xml | head
```

Затем вручную: тестовая заявка → появилась в админке → пришло письмо → пришло в Telegram (если канал включён). Тестовую заявку после проверки удалить.
