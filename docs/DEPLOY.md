# DEPLOY — выкладка и эксплуатация

> Обоснование решений: [TECH_DECISIONS.md](TECH_DECISIONS.md) · Чек-лист перед запуском — там же, §19

---

## 1. Что где живёт

**Продакшн:** VPS у российского провайдера (Selectel / Timeweb / REG.RU). Минимально: 2 vCPU, 4 ГБ RAM, 40 ГБ SSD.

**Контейнеры:**

| Сервис    | Что делает                                                                       |
| --------- | -------------------------------------------------------------------------------- |
| `caddy`   | TLS (Let's Encrypt автоматически), реверс-прокси, канонический хост, gzip/brotli |
| `web`     | Next.js в режиме `standalone`                                                    |
| `worker`  | разбирает очередь уведомлений; идёт из полной сборки — ему нужен `tsx`           |
| `migrate` | разовый шаг выкладки: `prisma migrate deploy`. `web` и `worker` ждут его успеха  |
| `db`      | PostgreSQL 16, данные в именованном volume, порт только на петле сервера         |

`worker` отдельным контейнером, чтобы перезапуск веба не рвал доставку уведомлений.

**Volume'ы:** `pgdata` — база · `uploads` — загруженные файлы · `caddy_data` — сертификаты.

**Размеры образов:** `web` — около 300 МБ (только standalone-сборка),
`worker` — около 1,6 ГБ (`node_modules`, Prisma CLI и `tsx`), `migrate` —
заметно легче: он растёт из стадии `deps` без сборки сайта (ADR-089).
Вместе с кешем сборки на диск уходит порядка 8–10 ГБ, поэтому 40 ГБ SSD —
это минимум с запасом, а не «впритык». Старые слои чистит сам `deploy.sh`
последним шагом (`docker image prune -f`).

## 2. Разработка — два режима

Режима два, и выбирается он не по вкусу, а по машине.

| Режим                                         | Когда                                                                                  |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| **Полный состав в Docker** — §2.1             | По умолчанию. Всё, что трогает Caddy, воркер, сборку образа или поведение прода        |
| **База в Docker, приложение на хосте** — §2.2 | Когда машина не тянет полный состав: вёрстка, панель, доменная логика, тесты (ADR-173) |

🔴 **Достоверность даёт первый режим, а не второй.** Хостовый запуск снимает
нагрузку ценой расхождения сред — того самого, ради которого заведён ADR-017.
Последнее слово остаётся за CI: он собирает боевой образ и гоняет тесты в
контейнере, и вердикт «работает» выдаёт он, а не хостовый прогон.

### 2.1 Полный состав в Docker

🔴 Здесь дев-среда совпадает с боевой (ADR-017, [TECH_DECISIONS §18](TECH_DECISIONS.md)). Всё, что про Caddy, воркер уведомлений, сборку образа и поведение прода, проверяется только так.

```bash
cp .env.example .env.dev            # заполнить; уведомления оставить в режиме «в лог»
                                    # SITE_URL остаётся http — ADR-102, иначе не работают ни вход в панель, ни seed:demo
docker compose -f docker-compose.dev.yml up --build
```

Поднимется тот же состав, что на проде: `caddy` + `web` + `worker` + `db`, плюс `storybook`.

| Адрес                           | Что это                                                                         |
| ------------------------------- | ------------------------------------------------------------------------------- |
| **http://tulaklimat.localhost** | сайт через Caddy — так же, как будет на проде: сжатие, заголовки, проксирование |
| http://localhost:3000           | то же приложение напрямую, в обход Caddy — для отладки                          |
| **http://localhost:6006**       | Storybook: UI Kit и блоки лендинга                                              |
| http://storybook.localhost      | Storybook через Caddy                                                           |
| localhost:5432                  | Postgres, для psql и GUI-клиентов                                               |

🔴 Все порты дев-состава опубликованы **только на петле** (`127.0.0.1`).
В дев-базе лежат настоящие данные владельца, а вход в панель — `admin`/`admin`:
на машине в сети слушающий `0.0.0.0` порт означал бы открытую панель с
персональными данными. Стенд с другой машины — туннелем, см. ниже.

Смотреть сайт правильно на `tulaklimat.localhost`: домены `*.localhost` браузеры резолвят в петлю сами, ничего прописывать в `/etc/hosts` не нужно. Порт 3000 оставлен как запасной вход — если что-то ведёт себя по-разному на нём и через Caddy, разница в прокси-слое, и это стоит починить до прода.

### 2.2 База в Docker, приложение на хосте

Тяжёлый в дев-составе ровно один контейнер: `web` занимает от 870 МБ до 2 ГБ
памяти и до 740% процессора, тогда как всё остальное вместе — 122 МБ. На машине,
которой этого не хватает, браузер перестаёт открывать страницы, и выглядит это
как поломка сайта, а не как нехватка памяти (ADR-173).

**Подготовка — один раз.**

```bash
nvm use                                        # версия из .nvmrc; должна совпадать с образом
pnpm install                                   # свой node_modules на хосте, тома контейнера не трогаются
pnpm --filter web exec prisma generate         # клиент Prisma под платформу хоста
pnpm --filter web exec playwright install chromium   # сборки под musl из образа на хосте не работают
cp apps/web/.env.local.example apps/web/.env.local
```

🔴 **`.env.local` кладётся в `apps/web/`, а не в корень репозитория.** Next
читает файлы переменных относительно каталога приложения. Файл в корне он не
увидит, и приложение не поднимется вовсе: «Некорректная конфигурация окружения:
DATABASE_URL Required».

🔴 **Доллары в `ADMIN_PASSWORD_HASH` здесь одинарные.** В `.env.dev` они
удвоены, потому что файл читает Compose и `$` для него — начало переменной.
Next читает файл сам, и удвоение оставит в хеше лишние символы: пароль
перестанет подходить, хотя он верный.

🔴 **`SESSION_SECRET` обязан совпадать с тем, что в `.env.dev`.** Им подписана
cookie сессии. С разными секретами вход, сделанный в одном режиме, в другом не
признаётся, и браузер со старой cookie получает отказ на каждой странице панели.

**Запуск.**

```bash
docker compose -f docker-compose.dev.yml up -d db    # одна база, 43 МБ
pnpm --filter web dev                                # приложение на хосте
```

Сайт — на **http://localhost:3000**. Caddy не поднят, поэтому
`tulaklimat.localhost` в этом режиме не отвечает: проверять поведение прокси,
сжатия и заголовков нужно в §2.1.

**Что в этом режиме не работает и почему.**

| Не работает                      | Почему и что делать                                                                                            |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `http://tulaklimat.localhost`    | Caddy не поднят. Отладка прокси — только полным составом                                                       |
| Воркер уведомлений               | Не запущен: очередь наполняется, но не разбирается. Нужен — поднимите `worker` рядом с `db`                    |
| Storybook                        | Не запущен. Поднимается отдельно: `up -d storybook`                                                            |
| Сквозные сценарии без переменной | Умолчание конфига — `http://web:3000`, имя из сети Compose. Снаружи нужен `E2E_BASE_URL=http://localhost:3000` |
| Ранее загруженные картинки       | Файлы лежат в томе контейнера, а хост пишет в `apps/web/.data/uploads`. Хранилища разные и не смешиваются      |

**Проверки.** Тесты и типы на хосте проходят целиком: 2927 проверок в 269
файлах, `tsc` — без ошибок. Хук коммита при выключенном `web` сам переключается
на хостовый прогон, обходить его по-прежнему нельзя.

🔴 **ADR-147 («`tsc` на хосте лжёт») к этому режиму не относится.** Причина
запрета была в том, что типы маршрутов Next генерируются в `.next`, а `.next`
лежал в томе контейнера. Когда Next работает на хосте, `.next` тоже на хосте, и
проверка типов честная. Запрет остаётся в силе для своего случая: приложение в
контейнере, `tsc` с хоста.

### Стенд на другой машине

Если Docker поднят не там, где открыт браузер (разработка идёт по SSH на отдельный ПК), привычный `tulaklimat.localhost` сам по себе не заработает: имена `*.localhost` браузер резолвит в петлю самостоятельно и в `hosts` за ними не ходит (RFC 6761). Прописать там адрес стенда бесполезно — строка будет проигнорирована, и браузер всё равно постучится к себе.

Адрес сохраняется пробросом порта Caddy по тому же SSH-подключению, которым идёт работа. Держать проброс лучше в `~/.ssh/config` рабочей машины, а не флагом `-L`: тогда туннель поднимается при любом подключении, включая Remote-SSH из редактора.

```
Host tulaklimat-dev
  HostName <ip-стенда>
  Port <порт sshd>
  User <пользователь>
  LocalForward 8080 localhost:80
```

Локальный порт — 8080, а не 80: на macOS и Linux порты ниже 1024 слушает только root, и проброс на 80-й молча не поднимется (`bind: Permission denied`, дальше ssh работает как ни в чём не бывало — легко не заметить). Адрес получается `http://tulaklimat.localhost:8080`; Caddy сверяет имя хоста и порт в заголовке `Host` не смотрит, так что стенд отвечает тем же сайтом.

🔴 На macOS в довесок нужна строка в `/etc/hosts` рабочей машины:

```
127.0.0.1 tulaklimat.localhost
```

Разворачивают `*.localhost` в петлю сами только Chrome и Firefox — у них собственный резолвер. Системный резолвер macOS про эти имена не знает: Safari, curl и всё, что ходит через него, имя не найдут вовсе. В Linux строка не нужна — `systemd-resolved` отвечает за `*.localhost` сам.

Прямой заход по адресу машины (`http://<ip-стенда>:3000`) тоже работает, но идёт мимо Caddy: ни сжатия, ни заголовков безопасности, ни слэш-редиректов — то есть ровно тот слой, ради которого дев-окружение и повторяет боевое, остаётся непроверенным.

Команды выполняются **внутри контейнера**, никогда с хоста:

```bash
docker compose -f docker-compose.dev.yml exec web pnpm prisma migrate dev
docker compose -f docker-compose.dev.yml exec web pnpm seed
docker compose -f docker-compose.dev.yml exec web pnpm test
docker compose -f docker-compose.dev.yml exec web pnpm shot / --theme both
docker compose -f docker-compose.dev.yml exec db psql -U tk -d tulaklimat
```

🔴 **После `prisma migrate reset` владельца в базе нет.** Его заводит базовый
`pnpm seed` из `ADMIN_LOGIN` и `ADMIN_PASSWORD_HASH`; `pnpm seed:demo`
создаёт только монтажников. Порядок обязателен, и средний шаг пропускать
нельзя:

```bash
docker compose -f docker-compose.dev.yml exec web pnpm prisma migrate reset
docker compose -f docker-compose.dev.yml exec web pnpm seed
docker compose -f docker-compose.dev.yml exec web pnpm seed:demo
```

Пропуск `seed` оставляет наполненный стенд без единого входа в панель, и
обнаруживается это на странице логина. Демо-сид с версии ADR-154 говорит об
этом сам, последней строкой вывода.

🔴 **База, наполненная до 29 августа, требует одного разового прогона.** С
ADR-171 снимки клиента — фото при заявке и снимки наряда — лежат в подкаталоге
`protected` и хранятся в базе именем файла, а не адресом. Записи, сделанные
раньше, об этом не знают: в панели у них будет битая картинка, а прежний
публичный адрес останется рабочим. Переносит их скрипт, идемпотентный и
безопасный для повторного запуска:

```bash
docker compose -f docker-compose.dev.yml exec -T web \
  pnpm --filter web exec tsx prisma/move-protected-media.ts
```

Базе, наполненной `pnpm seed:demo` начиная с этой версии, прогон не нужен —
демо-сид кладёт снимки сразу как надо.

`pnpm shot` снимает страницы стенда в PNG (`apps/web/.screenshots`, в
репозиторий не попадают) — это способ увидеть вёрстку, когда браузера под
рукой нет: работа по SSH, проверка на чужой машине, ревью правки по описанию.
Ширины и темы задаются списком (`--width 1200,375 --theme both`), `--full`
снимает страницу целиком, `--admin` входит в панель. Рядом с файлом печатается
код ответа: снимок страницы с ошибкой выглядит как страница (ADR-103).

Репозиторий — pnpm-воркспейс: приложение живёт в `apps/web`, в корне только инфраструктура и документация (ADR-027). Корневые скрипты пробрасывают команды в приложение, поэтому запускать их можно из `/app`, не переходя в каталог.

Если pnpm просит подтвердить пересборку `node_modules`, а команда идёт без TTY — добавь `-e CI=true` к `docker compose exec`.

Что это ловит до деплоя: расхождение версий Node и Postgres, регистр в путях импортов (на macOS `Button` и `button` — одно и то же, в Linux-сборке — нет), права и пути к volume с загрузками, поведение Caddy.

Версии Node и Postgres заданы в одном месте и одинаковы в `docker-compose.dev.yml` и `docker-compose.prod.yml`. Расхождение версий между средами — баг.

## 3. Первый запуск на проде

```bash
git clone <repo> /opt/tulaklimat && cd /opt/tulaklimat
cp .env.prod.example .env.prod   # заполнить все значения, включая SITE_DOMAIN и BUILD_DATABASE_URL
infra/deploy.sh
```

🔴 **Каждый `$` в значении удваивается.** `.env.prod` читает docker compose, и
`$argon2id` он подставляет как переменную окружения — то есть как пустоту. Хеш
Argon2id содержит `$` всегда, поэтому пишется он так:

```
ADMIN_PASSWORD_HASH=$$argon2id$$v=19$$m=19456,t=2,p=1$$<соль>$$<хеш>
```

То же касается `SMTP_PASSWORD` и пароля внутри `TELEGRAM_PROXY_URL`. Пропуск
не виден ничем, кроме следствия: в панель перестаёт пускать верный пароль, а в
журнале компоуза остаётся строка «The "argon2id" variable is not set».
`infra/deploy.sh` проверяет это первым шагом и останавливает выкладку.

🔴 До первого деплоя заведите на VPS swap не меньше 2 ГБ: сборка `next build`
идёт на том же сервере рядом с работающим составом, и без запаса её пик
упирается в OOM-killer. Сервисы ограничены `mem_limit` в compose — прожорливый
контейнер перезапустится сам, не утащив за собой postgres, — но сборка живёт
вне этих лимитов, её страхует только swap. Деплойтесь не в пик обращений.

`infra/deploy.sh` делает всё в единственно возможном порядке: поднимает базу, ждёт
её готовности, накатывает миграции, собирает образы и запускает состав.

🔴 **Порядок не переставляется.** Главная, политика и статьи пререндерятся с
данными (ISR), поэтому `next build` ходит в базу: собрать образ раньше, чем
появилась схема, нельзя (ADR-062). Собранный образ при недоступной базе
падает — это лучше, чем пустая главная, попавшая в кеш и в индекс.

Первое наполнение — только на пустой базе:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm migrate pnpm --filter web seed
```

DNS-записи `A` для домена и `www` должны уже вести на IP сервера — Caddy выпустит сертификат при первом обращении. `www` и адреса со слэшем на конце уводятся 301-м редиректом на канонический хост.

## 4. Обновление

```bash
cd /opt/tulaklimat && git pull
infra/deploy.sh
```

Тот же скрипт: миграции накатываются до сборки, старые контейнеры заменяются
после неё. Простой — секунды, пока поднимается новый `web`. Перед миграциями
скрипт снимает дамп в `/var/backups/tulaklimat/predeploy_*.dump` (путь —
переменная `BACKUP_DIR`) — это срез «за минуту до», на случай разбора ниже.

**Если миграция упала.** Сайт продолжает работать на старой версии — `web` не
пересоздавался. Но Prisma пометила миграцию как неудавшуюся, и повторный
`deploy.sh` заблокирован, пока это не разобрано руками:

```bash
# что именно упало и на каком шаге
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm migrate \
  pnpm --filter web exec prisma migrate status

# база не менялась (упало на первом операторе) — снять пометку и деплоить снова
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm migrate \
  pnpm --filter web exec prisma migrate resolve --rolled-back <имя_миграции>

# база изменилась частично — сначала вернуть её к срезу «за минуту до»:
# pg_restore --clean дампа predeploy_*, затем resolve --rolled-back и деплой
```

Чинить миграцию правкой SQL на живой базе нельзя (docs/CLAUDE.md, «Данные»):
исправление — это новая миграция в репозитории.

Автодеплой с каждого пуша сознательно не настраивается: на проекте одного разработчика он создаёт больше рисков, чем экономит времени.

## 5. Переменные окружения

Полный список с комментариями — в `.env.prod.example`. Ключевые:

| Переменная                               | Смысл                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------- |
| `DATABASE_URL`                           | строка подключения к Postgres из контейнеров                                          |
| `BUILD_DATABASE_URL`                     | она же для сборки образа: адрес базы на петле сервера                                 |
| `SITE_DOMAIN`                            | домен без схемы — по нему Caddy выпускает сертификат                                  |
| `ACME_EMAIL`                             | адрес для писем Let's Encrypt об истечении сертификата                                |
| `SITE_URL`                               | канонический адрес, из него строятся каноникалы, sitemap и OG                         |
| `SESSION_SECRET`                         | подпись cookie-сессии админки                                                         |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH`     | первый администратор (Argon2id). 🔴 В хеше каждый `$` удваивается — см. ниже          |
| `NOTIFY_DRIVER`                          | 🔴 `live` на бою. По умолчанию `log`: уведомления пишутся в журнал и никуда не уходят |
| `SMTP_*`, `NOTIFY_EMAIL_TO`              | почтовый канал уведомлений                                                            |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | 🔴 только на сервере                                                                  |
| `TELEGRAM_TRANSPORT`                     | `direct` \| `proxy` \| `off`                                                          |
| `TELEGRAM_PROXY_URL`                     | адрес прокси при `proxy`                                                              |
| `TELEGRAM_WEBHOOK_SECRET`                | проверка входящих апдейтов                                                            |
| `UPLOADS_DIR`                            | путь к volume с файлами                                                               |

🔴 **Знак доллара в значении удваивается.** `.env.prod` подставляется docker
compose, и `$имя` для него — переменная окружения. Значение с одиночным `$`
приезжает в контейнер обрубленным: `$$argon2id$$v=19$$m=…` — верно,
`$argon2id$v=19$m=…` — молча ломает вход в панель. Касается
`ADMIN_PASSWORD_HASH`, `SMTP_PASSWORD` и пароля внутри `TELEGRAM_PROXY_URL`.
Выкладку с одиночным `$` останавливает предполётная проверка в
`infra/deploy.sh`.

🔴 Ни одна из них не должна попасть в клиентский бандл. Счётчик Метрики — не переменная окружения: его идентификатор владелец задаёт в админке (настройки, группа `integrations`). ENV проверяется Zod-схемой при старте: приложение не поднимется с неполной конфигурацией.

## 6. Проверка Telegram с боевого сервера

Это единственный способ узнать правду о доступности — с локальной машины (тем более через VPN) проверка ничего не значит.

Проверять надо из `worker` — в Telegram ходит именно он. `curl` в образах нет,
есть `wget` из busybox:

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml exec worker \
  sh -c 'time wget -qO- --timeout=10 https://api.telegram.org/ >/dev/null && echo доступен'
```

| Результат             | Действие                                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| «доступен» за секунду | `TELEGRAM_TRANSPORT=direct`                                                                                                                 |
| таймаут или обрыв TLS | поднять WireGuard-туннель с маршрутизацией `149.154.160.0/20` и `91.108.4.0/22`, либо SOCKS5 на зарубежном VPS → `TELEGRAM_TRANSPORT=proxy` |
| решение отложено      | `TELEGRAM_TRANSPORT=off`, работает email                                                                                                    |

После включения канала — поставить вебхук (с сервера, тем же транспортом):

```
POST https://api.telegram.org/bot<TOKEN>/setWebhook
  url=https://<домен>/api/telegram/webhook
  secret_token=<TELEGRAM_WEBHOOK_SECRET>
```

🔴 Что настраивается где: **в переменных окружения — доступы** (токен бота,
пароль SMTP, адрес прокси), **в админке — выбор каналов и адресация** (раздел
«Уведомления»: включён ли Telegram, включена ли почта, в какой чат и на какой
адрес). Канал работает, только если владелец его выбрал и доступы на месте;
раздел показывает оба условия и подсказывает, чего не хватает (ADR-058).

🔴 Секрет вебхука — только ASCII: A–Z, a–z, 0–9, дефис и подчёркивание, 1–256 символов.
Кириллица в заголовок HTTP не поместится, и Telegram такой вебхук не примет.

Проверка после установки: нажать кнопку модерации под любым отзывом в чате.
Кнопки должны исчезнуть, а к сообщению — дописаться итог и имя нажавшего.
Ничего не произошло — смотреть `getWebhookInfo`: там видно последнюю ошибку
доставки. **Пока `TELEGRAM_WEBHOOK_SECRET` не задан, адрес отвечает 404 на
любой запрос** — это защита от чужих команд, а не поломка.

## 7. Бэкапы

```bash
0 3 * * * cd /opt/tulaklimat && infra/backup.sh >> /var/log/tulaklimat-backup.log 2>&1
```

`infra/backup.sh` кладёт дамп базы (`pg_dump -Fc`) и архив загрузок в
`BACKUP_DIR` (по умолчанию `/var/backups/tulaklimat`), хранит 30 дней и падает,
если дамп вышел пустым.

🔴 **Каталог назначения — на другом диске или на другой машине.** Бэкап рядом
с базой не переживёт ровно тот случай, ради которого делался.

Раз в квартал — проверка восстановления. Непроверенный бэкап бэкапом не
является:

```bash
infra/restore-check.sh /var/backups/tulaklimat/db_2026-08-22_03-00.dump
```

Скрипт поднимает одноразовый Postgres, восстанавливает в него дамп, проверяет,
что таблицы на месте, и показывает, сколько в нём заявок, отзывов, товаров и
статей. Боевую базу он не трогает вовсе.

| Дата проверки   | Дамп          | Итог                                                                        |
| --------------- | ------------- | --------------------------------------------------------------------------- |
| 22 августа 2026 | дев-база      | репетиция: дамп восстановился, схема и данные на месте (2 заявки, 4 статьи) |
| —               | боевые данные | после выкладки                                                              |

## 8. Проверка после выкладки

```bash
curl -s https://<домен>/api/health                    # {"ok":true}
curl -s https://<домен>/ | grep -c "₽"                # цены в HTML, без JS
curl -sI https://<домен>/admin | grep -i x-robots     # noindex
curl -s https://<домен>/robots.txt
curl -s https://<домен>/sitemap.xml | head
curl -sI https://www.<домен>/ | head -2               # 301 на канонический хост
curl -sI https://<домен>/knowledge/ | head -2         # 301 без слэша на конце
```

Затем вручную: тестовая заявка → появилась в админке → пришло письмо → пришло в Telegram (если канал включён). Тестовую заявку после проверки удалить.
