> Основан на `design/API-контракт.md` из хендоффа (лежит в репозитории, ADR-185 — этот документ самодостаточен). Здесь зафиксированы **отличия боевой версии** от прототипа и добавлено то, чего в нём не было.
>
> Обоснование решений: [DECISIONS.md](DECISIONS.md) и [TECH_DECISIONS.md](TECH_DECISIONS.md) · Модель данных: [PROJECT.md](PROJECT.md)

Все ответы — `application/json; charset=utf-8`. Маршруты живут внутри Next (`src/app/api/**`), но контракт соблюдается буквально, чтобы бэкенд можно было вынести в отдельный сервис без правок фронта.

## 2. Публичные данные — ⏳ не реализовано

🔴 **Этого раздела в коде нет.** Ни одного `/api/public/*` не существует, и до появления настоящего потребителя не появится (ADR-122). Раздел оставлен как спроектированная форма будущей границы, а не как описание работающего API: страницы сайта серверные и читают данные напрямую через `server/repo`, лишний круг через сеть им не нужен.

Что было спроектировано и чем станет, когда потребитель появится:

| Метод | Путь                          | Описание                                                                                                                                              |
| ----- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/public/site`            | Всё для рендера одним запросом: `models` (visible), `prices`, `extras`, `contacts`, `legal`, `reviews` (approved), `articles` (published, без `body`) |
| GET   | `/api/public/articles`        | Список опубликованных, без `body`                                                                                                                     |
| GET   | `/api/public/articles/{slug}` | Статья целиком                                                                                                                                        |
| GET   | `/api/public/models/{slug}`   | Модель целиком                                                                                                                                        |

Отдельные публичные чтения, которые **есть** и работают: `/api/settings/{key}` (§5), `/api/prices` (§4), `/api/weather` и `/api/health` (§15).

## 3. Модели

```json
{
  "id": "…",
  "slug": "split-sistema-09",
  "badge": "09",
  "name": "Сплит-система 09",
  "brand": "…",
  "sku": "…",
  "areaMax": 27,
  "tag": "инвертор",
  "priceNum": 38500,
  "salePrice": 34900,
  "saleFrom": "2026-09-01",
  "saleTo": "2026-10-31",
  "saleLabel": "Осенняя цена",
  "link": "",
  "featured": true,
  "visible": true,
  "sort": 0,
  "seoTitle": null,
  "seoDescription": null,
  "photos": [{ "id": "…", "url": "…", "alt": "…", "isMain": true, "sort": 0 }],
  "specs": [{ "k": "Площадь", "v": "до 27 м²" }]
}
```

**`visible` и `featured` — разные вопросы.** `visible` — «модель в продаже»:
она попадает в каталог `/catalog` и в карту сайта. `featured` — «вынести на
главную»: витрина лендинга показывает то, что владелец хочет продать сегодня,
а каталог — весь ассортимент (ADR-109). Порядок в обоих случаях задаёт `sort`.

🔴 `featured` работает только вместе с `visible`: снятая с продажи модель на
главной — предложение купить то, чего нет.

🔴 `specs` — произвольный упорядоченный список пар `{ k, v }`. Никакого фиксированного набора характеристик на бэкенде быть не должно (ADR-015). Группы и порядок вывода задаёт справочник в настройках (§5, ключ `specs`) — он подсказывает и упорядочивает, но ничего не запрещает (ADR-094).

**Скидка.** `salePrice` — конечная цена, а не процент; процент вычисляется на выдаче. Скидка активна, если `salePrice` заполнена и текущая дата внутри `saleFrom…saleTo` (пустые границы = без ограничения). Публичные ответы отдают вычисленные `currentPrice`, `oldPrice`, `discountPercent`, `saleActive` — чтобы клиент, разметка и калькулятор не считали это каждый по-своему.

| Метод  | Путь                                                                                                            |
| ------ | --------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/admin/models`                                                                                             |
| POST   | `/api/admin/models` → `201`                                                                                     |
| PUT    | `/api/admin/models/{id}`                                                                                        |
| PATCH  | `/api/admin/models/{id}`                                                                                        |
| DELETE | `/api/admin/models/{id}`                                                                                        |
| POST   | `/api/admin/models/{id}/photos` — `multipart/form-data`, поле `photo`, jpeg/png/webp ≤ 5 МБ → `201 { id, url }` |
| PATCH  | `/api/admin/models/{id}/photos/{photoId}` — `{ alt, isMain, sort }`                                             |
| DELETE | `/api/admin/models/{id}/photos/{photoId}`                                                                       |
| PATCH  | `/api/admin/models/{id}/sale` — `{ salePrice, saleFrom, saleTo, saleLabel }`; `salePrice: null` снимает скидку  |

Слаг генерируется из названия транслитерацией, уникальность обеспечивается суффиксом. Изменение слага у опубликованной модели заводит 301-редирект со старого адреса.

## 5. Данные компании

🔴 Всё, что в прототипе было выдумано и зашито в разметку, живёт здесь. Ключи и их содержимое — в [PROJECT.md §3](PROJECT.md).

| Метод | Путь                        | Описание                                                                                                                                                                 |
| ----- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET   | `/api/settings/{key}`       | Публичное чтение одной группы: `company`, `contacts`, `address`, `geo`, `area`, `legal` (проекцией, см. ниже), `extras`, `warranty`, `payment`, `social`, `seo`, `specs` |
| GET   | `/api/admin/settings`       | Все группы разом                                                                                                                                                         |
| PUT   | `/api/admin/settings/{key}` | Обновить группу целиком. Тело валидируется схемой, своей для каждого ключа                                                                                               |

Схема каждой группы задана Zod'ом: телефон приводится к единому виду, координаты проверяются на диапазон, часы работы — на формат, пригодный для `openingHours`. Неполные данные компании сохранить можно (владелец заполняет постепенно), но 🔴 **перед запуском действует проверка: ни одна группа не должна содержать заглушку** — эндпоинт `/api/admin/settings/readiness` возвращает список незаполненного.

🔴 **Группа `legal` — размеченное объединение по `form`** (ADR-112, ADR-143), а
не объект с необязательными полями. Состав зависит от формы регистрации:

| Форма   | Поля                                                                                                                     |
| ------- | ------------------------------------------------------------------------------------------------------------------------ |
| `"ИП"`  | `name` (ФИО), `inn` (12), `ogrn` (ОГРНИП, 15), `regDate` (`2015-03-12`), `regAuthority`, `address`, банк                 |
| `"ООО"` | `name` (полное фирменное), `shortName`, `inn` (10), `kpp` (9), `ogrn` (13), `address`, `director`, `directorTitle`, банк |

Банковские реквизиты (`bankName`, `bankBik`, `bankAccount`, `bankCorrAccount`)
одинаковы у обеих форм и необязательны.

Поле чужой формы не игнорируется, а **отвергается**: группа закрыта
`.strict()`, и `PUT` с `kpp` при форме `"ИП"` вернёт `400`. Смена формы стирает
реквизиты прежней — совпадает имя поля, а не смысл.

ИНН, ОГРН, ОГРНИП, КПП, БИК и счета проверяются **контрольным разрядом**, а не
длиной строки (PROJECT §5.2); ключ счёта считается вместе с БИК, поэтому
несходимость приходит с полем `bankAccount` или `bankCorrAccount`. Пустое
значение и заглушка сидов проходят — кроме `regDate`, которая датой быть не
может.

Подпись поля `ogrn` на сайте зависит от формы: у ИП «ОГРНИП», у ООО «ОГРН».
🔴 Адрес регистрации предпринимателя наружу не публикуется (домашний адрес —
персональные данные): что уходит на сайт, решает `publicRequisites`, а не
потребитель группы.

🔴 **Публичное чтение отдаёт реквизиты проекцией, а не группой как есть:**
`{ form, title, requisites: [{ key, label, value }] }` — ровно то, что
напечатано в футере и в политике. Адрес регистрации предпринимателя, КПП,
руководитель и банковские реквизиты наружу не уходят. Группа лежит в базе
целиком, но у неё две двери, и обе закрывает `publicRequisites`.

🔴 **Все три маршрута `/api/admin/settings*` — только для владельца.** Монтажник
получает `403`: в группе лежат персональные данные и адреса доставки
уведомлений, а правка реквизитов меняет продавца на всём сайте.

Отчёт `/api/admin/settings/readiness` называет причину `invalid` для группы,
которую отвергает её собственная схема: значение в базе есть, но публичная
страница разбирает группу с умолчаниями и не показывает ничего.

Группа `schedule` — рабочее окно календаря: `{ fromMin, toMin }`, минуты от
московской полуночи (по умолчанию 540 и 1140). 🔴 Наружу не отдаётся: это
сетка панели, а не часы работы для посетителя — те живут в `contacts.hours`
свободной строкой и разбору не подлежат (ADR-128). Окно ограничивает
показанное по умолчанию, но не то, что можно завести: запись за его границами
создаётся обычным образом и помечается переработкой (ADR-138).

Группа `specs` — справочник характеристик товара (ADR-094):

```json
{
  "groups": [
    {
      "title": "Основное",
      "fields": [
        { "k": "Мощность охлаждения", "unit": "кВт", "hint": "Сколько тепла отводит" },
        { "k": "Тип компрессора", "unit": "", "hint": "" }
      ]
    }
  ]
}
```

🔴 Справочник не ограничивает набор характеристик товара (инвариант 6): он
задаёт группы и порядок, а характеристика, которой в нём нет, попадает в
группу «Прочее» и остаётся видимой.

Сохранение любой группы вызывает ревалидацию всех страниц: данные компании присутствуют в шапке и футере, то есть везде.

## 6. Статьи

Объект `Article` — как в исходном контракте, плюс `seoTitle`, `seoDescription`, `updatedAt`.

| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| GET                  | `/api/admin/articles`                                                                                                           |
| POST                 | `/api/admin/articles` → `201`                                                                                                   |
| PUT / PATCH / DELETE | `/api/admin/articles/{id}`                                                                                                      |
| POST                 | `/api/admin/articles/{id}/cover` → `200 { cover }`                                                                              |
| DELETE               | `/api/admin/articles/{id}/cover` → `200 { cover: null }` — снимает обложку и стирает файл. У статьи без обложки отвечает тем же |

## 7. Отзывы

| Метод  | Путь                               | Описание                                                                                                                                                                                     |
| ------ | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/api/reviews`                     | **Публичный.** `multipart/form-data`: `name`_, `rating`_ (1–5), `text`* (≥ 10 символов), `photo` (≤ 5 МБ), `consent`*, `hp` (honeypot). Создаётся `pending` → `201 { id }`. Rate-limit по IP |
| GET    | `/api/admin/reviews?status=&page=` | Страница списка по статусу: `{ items, total, page, pages }`. По 8 записей, свежие первыми                                                                                                    |
| PATCH  | `/api/admin/reviews/{id}/status`   | `{ status: "pending" \| "approved" \| "archived" }` либо `{ status: "rejected", reason }` — причина 10–500 символов, обязательна                                                             |
| DELETE | `/api/admin/reviews/{id}`          | Безвозвратно                                                                                                                                                                                 |

🔴 Текст отзыва не редактируется ни одним эндпоинтом. Модератор меняет только статус.

🔴 **Отказ без причины не принимается — 400** (ADR-300). Причина инварианту 7 не
противоречит: она про решение модератора, а не про слова автора, и лежит
отдельным полем. Приделать `reason` к одобрению нельзя — схема строгая и
различает переходы: это поле отказа, а не поле на все случаи.

Отзыв отдаётся с блоком `reject` — целиком или `null`, половины не бывает:

```json
{
  "id": "r5",
  "status": "rejected",
  "reject": {
    "reason": "Реклама стороннего магазина",
    "by": "Богдан",
    "at": "2026-09-04T09:00:00.000Z"
  }
}
```

`by` — имя модератора; `null` означает, что учётной записи за отказом нет:
отклонили кнопкой в Telegram либо учётку удалили. Любой переход, кроме отказа,
гасит блок: причина, пережившая возврат на модерацию, читалась бы как
действующая.

🔴 **Кнопка «Запретить» в Telegram причину собрать не может** — у неё нет поля
ввода и нет сессии панели. Канал складывает причину сам и честно называет себя:
`Отклонено кнопкой в Telegram — Имя. Причина не записана.` Отказ остаётся в одно
нажатие намеренно: сделать его дороже соседних кнопок — значит получить архив
вместо отказа.

Смена статуса вызывает ревалидацию страниц с отзывами.

## 8. Заявки

| Метод  | Путь                                | Описание                                                                                                                                                              |
| ------ | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/api/leads`                        | **Публичный.** `multipart/form-data`: `name`_, `phone`_, `topic`, `model`, `place`, `qty`, `callTime`, `address`, `comment`, `photo`, `consent`*, `hp` → `201 { id }` |
| POST   | `/api/leads/to-reminder`            | Напоминание о ТО: `{ phone, when, consent }` → `201`                                                                                                                  |
| GET    | `/api/admin/leads?status=&page=&q=` | Страница списка: `{ items, total, page, pages }`. По 8 записей, свежие первыми. `q` ищет по имени, телефону, адресу, теме и номеру обращения. Клиентский цикл         |
| GET    | `/api/admin/leads/{id}/photo`       | Снимок, приложенный к обращению (ADR-171): `private, no-store`. Клиентский цикл                                                                                       |
| POST   | `/api/admin/leads/{id}/order`       | «Создать заказ»: заводит или находит клиента по телефону и переводит обращение в работу → `200 { client, created, lead }`. Только владелец                            |
| PATCH  | `/api/admin/leads/{id}`             | `{ status, cancelReason, cancelNote, managerComment }`. Клиентский цикл                                                                                               |
| DELETE | `/api/admin/leads/{id}`             | 🔴 Уничтожение персональных данных обращения по 152-ФЗ → `204`. Только владелец                                                                                       |

🔴 Порядок обработки `POST /api/leads`: валидация → запись `Lead` → постановка `Notification` в очередь → `201`. Ответ клиенту **не ждёт** внешние сервисы.

🔴 **У обращения есть вид работ, и он не заменяет свободную тему** (ADR-343).
`workType` в ответе — запись справочника (тот же объект, что у наряда, §13) или
`null`. `null` — рабочее состояние, а не сбой: поле появилось вместе со
справочником, и у всех обращений, пришедших до него, вида работ нет.
Накопленные темы задним числом не разбираются — угаданный по словам вид
честнее не становится. Форма сайта начнёт присылать выбранный вид следующей
фазой; до тех пор поле заполняется только у новых обращений.

🔴 **`model` — то, что человек видел в поле формы и подтвердил** (ADR-129).
Кнопка у модели ведёт на `/?model=<слаг>&topic=<ключ>#lead`, форма открывается
с заполненным видимым полем, и уезжает свободный текст из него, а не слаг из
адреса: поле правится и стирается. Не путать с `Lead.context.model`
(ADR-133) — там невидимый снимок того, с какой карточки человек пришёл. Одно и
то же название может оказаться в обоих полях; подписи в карточке заявки и в
уведомлении их различают. Ограничение — 120 символов, иначе `400` с
`field: "model"`. Параметры `model` и `topic` содержимого главной не меняют и
уходят в `Clean-param` (`robots.txt`), каноникал главной остаётся чистым.

**Имя поля времени звонка — `callTime`.** В первой редакции контракта оно называлось `time`; сервер принимает оба имени ради совместимости, но канонический вариант один, и формы должны слать `callTime`. Расхождение имени поля между контрактом и схемой — то, из-за чего форма молча теряет данные.

`sourceUrl`, `referrer` и utm-метки **не приходят из формы**: сервер собирает их сам из заголовков и адреса страницы-источника. Присылать их в теле бессмысленно — они будут проигнорированы.

`consent` обязателен: без него `400`. Время согласия пишется в `Lead.consentAt`.

**`POST /api/admin/leads/{id}/order` идемпотентен**: `created: false` означает,
что номер уже был в базе. Статус двигается только из `new` в `in_progress` —
завершённую или отклонённую заявку заказ в работу не возвращает.

🔴 **Наряд маршрут не создаёт.** Он готовит клиента, после чего панель уводит
владельца на `/admin/orders/new?lead={id}` — форма наряда одна на панель, и
второй её копии в разделе заявок нет. Номер наряда сквозной, и тратить его на
промах мимо кнопки нельзя (ADR-114).

🔴 **У обращения есть свой сквозной номер** `number` (ADR-311). Он приходит в
каждом ответе, растёт вместе с очередью и не дырявится: счётчик лежит в
`Setting.leadSeq` и инкрементируется в той же транзакции, что и вставка, — так
же, как у наряда (ADR-114). По нему на обращение ссылаются вслух, и по нему же
работает поиск `q`, когда запрос состоит из одних цифр.

🔴 **Отмена и удаление — разные вещи** (ADR-310).

- **Отмена — состояние.** `PATCH { status: "rejected" }` **обязан** нести
  `cancelReason` из справочника (`shared/lib/cancel-reason`: `client_refused`,
  `no_answer`, `too_expensive`, `chose_other`, `postponed`, `our_fault`,
  `other`) и может нести свободное уточнение `cancelNote` (до 500 знаков).
  🔴 Справочник общий с нарядом, и ключ «выбрал другого» — `chose_other`:
  до 7 сентября здесь стоял `other_contractor`, а у наряда `chose_other`,
  и это была одна и та же причина под двумя именами (ADR-311).
  Отказ без причины — `400` с `field: "cancelReason"`: ради разбора причин
  вкладка отказов и заводится. Причина при любом другом статусе — тоже `400`:
  обращение, вернувшееся в работу, не тащит объяснение, которое перестало быть
  правдой, и репозиторий стирает его при обратном переходе.
- **`DELETE` — уничтожение.** В обращении лежат имя, телефон, адрес,
  комментарий и снимок комнаты: 152-ФЗ требует уметь уничтожить их по
  требованию человека. Удаляются и строка, и файл снимка (`services/leads`),
  порядок — сначала запись, потом файл. Наряд, выросший из обращения, остаётся:
  связь помечена `SetNull`, и удалённая заявка не отменяет работу, о которой
  уже договорились.

**Списки админки приходят страницами** — так же, как клиенты (§12): по 8
записей, `page` за пределами списка прижимается к последней странице, мусор и
ноль — к первой. Список без границы за годы работы кладёт панель вместе с
базой, и это относится и к заявкам, и к отзывам: отклонённые и архивные
отзывы не удаляются (инвариант 7), их список только растёт.

## 9. Календарь работ

Внутренний раздел панели: наружу не отдаётся нигде — это график владельца с
телефонами и адресами клиентов (ADR-080).

| Метод  | Путь                       | Описание                                                                                                                |
| ------ | -------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| POST   | `/api/admin/crm`           | Новое дело: `{ workTypeId, day, time, durationMin?, clientName, clientPhone?, address?, note?, leadId? }` → `201 { … }` |
| PATCH  | `/api/admin/crm/{id}`      | Правка. Любое подмножество полей создания плюс `status`                                                                 |
| DELETE | `/api/admin/crm/{id}`      | Удаление → `204`                                                                                                        |
| GET    | `/api/admin/crm/search?q=` | Поиск по клиенту, адресу и заметке среди дел, нарядов и заявок → `200 { items }`                                        |

🔴 **`workTypeId` — ссылка на справочник видов работ, а не значение перечня**
(ADR-343). Перечня видов дел в контракте нет и быть не может: набор видов
работ правит владелец из настроек, и «Чистка дренажа» появляется в нём без
правки кода и без правки этого документа. Существование записи проверяет
внешний ключ базы; ответ отдаёт вид работ целиком — `workType: { id, code,
title, icon, tone, dayLong }`.

`status`: `planned` · `done` · `cancelled`.

**Дата и время — двумя полями (`day` = `2026-08-23`, `time` = `14:30`), в
московском времени.** Сервер собирает из них момент и хранит в UTC. Пояс
задаёт город работ, а не браузер того, кто открыл панель.

**`day` и `time` переносятся только вместе**: `PATCH` с одним из них — `400`.
Перенести дело на другой день, не сказав на какое время, нельзя.

Пустая правка (`PATCH {}`) — `400`: молча ничего не менять хуже, чем отказать.

**`durationMin`** — длительность дела, час по умолчанию, шаг пятнадцать минут,
как у наряда. Без неё дело нечем нарисовать на часовой сетке: «занято с 11 до
20» — это отрезок, а не точка (ADR-128).

🔴 **`overtimeMin` считает сервер при сохранении и отдаёт только на чтение.**
Это минуты за границей рабочего окна (`schedule`, §5) **на момент записи**.
Принимать его от клиента нельзя, пересчитывать при показе — тоже: владелец
сдвигает окно, а переработка прошлого четверга измениться не имеет права, на
неё смотрят при расчётах с людьми (ADR-138).

Ревалидации ни один из маршрутов не делает: календарь на публичных страницах
не показывается.

### Занятость

Календарь показывает, что запланировано; занятость отвечает на обратный
вопрос — когда человека нет. 🔴 **Занятость личная** и **предупреждает, но не
запрещает** назначить наряд или дело (ADR-115).

| Метод  | Путь                              | Описание                                                                                                             |
| ------ | --------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/admin/blocks?month=2026-08` | Занятость, попадающая в сетку месяца. Обе роли; монтажник получает только свою. Незнакомый месяц — текущий, не `400` |
| POST   | `/api/admin/blocks`               | Новая занятость **на себя** → `201`                                                                                  |
| PATCH  | `/api/admin/blocks/{id}`          | Правка — телом заведения целиком                                                                                     |
| DELETE | `/api/admin/blocks/{id}`          | Снятие → `204`                                                                                                       |

```json
{
  "repeat": "once",
  "day": "2026-08-26",
  "endDay": null,
  "weekday": null,
  "fromMin": null,
  "toMin": null,
  "reason": "Семейные дела"
}
```

- `repeat`: `once` · `weekly`.
- `day` — календарная дата у разовой, `null` у повторяемой; `weekday` — день
  недели по ISO-8601 (1 — понедельник … 7 — воскресенье) у повторяемой, `null`
  у разовой. Нарушение — `400`.
- `endDay` — последний день разовой отлучки **включительно**: отпуск с 1 по 14
  июля — одна запись, а не четырнадцать (ADR-165). `null` — отлучка на один
  день. Раньше `day` — `400`; у повторяемой любое непустое значение — `400`:
  она тянется неделями, и диапазона дат у неё нет. В ответе поле заполнено
  всегда, когда заполнен `day`: пустой конец читается как «в тот же день».
- `fromMin` / `toMin` — минуты от полуночи **по московскому времени**, 0…1439.
  Оба пусты — занят весь день; заполнен один — `400`; `toMin` не больше
  `fromMin` — `400`. Верхняя граница 1439, а не 1440: всё, что вводится через
  `input[type=time]`, обязано в нём же представляться.
- **Владельца записи задаёт сессия**, `userId` в теле игнорируется: занятость
  заводят себе. Владелец чужую видит, но не заводит и не снимает — она про
  чужие семейные дела.
- Правка и снятие — только своей записи: монтажнику чужая отвечает `404` (он
  её не видит), владельцу — `403`.
- Ответ добавляет `id`, `userId`, `userName`.
- `PATCH` принимает тело заведения целиком, а не подмножество: повтор, дата,
  день недели и окно связаны, и частичная правка даёт комбинации, которые
  нечем истолковать.

**Зашитых выходных нет.** Суббота и воскресенье в этой отрасли рабочие, а
отдых приходится на будни; нерабочий день задаёт занятость, заведённая
человеком, а не календарь.

---

🔴 **Поиск не ограничен видимым периодом.** Человек ищет «Первомайская» именно
тогда, когда не помнит, в каком месяце был выезд: выдача, обрезанная по
показанной неделе, отвечала бы «ничего нет» ровно в том случае, ради которого
поиск и открыли.

🔴 **Роль ограничивает выдачу условием запроса, а не фильтром после него.**
Монтажник находит только назначенные ему наряды; дела и обращения его запрос не
выбирает вовсе (CRM §6, ADR-114). Пустой `q` — законный случай: так выглядит
очищенное поле, и ответом служит пустой список, а не `400`.

Находка — одно из трёх, различаются полем `kind`:

```
{ kind: "order", id, number, clientName, address, at }
{ kind: "event", id, workTypeTitle, clientName, address, at }
{ kind: "lead",  id, topic,  clientName, address, at }   // at — момент обращения
```

Номер наряда и тему обращения сервер отдаёт как есть, а подписи к ним живут
там же, где остальные тексты. 🔴 Вид работ — исключение: его название приходит
готовым (`workTypeTitle`), потому что живёт в базе, а не в словаре разметки
(ADR-343), и переводить ключ на стороне интерфейса стало нечем.

## 10. Уведомления

Внутренний контур, наружу не торчит.

```
Notification { channel: "email" | "telegram",
               kind: "lead" | "review" | "to-reminder"
                   | "order-assigned" | "order-changed" | "order-cancelled",
               payload, recipientId, address,
               status: "pending" | "sent" | "failed", attempts, lastError }
```

**Кому уходит сообщение, решает жёсткая таблица «роль × вид события»**
(ADR-119), а не настройка по человеку. Заявка, отзыв и напоминание о ТО —
владельцу; назначение наряда, изменение вводных и отмена — тому, кому наряд
назначен.

- `recipientId = null` — владельцу по общим настройкам; заполнен — человеку
  лично.
- `address` — **снимок** адреса на момент постановки: человек меняет чат и
  почту, а журнал обязан показывать, куда доставляли тогда. У уведомлений
  владельца пуст: его адрес берётся из настроек в момент доставки, иначе
  выключенный канал доставил бы то, что уже лежит в очереди (ADR-058).
- 🔴 **В сообщении монтажнику нет ничего, чего он не видит в панели** (§13):
  ни заметки владельца, ни удержания, а сумма заказа — только при оплате
  наличными.
- Нет ни одного адреса — уведомление не теряется молча: ложится в журнал
  отказом с внятной причиной.

Воркер разбирает очередь с экспоненциальными ретраями. Раздел «Уведомления» в
админке показывает сводку по каналам и разбор того, что не дошло: `lastError`
выводится дословно, как его вернул канал (ADR-061).

**Формат сообщений в Telegram** — как в исходном контракте: заявка текстом (или `sendPhoto` с текстом в `caption`, если приложено фото); новый отзыв — с `inline_keyboard`:

```json
{
  "inline_keyboard": [
    [
      { "text": "✅ Одобрить", "callback_data": "rev:approve:r5" },
      { "text": "🚫 Запретить", "callback_data": "rev:reject:r5" },
      { "text": "📦 Архив", "callback_data": "rev:archive:r5" }
    ]
  ]
}
```

| Метод | Путь                                  | Описание                                                                                                                                                                                             |
| ----- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST  | `/api/telegram/webhook`               | Приём `callback_query` и `message`. Проверяет `X-Telegram-Bot-Api-Secret-Token`, меняет статус тем же кодом, что админка, редактирует сообщение (`editMessageText`), дописывая итог                  |
| POST  | `/api/admin/notifications/{id}/retry` | Вернуть отказ в очередь: `attempts = 0`, `nextTryAt = now`, `lastError = null`. Отправляется тот же `payload`, ничего не создаётся заново. `404`, если уведомления нет или оно не в статусе `failed` |

### Привязка телеграма

Chat ID человек не знает и узнать сам не может. Панель показывает код, человек
присылает его боту, бот запоминает чат.

- Вебхук принимает `/start <код>`, голый код и `/stop` (отвязка).
- Код — HMAC от `SESSION_SECRET` и получасового окна: хранить нечего, таблицы
  нет, подобрать нельзя. Принимаются текущее и прошлое окно.
- Отключённая учётная запись привязку не получает.

| Метод | Путь                                       | Описание                                                                                                             |
| ----- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| PATCH | `/api/admin/notifications/recipients/{id}` | **Только владелец.** `{ email?, unbindTelegram? }` → `{ id, telegram: boolean, email }`. Пустая строка стирает почту |

🔴 **Chat ID не принимается от клиента ни одним маршрутом** и наружу не
отдаётся: в ответах только факт привязки. Прислать его может лишь сам
телеграм.

## 11. Команда и профиль

Раздел появился вместе с ролями (ADR-092). Всё под `/api/admin/staff/*` —
**только для владельца** (перечень `OWNER`, [§17](#17-разграничение-доступа-четыре-роли)):
`403` получает любая другая роль, даже зная адрес. Профиль открыт всем четырём
ролям (`EVERYONE`) и правит всегда своего пользователя, а не того, чей `id`
пришёл в теле.

Объект `Staff`:

```json
{
  "id": "cmt8lwtv0",
  "login": "sokolov",
  "name": "Дмитрий Соколов",
  "phone": "+7 (910) 155-24-68",
  "role": "installer",
  "employment": "self_employed",
  "inn": "710703123450",
  "permissions": [],
  "active": true,
  "createdAt": "2026-04-10T09:00:00.000Z",
  "lastLoginAt": "2026-08-24T06:12:00.000Z"
}
```

🔴 Пароля в ответе нет ни в каком виде — ни хеша, ни исходного.

🔴 **`permissions`** — что владелец открыл этому администратору: тринадцать
разделов и пять опасных действий (ADR-344, [§17.4](#174-разрешения-администратора)).
У остальных ролей набор пуст и ни на что не влияет: доступ владельца, менеджера
и монтажника задан ролью целиком. Приходит только там же, где `inn`, — в
`GET /api/admin/staff` и `GET /api/admin/staff/{id}`; свой профиль его не
отдаёт.

**`employment`** — как оформлены отношения с человеком: `self_employed` ·
`contract` · `staff` · `null`. От него зависит смысл удержания в наряде
(§13, [CRM.md §9](CRM.md)): у самозанятого и подрядчика по ГПХ это уменьшение
вознаграждения, у работника по трудовому договору — внутренняя пометка.

🔴 `null` — «оформление не заведено», а не четвёртое значение словаря.
Умолчания у поля нет и быть не может: подставив значение за владельца,
система решила бы за него, можно ли уменьшать человеку выплату. Пока
оформления нет, наряд исходит из того, что нельзя.

🔴 **`inn`** — ИНН монтажника: 12 цифр или `null`, проверяется контрольными
разрядами (ADR-144). Нужен, чтобы проверить статус самозанятого на дату
выплаты; пустой не мешает завести человека.

Объект `Staff` бывает **в двух формах**, и это проекция под роль, а не
оформление ответа (ADR-114): `inn` приходит только в `GET /api/admin/staff` и
`GET /api/admin/staff/{id}` — оба под проверкой владельца. Свой профиль
(`GET /api/admin/profile`) ИНН не отдаёт вовсе: маршрут доступен обеим ролям, а
ИНН — персональные данные работника ([PROJECT §5.5](PROJECT.md)), и лишняя
дорога к ним не нужна. Ответы на запись ИНН тоже не содержат.

Принимается в `POST /api/admin/staff` и `PATCH /api/admin/staff/{id}`; пустая
строка означает «снять номер».

| Метод  | Путь                                   | Описание                                                                                                                                                                  |
| ------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/admin/staff`                     | Вся команда, владельцы первыми                                                                                                                                            |
| POST   | `/api/admin/staff`                     | Завести монтажника: `{ name, login, phone, employment, inn, password }` → `201` со `Staff`. Логин латиницей, пароль от 8 символов. Занятый логин — `400`                  |
| GET    | `/api/admin/staff/{id}`                | Карточка вместе с `notes`                                                                                                                                                 |
| PATCH  | `/api/admin/staff/{id}`                | Любое подмножество `{ name, login, phone, employment, inn, password, active }`. Роль не меняется. Отключить доступ себе — `403`, сменить оформление себе — `403`          |
| DELETE | `/api/admin/staff/{id}`                | Удалить. Себя и владельца — `403`; выполненные наряды остаются в истории                                                                                                  |
| GET    | `/api/admin/staff/{id}/notes`          | Заметки владельца о монтажнике                                                                                                                                            |
| POST   | `/api/admin/staff/{id}/notes`          | `{ text }` → `201`                                                                                                                                                        |
| DELETE | `/api/admin/staff/{id}/notes/{noteId}` | Удалить заметку                                                                                                                                                           |
| PATCH  | `/api/admin/staff/{id}/access`         | Роль и разрешения: `{ role?, permissions? }` → `Staff`. Только владелец, никаким переключателем не открывается. `role: "owner"` — `400`, учётная запись владельца — `403` |
| GET    | `/api/admin/profile`                   | Свой `Staff`                                                                                                                                                              |
| PATCH  | `/api/admin/profile`                   | `{ name?, phone? }`. Логин, роль и оформление себе не меняют: оформление отдаётся на чтение, попытка его прислать — `403`                                                 |
| POST   | `/api/admin/profile/password`          | `{ current, next }` → `204`. Неверный текущий — `400` с `field: "current"`. Остальные сессии этого человека закрываются                                                   |
| DELETE | `/api/admin/profile/sessions`          | Выйти на всех устройствах, кроме этого: `204`. Тела нет — кого выгонять, сервер знает из сессии. Доступен обеим ролям                                                     |

Отключение доступа и смена пароля владельцем закрывают уже открытые сессии
человека сразу, а не через тридцать дней: cookie в телефоне уволенного
монтажника перестаёт работать тем же запросом.

🔴 **`DELETE /api/admin/profile/sessions` оставляет текущую сессию.** Это
реакция на «кажется, кто-то знает мой пароль» или на забытый в машине телефон:
выкинуть человека из панели за то, что он наводит порядок, значит заставить его
войти заново на том самом устройстве, с которого он это делает. Пароль не
спрашивается — до маршрута доходит только тот, у кого уже есть рабочая сессия,
а действие ничего не разрушает: оно лишь просит войти заново.

## 12. Клиенты

База людей, с которыми компания работает, — внутренний раздел панели, наружу
не отдаётся нигде. Всё **только для владельца** (перечень `OWNER`,
[§17](#17-разграничение-доступа-четыре-роли)): `403` получает любая другая
роль, даже зная адрес (ADR-105). Монтажник получает адрес только со своим
нарядом.

Объект `Client`:

```json
{
  "id": "cmta5ovbh",
  "name": "Ирина Соколова",
  "phone": "+7 (910) 155-24-68",
  "address": "Тула, Первомайская, 12, кв. 4",
  "note": "Домофон не работает",
  "createdAt": "2026-06-14T09:00:00.000Z",
  "leadCount": 2
}
```

Телефон отдаётся в том виде, в каком его ввели. Нормализованный ключ
(`phoneKey` — только цифры, приведённые к коду 7) наружу не выходит: он
служебный и нужен базе для дедупликации и поиска.

| Метод  | Путь                           | Описание                                                                                                        |
| ------ | ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/admin/clients?q=&page=`  | Страница списка: `{ items, total, page, pages }`. По 8 записей, свежие первыми                                  |
| POST   | `/api/admin/clients`           | Завести: `{ name, phone, address, note }` → `201` с `Client`. Занятый телефон — `400` с `field: "phone"`        |
| GET    | `/api/admin/clients/{id}`      | Карточка вместе с `leads` — обращениями этого человека                                                          |
| PATCH  | `/api/admin/clients/{id}`      | Любое подмножество `{ name, phone, address, note }`. Пустая правка — `400`                                      |
| DELETE | `/api/admin/clients/{id}`      | Удалить карточку → `204`. Обращения остаются, их связь с клиентом обнуляется                                    |
| POST   | `/api/admin/leads/{id}/client` | «В клиенты»: `{ client, created }`. `201` — карточку завели, `200` — номер уже был в базе и обращение привязали |

**Поиск `q` — одна строка на три поля:** имя, адрес и телефон. Имя и адрес
сравниваются без учёта регистра, телефон — по цифрам: «910 155», «8910» и
«+7 910» находят одного и того же человека.

**`page` за пределами списка прижимается к последней странице**, мусор и ноль
— к первой. Адрес правят руками и присылают друг другу: отказ вместо списка
там ничего не объясняет.

**Техника клиента** — что у человека стоит. Записи заводятся сами из
выполненного монтажа (CRM.md §3.2); маршрутами добавляют то, что поставили до
этой системы или не мы.

| Метод  | Путь                                           | Описание                                                                   |
| ------ | ---------------------------------------------- | -------------------------------------------------------------------------- |
| POST   | `/api/admin/clients/{id}/units`                | Завести: `{ model, installedAt, warrantyUntil }` → `201` с записью         |
| PATCH  | `/api/admin/clients/{id}/units/{unitId}`       | Любое подмножество тех же полей. Пустая правка — `400`                     |
| DELETE | `/api/admin/clients/{id}/units/{unitId}`       | Удалить запись → `204`. Файл снимка остаётся: он принадлежит наряду        |
| GET    | `/api/admin/clients/{id}/units/{unitId}/photo` | Снимок установки: закрытая отдача по сессии владельца, `private, no-store` |

🔴 **Снимок отдаётся маршрутом, а не адресом файла** (ADR-171, issue #868). В
колонке лежит имя файла из закрытого подкаталога, и в карточке `photo` — это
адрес маршрута выше, ровно как у снимка наряда и фото заявки. `photoMissing`
означает «ссылка есть, а файла на томе нет» и от `photo: null` («снимка нет
вовсе») отличается намеренно: у них разные ответы на экране (issue #690).

🔴 **Дедупликация по телефону обязательна.** Второй карточки на один номер не
бывает: половина работ приходит от постоянных клиентов, и повторное обращение
с того же номера обязано попадать в существующую карточку, а не заводить
второго человека. `POST /api/admin/leads/{id}/client` идемпотентен — повторное
нажатие возвращает ту же карточку и ничего не создаёт.

🔴 **Удаление карточки не удаляет обращения** — в том числе когда карточку
удаляют по требованию субъекта ПДн. У заявки своё согласие на обработку и свой
срок хранения, и стирать её вместе с карточкой значит терять доказательство
согласия по 152-ФЗ.

## 13. Заказы (наряды)

Внутренний раздел панели, наружу не отдаётся нигде. Наряд — работа с деньгами,
датой и исполнителем; дело в календаре остаётся напоминанием без денег
(ADR-093).

🔴 **Видимость полей зависит от роли** — на сервере, а не скрытием кнопок
(CRM.md §6). Владелец получает наряд целиком. Монтажник:

- видит только наряды, где `installerId` — он сам; чужой `id` даёт `404`,
  а не `403`: существование чужого наряда его не касается;
- не получает `ownerNote`, `deductionSum`, `deductionReason` и `margin` — этих
  ключей в ответе нет вовсе, а не `null`;
- получает `price` **только** при `payment: "cash_to_installer"` — там сумму
  нужно принять от клиента; в остальных случаях ключа нет;
- `installerFee` получает всегда — это его деньги;
- меняет статус только на `in_progress` и `done`, остальные переходы — `403`.

Объект `Order`:

```json
{
  "id": "cmta7q1x0",
  "number": 1059,
  "workType": {
    "id": "wt_install",
    "code": "install",
    "title": "Монтаж",
    "icon": "wrench",
    "tone": "ok",
    "dayLong": false
  },
  "status": "assigned",
  "client": { "id": "cmta5ovbh", "name": "Ирина Соколова", "phone": "+7 (910) 155-24-68" },
  "installer": { "id": "u2", "name": "Дмитрий Соколов" },
  "at": "2026-08-28T08:00:00.000Z",
  "durationMin": 180,
  "address": "Тула, Первомайская, 12, кв. 4",
  "intercom": "24К",
  "phone2": null,
  "floor": 5,
  "heightWorks": true,
  "payment": "company",
  "price": 38500,
  "installerFee": 9000,
  "deductionSum": 0,
  "deductionReason": null,
  "margin": { "known": true, "materials": 4200, "value": 25300 },
  "comment": "Домофон не работает, звонить на телефон",
  "ownerNote": "Клиент постоянный, скидку не даём",
  "leadId": null,
  "units": [
    {
      "id": "cmta7q2y1",
      "equip": "conditioner",
      "model": "Сплит-система 09",
      "source": "ours",
      "trassaM": 4,
      "diameter": "1/4–3/8",
      "shtrob": true,
      "sort": 0
    }
  ],
  "createdAt": "2026-08-26T14:00:00.000Z"
}
```

🔴 **`overtimeMin` считает сервер при сохранении и отдаёт только на чтение** —
минуты за границей рабочего окна (`schedule`, §5) на момент записи. Приходит
обеим ролям наравне с `installerFee`: это часы человека, а не деньги компании.
Принимать его от клиента нельзя, пересчитывать при показе — тоже (ADR-138).

🔴 **Вид работ приходит записью справочника, а не ключом перечисления**
(ADR-343). Перечисление `OrderType` снято со схемы: набор видов работ —
данные, которыми владелец управляет из настроек, и «Чистка дренажа»
заводится без разработчика. При записи (`POST`, `PATCH`) наряд принимает
`workTypeId` — идентификатор записи справочника; в ответе приезжает вся
метка: подпись, значок и краска. Отключённый вид работ не предлагается, но у
прежних нарядов остаётся; удалить вид, на который ссылаются записи, нельзя —
только отключить (`409`).

`tone`: `accent` · `info` · `ok` · `warn` · `sale` · `error` · `neutral`.
`status`: `new` · `assigned` · `in_progress` · `done` · `cancelled`.
`payment`: `company` · `cash_to_installer`.
`equip`: `conditioner` · `fridge` · `compressor` · `ventilation` · `heat_curtain` · `other`.
`source`: `ours` (наше, продажа с монтажом) · `client` (клиента, только работы).

| Метод  | Путь                                      | Описание                                                                          |
| ------ | ----------------------------------------- | --------------------------------------------------------------------------------- |
| GET    | `/api/admin/orders?q=&tab=&period=&page=` | Страница списка: `{ items, total, page, pages }`. По 8 записей, ближайшие первыми |
| POST   | `/api/admin/orders`                       | Завести наряд → `201`. Только владелец. Номер выдаёт сервер                       |
| GET    | `/api/admin/orders/{id}`                  | Карточка. Монтажнику — только своя и без закрытых полей                           |
| PATCH  | `/api/admin/orders/{id}`                  | Любое подмножество полей. Монтажнику доступны `status`, и только два значения     |
| DELETE | `/api/admin/orders/{id}`                  | Удалить → `204`. Только владелец                                                  |

**Параметры списка.** `q` — номер, имя клиента, адрес или модель в позициях.
`tab`: `active` (назначен и в работе) · `new` · `history` (выполненные) ·
`cancelled` · `all`; без параметра — `active`. `period`: `all` · `month` ·
`prev`. Разбивка — общая, `shared/lib/paging`.

**Дата и время — двумя полями** (`day` = `2026-08-28`, `time` = `11:00`), в
московском времени, как у дела календаря (§9). Сервер собирает момент и хранит
в UTC. `day` и `time` переносятся только вместе: `PATCH` с одним из них —
`400`.

🔴 **Номер сквозной и без дыр.** Счётчик живёт в `Setting` под ключом
`orderSeq` и инкрементируется **в той же транзакции**, что и создание наряда.
Автоинкремент Postgres не годится: он оставляет дыру на каждой откатанной
транзакции, а владелец диктует номер клиенту по телефону.

🔴 **Маржа вычисляется, а не хранится** (ADR-310, [CRM §8.2](CRM.md)):
`price − installerFee − материалы по движениям + deductionSum`. Материалы —
списания в наряд минус возвраты, каждое по снимку закупочной цены на момент
движения (§14).

Ключ владельческий и **необязательный**: там, где маржу не спрашивали, её не
считали — собирать движения склада ради списка, который её не показывает,
означало бы лишний запрос на каждую отрисовку. Приходит на карточке наряда и в
списке; в наряде дня монтажника её нет.

🔴 **Маржа либо посчитана целиком, либо не посчитана вовсе** — размеченное
объединение, а не число с флагом:

```json
{ "known": true, "materials": 4200, "value": 25300 }
{ "known": false, "unpriced": 2 }
```

`unpriced` — сколько движений наряда ушло со склада без заведённой закупочной
цены. Считать их по нулю значило бы занизить расход и завысить маржу, то есть
соврать в ту сторону, ради которой поле и заводится; пропустить возврат —
наоборот. Поэтому неизвестной становится вся маржа наряда, а панель
показывает прочерк с объяснением, а не число.

**Итог периода** на вкладке «История» — `{ closed, revenue, margin,
marginSkipped }`, только владельцу. `marginSkipped` — сколько нарядов не вошло
в `margin`: итог, умолчавший о пропуске, читается как полный.

🔴 **Удержание — не штраф.** `deductionSum` при ненулевом значении требует
`deductionReason`, иначе `400` с `field: "deductionReason"`. Подпись в
интерфейсе — «Удержание», и что она означает, зависит от `employment` того,
кому наряд назначен (§11): у самозанятого и подрядчика по ГПХ это уменьшение
вознаграждения, у работника по трудовому договору — внутренняя пометка, без
автоматического вычета из выплаты. Разбор — [CRM.md §9](CRM.md).

**Позиции оборудования** приходят и уходят вместе с нарядом, полем `units`.
Отдельных маршрутов у позиции нет: список позиций правится целиком — так же,
как строки прайса (§4). Пустой список допустим: наряд заводят по звонку, а что
именно везти, выясняется на замере.

Ревалидации ни один из маршрутов не делает: наряды на публичных страницах не
показываются.

## 14. Склад

Внутренний раздел панели, наружу не отдаётся. Требования — [CRM §11](CRM.md),
решения — ADR-111 и ADR-134.

🔴 **Остаток — сумма движений, а не поле.** Записать его напрямую нельзя ни
одним маршрутом: правка руками существует, но как движение `count`
(инвентаризация) с обязательным основанием.

🔴 **Видимость зависит от роли** — на сервере, а не скрытием кнопок. Владелец
видит все зоны и пороги заказа. Монтажник:

- получает только зоны-машины, где `userId` — он сам; остальные в ответе не
  появляются вовсе;
- не получает `minQty`, `low` и `lowCount` — этих ключей в ответе нет, а не
  `null`: порог заказа говорит о закупочных привычках владельца;
- не получает `purchasePrice` — по той же причине и тем же способом:
  закупочная цена коммерческая тайна, наружу не уходит никогда и в ответах
  маршрутов монтажника её нет (ADR-310);
- из движений может провести только `consume` и `return` по **своему** наряду
  и **из своей** машины; всё остальное — `403`.

Единицы (`unit`): `piece` · `meter` · `kilogram` · `liter` · `pair` · `pack` ·
`coil` · `roll` · `cylinder`. Набор задан кодом, номенклатура — справочник в
базе (инвариант 8).

Зоны (`kind`): `warehouse` (гараж) · `van` (машина монтажника, всегда с
`userId`). Зоны «выдано под наряд» нет: до списания материал лежит в машине, а
расход наряда считается по движениям с этим нарядом (ADR-134).

Виды движения (`kind`): `income` приход · `transfer` перемещение между зонами
· `consume` списание в наряд · `return` возврат с объекта · `count`
инвентаризация.

Остатки — объект `StockOverview`:

```json
{
  "zones": [
    {
      "id": "z1",
      "kind": "warehouse",
      "name": "Гараж",
      "userId": null,
      "userName": null,
      "sort": 0,
      "archived": false
    },
    {
      "id": "z2",
      "kind": "van",
      "name": "Газель",
      "userId": "u2",
      "userName": "Дмитрий Соколов",
      "sort": 1,
      "archived": false
    }
  ],
  "items": [
    {
      "id": "s1",
      "name": "Труба медная 1/4″",
      "group": "Медная труба",
      "unit": "meter",
      "note": null,
      "archived": false,
      "product": null,
```

`byZone` содержит все видимые зоны, включая нулевые: пустая колонка — это

**Тело `POST /api/admin/stock/movements`** зависит от вида:

| `kind`     | Обязательно                                       | Необязательно       |
| ---------- | ------------------------------------------------- | ------------------- |
| `income`   | `itemId`, `qty`, `toZoneId`                       | `serials`, `reason` |
| `transfer` | `itemId`, `qty`, `fromZoneId`, `toZoneId`         | `reason`            |
| `consume`  | `itemId`, `qty`, `fromZoneId`, `orderId`          | `serials`           |
| `return`   | `itemId`, `qty`, `orderId`, `toZoneId`            | `reason`            |
| `count`    | `itemId`, `qty` (со знаком), `toZoneId`, `reason` | —                   |

`qty` принимается строкой или числом, «1,5» и «12 000» разбираются: так пишут
по-русски. Точность — три знака после запятой, больше склад не хранит.

🔴 **Уход в минус не запрещается, а помечается.** Запрет означал бы, что
монтажник, у которого труба кончилась раньше, чем в системе, впишет неправду,
лишь бы закрыть наряд. Отрицательный остаток — сигнал «пора провести
инвентаризацию», и он показывается как предупреждение, а не как отказ.

🔴 **Закупочная цена живёт на позиции** (`purchasePrice`, целые рубли) и
принимается маршрутами `POST`/`PATCH /api/admin/stock/items`. Партий и FIFO
нет — цена одна на позицию (ADR-310, [CRM §11.7](CRM.md)).

`null` означает «цена не заведена» и **не равно нулю**: ноль — это настоящая
цена материала, доставшегося даром, а `null` оставляет наряд без маржи. Из-за
этого поле необязательное и без умолчания: ноль по умолчанию занижал бы расход
и завышал маржу.

🔴 **Движение хранит снимок цены на свой момент** — цену позиции на день
списания. Наружу снимок не отдаётся: в объекте `StockMovement` его нет, он
нужен только расчёту маржи наряда (§13). Отмена списания возвратом переносит
цену отменяемого движения, а не берёт текущую: иначе переоценка между
списанием и отменой оставила бы в расходе наряда осадок из ничего.

**Порог «пора заказывать»** живёт на позиции (`minQty`, ноль — не следим).
Позиция, опустившаяся ниже порога, попадает в `low` и уходит владельцу
уведомлением `kind: "stock-low"` по общей очереди (§10). Уведомление
срабатывает **на переходе** через порог, а не на каждом движении: иначе в день
монтажа владелец получит десять одинаковых сообщений и перестанет их читать.

🔴 **Отмена списания — это возврат, а не удаление записи.** Ответ `201`, а не
`204`: появилось новое движение, а не исчезло старое. Возврат ссылается на
отменённое списание, ссылка уникальна — отменить одно списание дважды база не
даст.

🔴 **Архив не прячет остаток.** Позиция и зона уходят в архив только пустыми:
иначе остаток исчезает из итогов, не оставив ни одного движения, — ровно тот
случай, ради которого склад и заводится. `DELETE` на уже архивной записи —
тихий успех.

## 16. Ошибки

```json
{
  "error": {
    "code": "validation_error",
    "message": "Поле rating обязательно (1–5)",
    "field": "rating"
  }
}
```

`400` валидация · `401` нет сессии · `403` нет прав · `404` нет объекта · `409` карточку изменили за это время · `413` файл слишком большой · `429` rate-limit · `500` прочее.

🔴 **`409` отличается от `400` тем, что тело запроса верное.** Изменилось состояние на сервере: пока карточку правили, её сохранил кто-то другой. Клиент присылает `updatedAt`, полученный при загрузке, сервер пишет только при совпадении версии (BUGS §1864). Поле необязательное: точечные действия вроде смены статуса кнопкой шлют одно поле и затирать нечем — они работают как раньше.

Текст `message` показывается пользователю — он на русском и объясняет, что делать. Технические детали уходят в лог, а не в ответ.

## 17. Разграничение доступа: четыре роли

Ролей четыре — `owner`, `admin`, `manager`, `installer` (ADR-344). Матрица данных, то есть «кто что видит внутри уже открытого раздела», живёт в [CRM §6](CRM.md); здесь — матрица маршрутов: **какой роли какой адрес отвечает, а какой отказывает**.

🔴 **Разграничение проверяется на сервере в каждом обработчике**, а не скрытием кнопок. Скрытый пункт меню — подсказка интерфейса; ответ `403` — защита. Адреса панели человек знает: он в ней работает.

🔴 **Перечень ролей закрытый, а не «все, кроме такой-то».** Роль, которую в перечне не назвали, получает `403`. Вычитание открывало бы каждую новую роль по умолчанию: именно так `withAdmin` — «любой вошедший» — молча открыл двадцать шесть методов администратору и менеджеру в тот день, когда роли завели.

### 17.1. Четыре перечня

Перечней ровно четыре на всю панель, и записаны они один раз — `apps/web/src/entities/staff/access.ts`. У маршрута и у страницы стоит **имя перечня**, а не выписанный список ролей: список по месту — это второй источник правды, и опасен он тем, что сегодня совпадает.

### 17.4. Что ещё не открыто и почему

Менеджер по ADR-344 ведёт клиента до назначенного наряда и видит занятость всей команды. Сегодня ему открыты «Заявки» — раздел целиком, вместе с чтением очереди, сменой статуса и снимком к обращению, — и профиль; календарь, заказы и клиенты закрыты. Заведение клиента и наряда **из** обращения тоже закрыто: эти два действия открывают разделы, которых у менеджера пока нет. Причина не в правах, а в ответах: наряд везёт вознаграждение исполнителя и удержания, а сужение выборки в репозитории (`viewerWhere`) знает только монтажника — менеджеру оно отдало бы владельческую проекцию целиком. Разделы открываются той же фазой, что вырезает деньги из ответов (фаза 3 плана «Роли и права»).

### 17.4. Разрешения администратора

Переключатели владельца действуют с фазы 4 (ADR-344, issue #781–#785). Разрешений восемнадцать: тринадцать разделов панели (`overview` `crm` `orders` `leads` `clients` `team` `stock` `catalog` `knowledge` `reviews` `company` `prices` `notifications`) и пять опасных действий (`data_delete` `money` `company_settings` `people` `activity_purge`).

🔴 **У администратора перечень ролей не спрашивается вовсе.** ADR-344 даёт ему права владельца **под переключателями владельца**, и отвечает за него центральная карта «маршрут → требуемое разрешение» — `apps/web/src/server/permissions.ts`. Спрашивать заодно перечень значило бы, что выданное разрешение не работает, пока роль не вписали в `access.ts`, то есть переключатель ничего не решает. Три остальные роли карта не касается: их доступ задан перечнями целиком.

🔴 **Карта закрытая.** Адрес, которого в ней нет, администратору не открывается — и контрактные проверки (`roles.contract.test.ts`, `permissions.pages.test.ts`) краснеют на маршруте или странице без строки. Правило по умолчанию — «раздел по первому сегменту адреса»; исключения — опасные действия и владельческие адреса — выписаны поимённо.

🔴 **Опасное действие требуется сверх раздела.** Удалить обращение может тот, кому открыты и «Заявки», и `data_delete`. Само по себе `data_delete` не открывает ничего.

🔴 **Журнал событий открывается администратору только чисткой.** Читать и комментировать записи — владельческое (🔒): журнал отвечает на вопрос «кто это сделал», и администратор в нём тоже записан. `POST /api/admin/activity/cleanup` — единственный его адрес под переключателем, и переключатель этот опасный: `activity_purge` (ADR-345). Разрешения на раздел рядом нет — раздела «Журнал» среди тринадцати не существует, поэтому обладатель «Чистки журнала» чистит то, чего не видит.

🔴 **Раздачу прав не открывает ни один переключатель** (🔒 в таблице §17.2). `PATCH /api/admin/staff/{id}/access` — владельческий адрес: администратор, правящий права, означает ровно то, что переключатели владельца — договорённость. Ручная ревалидация (`POST /api/admin/revalidate`) владельческая по той же схеме: она принимает произвольный список адресов сайта, а не адреса одного раздела.

🔴 **Снятый переключатель действует немедленно.** Набор читается из базы вместе с сессией на каждый запрос, кеша у него нет: раздел закрывается тем же запросом, без повторного входа. Правка прав при этом сессий не закрывает — «убрал раздел» не должно значить «выгнал человека».

🔴 **Владелец в системе один.** `role: "owner"` схема не принимает (`400`), а учётную запись владельца эта ручка не правит вовсе (`403`): понизить единственного владельца значит запереть панель снаружи. Смена роли на неадминистраторскую гасит набор — сохранённые разрешения у менеджера были бы настройкой, которая не работает.

### 17.5. Коды ответа

| Что случилось                       | Ответ                                                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Сессии нет или она погашена         | `401` `unauthorized`                                                                                                                                               |
| Роль не в перечне маршрута          | `403` `forbidden`, текст «Этот раздел панели вашей учётной записи не открыт»                                                                                       |
| У администратора снят переключатель | `403` `forbidden`, **тот же текст**: разница между «роль не та» и «переключатель снят» человеку ничего не даёт, а постороннему рассказывает, что раздел существует |
| Запрос пришёл с чужого сайта        | `403` `forbidden`, текст про чужой сайт                                                                                                                            |
| Роль в перечне, но запись чужая     | `404` — чужой наряд для монтажника не существует, а не «закрыт»                                                                                                    |

🔴 **Текст отказа безличный, а не «доступен только владельцу».** Ролей четыре, и прежняя формулировка врала бы менеджеру: закрытый ему раздел бывает открыт администратору.

## 18. Журнал событий

Кто и что сделал в панели — ADR-345, [план](plan-activity-log.md). Раздел
владельческий целиком; отдельные разрешения «Журнал» и «Чистка» приходят с
механизмом прав ADR-344 (issue #823).

| Метод | Путь                          | Описание                                                                      |
| ----- | ----------------------------- | ----------------------------------------------------------------------------- |
| GET   | `/api/admin/activity`         | Страница журнала: `{ items, total, page, pages }`. Отбор — параметрами адреса |
| PATCH | `/api/admin/activity/{id}`    | Пометка человека у записи: `{ note }`. Пустая строка стирает пометку          |
| POST  | `/api/admin/activity/cleanup` | Чистка за период: `{ from, to }` → `{ removed }`. Обе границы обязательны     |

**Отбор списка** — `actor` (учётная запись автора), `role`, `section` (раздел
панели: левая часть ключа действия), `entity`, `from`, `to` (календарные дни
включительно, границы считаются по московской полуночи), `page`. Мусор в любом
условии снимает это условие, а не отвечает ошибкой: адрес правят руками и
присылают друг другу. Повторённый параметр (`?actor=a&actor=b`) — тоже мусор:
условие снимается целиком, первое значение не берётся, и ручка ведёт себя тут
так же, как сама страница.

`role` отбирает по **сегодняшней** роли автора: своей копии роли у события
нет. Роль разворачивается в перечень учётных записей до запроса к журналу —
условие тогда ложится на индекс `[actorId, createdAt]` самого журнала, а не
уводит запрос в чужую таблицу. Событие без автора (`system`) в отбор по роли
не попадает никогда.

🔴 **Список отдаётся только страницами.** Параметра «сколько» нет ни в адресе,
ни в репозитории: событие пишется на каждое изменение — это тысячи строк в
месяц, и один ответ «отдай всё» кладёт панель вместе с базой (issue #816).

🔴 **Правится у записи одно поле — пометка.** Тело `PATCH` с `actorId`,
`createdAt`, `changes`, `action`, `entity`, `entityId`, `id` или
`noteUpdatedAt` отвечает `403`, а не `400`: `400` читается как «поправьте тело
и повторите», а повторять здесь нечего — этого нельзя. Журнал, в котором
переписывается автор, доказывает ровно столько же, сколько пустой (инвариант
7, issue #820, #824).

🔴 **Построчного удаления нет.** Метода `DELETE` у записи не существует — не
«скрыт» и не «только владельцу». Убрать из журнала одну неудобную строку
нельзя ничем; есть только чистка за период, и она оставляет свой след
(issue #821).

🔴 **След чистки переживает чистку.** Событие `activity.cleanup` пишется в той
же транзакции, что и удаление, и исключается **условием запроса**, а не
порядком вызовов: повторная чистка того же периода след первой не уносит. Оно
записывается видом «безопасность» — срок хранения 36 месяцев против 12
(issue #822).

🔴 **Ручная чистка не касается событий вида «безопасность» вовсе** — ни входа,
ни отказа входа, ни смены роли. Срок хранения у них втрое длиннее не по
случайности, и кнопка в панели не должна быть сильнее того, что решено про
хранение: журнал, из которого владелец убирает отказы входа, перестаёт
защищать в ту сторону, ради которой заведён. Свои сроки применяет уборка по
расписанию (фаза 6). Условие по имени действия при этом остаётся отдельным:
выживание следа чистки не должно зависеть от решения о сроках хранения.
