# Plan: Журнал событий панели

**PRD:** [docs/prd-activity-log.md](prd-activity-log.md)
**Решение:** [ADR-342](DECISIONS.md)
**Дата:** 2026-09-08

## Фазы реализации

### Фаза 1: Событие пишется и читается

**Цель:** Сквозной минимум — одно действие оставляет след, и след виден.
**Затрагивает:** database / backend / frontend
**Задачи:**

- [ ] Миграция: таблица событий — кто, когда, действие, сущность и её `id`,
      состав изменений; индексы по человеку, сущности и периоду
- [ ] Сервис записи события: пишет в одной транзакции с изменением, `id` и
      `createdAt` неизменяемы
- [ ] Модерация отзывов записывает события: снятие, публикация, отклонение
- [ ] Простой список событий на закрытой странице панели
- [ ] Тесты: событие пишется вместе с изменением, откат транзакции не
      оставляет ни того, ни другого

**Когда готова:** снятие отзыва с публикации видно в списке событий с автором и
временем.

### Фаза 2: События всей панели

**Цель:** Ни одно изменение в панели не проходит без следа.
**Затрагивает:** backend
**Задачи:**

- [ ] События заводятся во всех разделах: клиенты, наряды, каталог, склад,
      статьи, цены, настройки, сотрудники
- [ ] Состав изменений «было → стало» хранится отдельным полем
- [ ] Персональные данные в событие не копируются: событие ссылается на
      сущность
- [ ] Контрактный тест: перечень изменяющих ручек сверяется с деревом
      маршрутов, ручка без события красит проверку
- [ ] Тест содержимого: в строке события нет телефона, имени и адреса

**Когда готова:** контрактный тест перечисляет все изменяющие ручки, у каждой
есть событие.

### Фаза 3: События безопасности и сайта

**Цель:** Журнал отвечает не только «кто менял», но и «кто входил».
**Затрагивает:** backend
**Задачи:**

- [ ] События входа, отказа входа, смены роли и разрешений
- [ ] События сайта: пришла заявка, пришёл отзыв, уведомление не доставлено
- [ ] Пометка вида события: обычное или безопасности — от неё зависит срок
- [ ] Тесты: неудачный вход пишет событие; заявка пишет событие и по-прежнему
      получает `201` независимо от внешних сервисов

**Когда готова:** три неудачных входа подряд видны в журнале, заявка с сайта
оставляет событие.

### Фаза 4: Раздел журнала

**Цель:** Журнал становится рабочим экраном, а не таблицей на 50 000 строк.
**Затрагивает:** frontend
**Задачи:**

- [ ] Раздел панели: отбор по человеку, роли, разделу, сущности и периоду
- [ ] Разбивка на страницы; список без неё не открывается
- [ ] Лента событий в карточке клиента, наряда, модели, статьи, сотрудника
- [ ] Истории Storybook: список, пусто, отбор без результата, ошибка
- [ ] Просмотр по скиллу `ui-ux-pro-max` на 1440, 768, 390 в обеих темах

**Когда готова:** владелец находит в журнале, что менеджер делал в среду, за
три нажатия; замер запроса на 50 000 событий приложен.

### Фаза 5: Пометка, чистка и доступ

**Цель:** Владелец распоряжается журналом, не переписывая его.
**Затрагивает:** backend / frontend
**Задачи:**

- [ ] Пометка человека у записи — единственное правимое поле, с `updatedAt`
- [ ] Чистка за период; построчного удаления нет в API
- [ ] Чистка пишет своё событие, и оно не удаляется вместе с периодом
- [ ] Доступ по ролям и разрешениям ADR-341: журнал и чистка — отдельные
      разрешения
- [ ] Тесты: попытка изменить автора, время и состав изменений — 403; после
      чистки запись о ней на месте

**Когда готова:** владелец чистит журнал за год, след чистки остаётся,
администратор без разрешения получает 403.

### Фаза 6: Уборка по расписанию

**Цель:** Журнал не растёт бесконечно и не требует кнопки.
**Затрагивает:** backend
**Задачи:**

- [ ] Работа воркера: обычные события старше 12 месяцев уходят, события
      безопасности живут 36
- [ ] Уборка пишет своё событие
- [ ] Тесты на границах срока: 11 месяцев остаётся, 13 уходит, событие
      безопасности того же возраста остаётся
- [ ] Замер: время уборки на журнале в 100 000 строк приложен к задаче

**Когда готова:** уборка проходит сама, границы сроков проверены тестом.
