## ADR-001 — Всё в одном приложении Next.js · 2026-08-20

**Контекст.** Нужен сайт + админка + API. Нагрузка — сотни визитов в сутки в пик сезона.

**Решение.** Один Next.js 15 (App Router): публичные страницы, админка и API-маршруты. Отдельного бэкенда нет.

**Следствия.** Один деплой, нет CORS, типы не дублируются. API при этом соблюдает контракт буквально — вынести бэкенд в отдельный сервис можно без правок фронта.

**Отвергнуто.** Next + NestJS — удвоение инфраструктуры без выгоды на этом масштабе. Headless CMS (Strapi, Directus) — админка из дизайна не ложится на чужой UI, а она часть продукта.

→ [TECH_DECISIONS §1](TECH_DECISIONS.md)

## ADR-002 — Кластер страниц вместо одного лендинга · 2026-08-20

**Контекст.** Прототип — один длинный лендинг со всеми секциями на одном URL.

**Решение.** Разбиваем на кластер: `/`, `/katalog`, `/katalog/[slug]`, `/ustanovka-kondicionerov`, `/ceny`, `/remont-i-obsluzhivanie`, `/otzyvy`, `/kontakty`, `/baza-znaniy/*`. Гео-страницы по районам — вторая волна.

**Следствия.** Объём работ примерно +40%. Взамен каждый интент получает свою посадочную страницу вместо конкуренции одним URL за все запросы сразу.

**Отвергнуто.** Оставить лендинг как есть — одна позиция по одному запросу, остальное отдаём конкурентам.

→ [SEO §1](SEO.md)

## ADR-003 — CSS Modules · 2026-08-20

**Контекст.** Прототип целиком на инлайн-стилях с CSS-переменными.

**Решение.** CSS Modules + глобальные токены в `tokens.css`. Тёмная тема — переопределением переменных на `html[data-theme="dark"]`.

**Следствия.** Ни одной лишней зависимости, стили изолированы по компонентам, тема живёт в одном файле.

**Отвергнуто.** Tailwind — рабочий вариант, выбран не был по решению заказчика.

## ADR-004 — VPS в РФ, PostgreSQL, Docker · 2026-08-20

**Контекст.** Формы собирают имя и телефон — это персональные данные.

**Решение.** VPS у российского провайдера, Docker Compose: Caddy + Next + Postgres + воркер уведомлений.

**Следствия.** 152-ФЗ соблюдён по локализации. Vercel и любой зарубежный хостинг для основной БД исключены.

→ [TECH_DECISIONS §3](TECH_DECISIONS.md)

## ADR-005 — SSG + ISR с точечной ревалидацией · 2026-08-20

**Контекст.** Данные меняются редко, но владелец не должен ждать час, чтобы увидеть новую цену.

**Решение.** Статическая генерация с ревалидацией по времени + `revalidatePath` из админки после каждого сохранения.

**Следствия.** Робот и человек получают готовый HTML без похода в БД; правка видна за секунду.

**Отвергнуто.** Чистый SSR — лишняя нагрузка на данных, которые меняются раз в неделю. Клиентский рендер — нарушает инвариант 1.

→ [TECH_DECISIONS §2](TECH_DECISIONS.md)

## ADR-006 — Заявка пишется в БД до любого уведомления · 2026-08-20

**Контекст.** В прототипе заявка уходила прямо в Telegram из браузера. Сбой отправки = клиент потерян навсегда.

**Решение.** `POST /api/leads`: валидация → запись `Lead` → постановка `Notification` в очередь → `201`. Ответ клиенту не ждёт внешние сервисы. Воркер разбирает очередь с ретраями.

**Следствия.** Заявка не может потеряться. Ошибки доставки видны в админке.

→ [TECH_DECISIONS §5](TECH_DECISIONS.md) · инвариант 2 в [CLAUDE.md](CLAUDE.md)

## ADR-007 — Email основной, Telegram со сменным транспортом · 2026-08-20

**Контекст.** Доступность `api.telegram.org` с российского дата-центра не гарантирована и не проверяема заранее. Заказчик указал, что Cloudflare из РФ тоже ненадёжен.

**Решение.** Email через российский SMTP — основной надёжный канал. Telegram — канал удобства с транспортом `direct | proxy | off`, выбираемым переменной окружения после замера с самого VPS. План Б — WireGuard-туннель до зарубежного VPS с маршрутизацией только подсетей Telegram.

**Следствия.** Работоспособность уведомлений не зависит от геополитики.

**Отвергнуто.** Реле на Cloudflare Workers — по требованию заказчика. Проверки доступности с локальной машины — бессмысленны, она под VPN.

→ [TECH_DECISIONS §6](TECH_DECISIONS.md) · [DEPLOY §6](DEPLOY.md)

## ADR-008 — Cookie-сессия вместо JWT · 2026-08-20

**Контекст.** Исходный контракт предполагал JWT в `Authorization: Bearer`.

**Решение.** httpOnly + Secure + SameSite=Lax cookie, пароль через Argon2id.

**Следствия.** Токен недоступен для XSS. Контракт в этой части сознательно расходится с прототипом.

→ [TECH_DECISIONS §8](TECH_DECISIONS.md) · [API — отличия](API.md)

## ADR-009 — Ни одного факта о компании в коде · 2026-08-20

**Контекст.** В прототипе всё выдумано: домен `tulaklimat.ru`, телефон `+7 (4872) 00-00-00`, «ул. Примерная, 1», ИНН, ОГРН, имя ИП, даже название бренда «ТулаКлимат». При этом Яндекс сверяет NAP-данные сайта с карточкой в Яндекс.Бизнесе, и расхождения бьют по локальному ранжированию.

**Решение.** Все данные о компании — записи в `Setting` и раздел «Компания» в админке: название и слоган, телефоны, мессенджеры, адрес по частям, координаты для JSON-LD, часы работы, регион обслуживания, реквизиты, тексты гарантии и оплаты, соцсети, дефолтная OG-картинка.

**Следствия.** Плейсхолдеры перестают быть блокером разработки: код пишется сразу, владелец заполняет реальные значения через админку без выкладки. JSON-LD, футер, шапка и политика собираются из одного источника — расхождения NAP становятся невозможными технически.

**Исключение.** Канонический домен остаётся в `SITE_URL` (ENV): смена домена — инфраструктурное событие с редиректами и переиндексацией, а не правка поля в форме.

→ [PROJECT §3, §4](PROJECT.md) · [TECH_DECISIONS §15](TECH_DECISIONS.md) · инвариант 8 в [CLAUDE.md](CLAUDE.md)

## ADR-010 — Каталог полностью управляется из админки · 2026-08-20

**Контекст.** В сидах четыре обобщённые модели («Сплит-система 09») без фотографий. Настоящих товаров нет, и появятся они у владельца, а не у разработчика.

**Решение.** Всё, что нужно товару, редактируется в админке: название, бренд, модель производителя, слаг, класс мощности, площадь, цена, скидка, фото (несколько, с выбором главного), внешняя ссылка, произвольные характеристики, метки, видимость, порядок, свои `title`/`description`.

**Следствия.** Владелец заводит реальный каталог сам и меняет его в сезон без разработчика. Разработка не ждёт контент.

🔴 Никакого фиксированного набора характеристик в коде и в схеме БД — только список пар «название → значение».

→ [PROJECT §2.1, §3](PROJECT.md)

## ADR-011 — Скидки: цена продажи, а не процент · 2026-08-20

**Контекст.** Нужен маркетинговый инструмент для сезонных распродаж и межсезонья.

**Решение.** У товара поля `salePrice` (конечная цена со скидкой), `saleFrom`/`saleTo` (период) и необязательная `saleLabel`. Процент считается автоматически и рисуется плашкой. Пустой `salePrice` = скидки нет.

**Почему так.** Владелец мыслит конечной ценой, и «красивые» 34 900 ₽ важнее математически ровного процента. Период действия нужен, чтобы скидка снималась сама и чтобы отдавать `priceValidUntil` в разметке `Offer`.

🔴 **Ограничение честности.** Перечёркнутая цена — только та, по которой товар действительно продавался. Рисованная «старая цена» — это введение в заблуждение по ЗоЗПП и ФЗ «О рекламе», и Яндекс за такое тоже наказывает.

→ [PROJECT §2.8](PROJECT.md) · [SEO §4](SEO.md) · [DESIGN_BRIEF §10](DESIGN_BRIEF.md)

## ADR-012 — Отзывы стартуют с пустого раздела · 2026-08-20

**Контекст.** В сидах пять выдуманных отзывов с именами и районами.

**Решение.** Отзывы не сидируем. Раздел стартует пустым: только форма и приглашение оставить отзыв. Публикуются исключительно настоящие, прошедшие модерацию.

**Следствия.** Разметка `Review` появляется вместе с первым реальным отзывом, `AggregateRating` — когда наберётся статистика.

**Почему.** Вымышленные отзывы в микроразметке — прямой путь под санкции Яндекса и претензии по ФЗ «О рекламе». Выигрыш в доверии на старте не стоит риска для домена.

→ инвариант 10 и красные линии в [CLAUDE.md](CLAUDE.md)

## ADR-013 — Раздел «Заявки» в админке · 2026-08-20

**Контекст.** В исходном дизайне раздела нет — заявки жили только в Telegram.

**Решение.** Добавляем: список с фильтром по статусу, карточка со всеми полями и фото места установки, смена статуса, комментарий менеджера.

## ADR-014 — Свой мини-формат разметки статей · 2026-08-20

**Контекст.** Статьи Базы знаний пишет владелец, не разработчик.

**Решение.** Плоский текст с разметкой `##`, `###`, `- `, `> `, `**жирный**`. Рендер — чистая функция с тестами.

**Следствия.** Правка в обычном textarea, без визуального редактора и без риска сломать вёрстку вставкой из Word.

**Отвергнуто.** Полноценный Markdown и WYSIWYG — избыточны и ломаются в руках непрограммиста.

## ADR-015 — Произвольные характеристики моделей · 2026-08-20

**Контекст.** Таблица сравнения в прототипе строится динамически.

**Решение.** `specs` — упорядоченный список пар `{ k, v }`. Таблица сравнения = объединение ключей всех видимых моделей, отсутствующее значение — прочерк.

**Следствия.** Владелец добавляет характеристику «Wi-Fi управление» одной модели — таблица сама вырастает на строку. Разработчик не нужен.

**Контекст.** Работа идёт сессиями; контекст между ними не сохраняется, а решения принимаются в переписке и там же теряются.

## ADR-017 — Разработка ведётся в Docker · 2026-08-20

**Контекст.** Разработка на macOS, прод — Linux-VPS. Классические расхождения: версия Node, версия Postgres, регистр в путях (на macOS файловая система его игнорирует, в Linux — нет), пути к volume, раздача статики и заголовков через Caddy вместо Next.

**Решение.** Локальный запуск — только через `docker compose -f docker-compose.dev.yml`, повторяющий продовый состав: `caddy` + `web` + `worker` + `db` той же мажорной версии. Общий `Dockerfile` с многостадийной сборкой, дев и прод из одного базового слоя. `npm run dev` на хосте не поддерживается.

**Следствия.** Расхождение сред обнаруживается на первой итерации, а не при деплое. Цена — более медленный hot reload через bind-mount на macOS; размен принят сознательно.

**Отвергнуто.** Нативный запуск с Postgres в Docker — половинчатый вариант: ловит расхождения БД, но не ловит регистр путей, версию Node, поведение Caddy и работу с volume.
