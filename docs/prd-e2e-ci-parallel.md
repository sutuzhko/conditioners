# PRD: Сквозные сценарии в CI: шлюз по изменённым файлам, кеш зелёного прогона, четыре группы параллельно

**Дата**: 2026-09-03
**Статус**: Draft

## Цель

Работа `e2e` — критический путь пайплайна: 10:16 на любом PR, включая правку
одной строки документации и повторный запуск ярлыком `vr:accepted`, и это
время растёт с каждым новым сценарием. Нужно, чтобы сценарии шли только там,
где правка способна изменить их исход, чтобы повторный прогон того же кода не
начинался заново, а сами сценарии шли четырьмя группами параллельно —
с критическим путём около четырёх минут и без правки защиты `main`.

## Пользовательские сценарии

- Разработчик правит документацию, журнал или задание выкладки → `e2e`
  зелёная за секунды, сценарии не запускались, журнал работы называет причину
- Разработчик ставит ярлык `vr:accepted` на PR, чей код уже прошёл сценарии →
  `e2e` зелёная за секунды, журнал называет ключ содержимого и прогон, который
  его записал
- Разработчик докоммичивает документацию поверх уже проверенного кода → то же:
  ключ содержимого не изменился, сценарии не запускались
- Разработчик правит компонент, маршрут, схему, сид, спек или конфиг → четыре
  группы сценариев идут параллельно, `e2e` выносит сводный вердикт примерно за
  четыре минуты
- Сценарий падает в одной группе → `e2e` красная, сводка называет группу, файл
  и число упавших; трассы этой группы лежат артефактом
- Сценарий прошёл со второй попытки → сводка показывает его как flaky, вердикт
  остаётся зелёным, но повторная попытка видна, а не спрятана ретраями
- Разработчик добавляет spec-файл и не приписывает его к группе → `check`
  красный (тест vitest) и `e2e` красная (та же проверка в сводке); файл не может
  молча не попасть в CI
- Шлюз работы не отработал → работа красная, а не молчаливо зелёная (ADR-221)
- Следующая сессия читает CLAUDE.md, ROADMAP и HANDOFF → там описан действующий
  порядок, а не «`e2e` одним куском в десять минут»

## В скоупе

Шлюз и кеш:

- Шлюз по списку изменённых файлов PR по образцу ADR-221: перечень путей,
  которые физически способны изменить исход сценариев; правка вне перечня даёт
  зелёную работу за секунды со сторожем «шлюз не отработал — красная»
- Ключ содержимого: хеш блобов тех же путей из дерева проверяемого коммита, а
  не список изменённых файлов; маркер зелёного прогона в кеше Actions под этим
  ключом; попадание — зелёная работа без сценариев, промах — полный прогон;
  маркер пишется только при зелёном сводном вердикте
- Перечень путей задан в одном месте и служит и шлюзу, и ключу; покрыт тестами

Параллельные группы:

- Четыре явные группы spec-файлов, взвешенные по замеру времени; каждая группа
  идёт своим раннером со своей базой, сидом, приложением и одним воркером —
  порядок и общая база внутри группы сохраняются
- Сводная работа `e2e` над группами: имя обязательной проверки не меняется;
  красная при любом красном шарде, при неполном наборе итогов и при
  неотработавшем шлюзе
- Состав групп задан в одном месте; каждый spec-файл лежит ровно в одной
  группе — проверяется тестом vitest и той же проверкой в сводной работе
- Сводка в отчёте работы: по группам прошло, пропущено, flaky, упало, время;
  трассы падений артефактом на группу

Документация:

- ADR с решением, замером до/после и отвергнутыми вариантами; ROADMAP, HANDOFF,
  CLAUDE.md и комментарии `ci.yml` описывают новый порядок

## Не в скоупе

- Боевая сборка вместо дев-сервера под сценарии: сняла бы компиляцию по
  первому обращению, но стоит минут сборки на каждый шард, сборка ходит в базу
  (ADR-062), а сценарии написаны под dev — отдельная задача со своим замером
- Больше одного воркера внутри группы: дев-сервер компилирует однопоточно
  (ADR-222), второй браузер даёт гонку за компиляцию, а не время
- Общий образ между работами — отвергнуто ADR-221 и ADR-222
- Правка самих сценариев, ретраев, таймаутов и набора профилей
- Изменение защиты `main` и состава обязательных проверок
- Шлюз по графу импортов, как у снимков (#444): для сценариев, которые ходят по
  всему приложению, граф не отсекает почти ничего
- Кеш между PR: кеш PR виден только этому PR, и обходить это не нужно

## Технические ограничения

- Кеш Actions — 10 ГБ на репозиторий, записи без обращений неделю удаляются;
  кеш `main` виден всем PR, кеш PR — только ему самому; промах кеша — штатный
  путь, а не ошибка
- Пропущенная работа считается обязательной проверкой не всегда одинаково:
  работа обязана завершаться зелёной, а не пропускаться (ADR-221)
- Ярлык на PR сам проверок не перезапускает; пайплайн слушает `labeled` /
  `unlabeled`, и именно этот перезапуск сегодня гоняет сценарии впустую
- `docker run` окружения шага не наследует: переменные раннеру передаются явно
  (ADR-222)
- Сценарии идут в дев-образе с системным chromium (ADR-021); дев-сервер
  собирает страницу по первому обращению, поэтому время группы включает
  компиляцию её маршрутов и не делится на раннеры вместе с тестами
- Сценарии правят прайс, реквизиты и статусы заявок и возвращают их сами:
  внутри группы порядок и общая база остаются как сейчас
- Имена обязательных проверок `check`, `e2e`, `vr`, `vr-panel`, `invariants`
  зашиты в защиту `main`
- Локальный стенд `pnpm e2e:stand` остаётся единственным способом гонять
  сценарии на машине разработчика (DEPLOY §2.3); группы — устройство CI
- Новых зависимостей не требуется: раннер — Playwright, кеш — `actions/cache`

## Критерии готовности

- [ ] PR с правкой только документации: `e2e` зелёная за секунды, сценарии не
      запускались, журнал работы называет причину
- [ ] Повторный прогон того же кода — ярлык `vr:accepted` или перезапуск:
      `e2e` зелёная за секунды, журнал называет ключ содержимого и прогон,
      записавший маркер
- [ ] PR с правкой исходников: четыре группы идут параллельно, критический путь
      `e2e` не больше 5 минут (цель — 4); числа до и после записаны в ADR и в
      описании PR
- [ ] Нарочно сломанный сценарий красит `e2e`; сводка называет группу и файл;
      артефакт трасс группы есть; маркер в кеш не записан
- [ ] Spec-файл, не приписанный к группе, красит `pnpm test` и сводку `e2e`
- [ ] Объединение групп равно списку spec-файлов, пересечений нет
- [ ] Сводка работы показывает по группам прошло, пропущено, flaky, упало и
      время
- [ ] Работа с неотработавшим шлюзом красная
- [ ] Защита `main` не переписывалась; `e2e` — имя сводной работы
- [ ] ADR записан в день решения; ROADMAP, HANDOFF, CLAUDE.md и комментарии
      `ci.yml` описывают новый порядок
