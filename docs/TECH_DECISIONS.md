## 1. Одно приложение вместо фронта и бэка

**Решение.** Next.js 15 (App Router) содержит публичный сайт, админку и API. Отдельного сервиса нет.

**Почему.** Нагрузка — сотни визитов в сутки в пик сезона, а не тысячи RPS. Отдельный NestJS дал бы второй деплой, CORS, дублирование типов и авторизацию через границу — без единой выгоды на этом масштабе.

**Страховка.** API соблюдает контракт из [API.md](API.md) буквально. Данные ходят через слой `repo.ts`, а не через Prisma из компонентов. Если сервис понадобится — переезжает бэкенд, фронт не трогаем.

**Отвергнуто:** Next + NestJS (сложность без выгоды) · headless CMS Strapi/Directus (админка из дизайна не ложится на чужой UI, а она — часть продукта).

## 2. Рендеринг: SSG + ISR

**Решение.** Публичные страницы — статические, с ревалидацией по времени (час) и **точечной ревалидацией из админки**: сохранил цену → `revalidatePath` на затронутые маршруты → страница перегенерилась за секунду.

**Почему.** Робот и человек получают готовый HTML за один запрос к CDN-кэшу Caddy, без похода в БД. При этом владелец не ждёт час, чтобы увидеть правку.

**Отвергнуто:** чистый SSR (лишняя нагрузка и время до байта на данных, которые меняются раз в неделю) · клиентский рендер (нарушает инвариант 1).

## 3. Хостинг — VPS в РФ

**Решение.** VPS у российского провайдера (Selectel / Timeweb / REG.RU), Docker Compose: `caddy` + `web` (Next standalone) + `worker` (разбор очереди уведомлений) + `db` (Postgres 16). Пятым идёт разовый `migrate`: он накатывает миграции до старта `web` и `worker` (ADR-062).

**Почему.** 152-ФЗ требует, чтобы персданные россиян изначально записывались в базу на территории РФ. Заявка = имя + телефон = персданные. Vercel и любой зарубежный хостинг для основной БД исключены.

**Caddy** вместо Nginx — автоматический Let's Encrypt без ручного обновления сертификатов и cron'а.

## 5. Уведомления — очередь, а не вызов

🔴 Ключевое решение проекта.

```
POST /api/leads
  → валидация (Zod)
  → INSERT Lead                       ← с этого момента заявка не может потеряться
  → INSERT Notification × N (pending)
  → 201 клиенту                       ← не ждём внешние сервисы
Воркер (интервал ~30 с)
  → берёт pending
  → шлёт в канал
  → sent | attempts++ и повтор с экспоненциальной задержкой
  → после N неудач: failed, видно в админке
```

**Почему.** Прямая отправка из обработчика формы связывает деньги владельца с доступностью чужого сервиса. Telegram недоступен — клиент ушёл к конкуренту. С очередью: заявка в БД, в админке, придёт письмом, а в Telegram доедет, когда сеть вернётся.

Воркер — отдельный процесс в том же контейнере (`setInterval` в инстанциированном при старте модуле) или отдельный контейнер с тем же образом. Второе честнее: перезапуск веба не рвёт доставку.

## 6. Каналы уведомлений

Интерфейс `NotificationChannel` с реализациями, выбор — через ENV.

### 6.1. Email — основной надёжный канал

SMTP российского провайдера (Яндекс 360 для бизнеса / Mail.ru для бизнеса) на домене сайта. Работает всегда, ничем не блокируется, не зависит от геополитики. Письмо содержит все поля заявки и ссылку в админку.

### 6.2. Telegram — удобный, но не гарантированный

Владельцу удобнее всего получать заявки в телефон и модерировать отзывы кнопками (`inline_keyboard`, `callback_data` вида `rev:<action>:<id>`), поэтому канал нужен. Но доступность `api.telegram.org` с российского дата-центра **не гарантирована и не проверяема заранее** — проверять только с самого VPS:

```bash
curl -sS -o /dev/null -w "http=%{http_code} tls=%{time_appconnect}s\n" --max-time 10 https://api.telegram.org/
```

Поэтому транспорт сменный:

| `TELEGRAM_TRANSPORT` | Как работает                                              | Когда                        |
| -------------------- | --------------------------------------------------------- | ---------------------------- |
| `direct`             | обычный `fetch` на `api.telegram.org`                     | если с VPS отвечает          |
| `proxy`              | `undici.ProxyAgent` на SOCKS5/HTTP-прокси за пределами РФ | если прямой путь закрыт      |
| `off`                | канал выключен, работает только email                     | пока не решён вопрос доступа |

Переключение — переменной окружения, без правок кода.

**Если нужен план Б,** предпочтительный вариант — WireGuard-туннель до дешёвого зарубежного VPS с маршрутизацией **только** подсетей Telegram (`149.154.160.0/20`, `91.108.4.0/22`): приложение не знает о туннеле вообще, решает маршрутизация. Второй вариант — SOCKS5 на том же VPS.

**Cloudflare Workers как реле отвергнут** по требованию заказчика: доступность Cloudflare из РФ ненадёжна.

### 6.3. Webhook Telegram

Апдейты (нажатия кнопок модерации) Telegram шлёт **к нам** — это входящее соединение на наш домен, оно не зависит от исходящей доступности. Обработчик проверяет секрет из заголовка `X-Telegram-Bot-Api-Secret-Token` и вызывает ту же смену статуса, что и админка. Модерация из Telegram и из админки остаётся консистентной, потому что путь один.

Если исходящий доступ закрыт, `setWebhook` не поставить — тогда канал в режиме `off` и модерация только через админку.

## 7. Секреты

Все — в ENV на сервере, ни один не в репозитории. `.env.prod.example` содержит только имена и комментарии.

При старте приложения ENV валидируется Zod-схемой: не поднимаемся с неполной конфигурацией, вместо того чтобы падать на первой заявке.

🔴 **Токен бота из прототипа скомпрометирован** — лежал открытым в handoff-архиве и уходил в клиентский бандл. Отозвать в BotFather, выпустить новый, в клиентский код не передавать никогда.

## 8. Авторизация админки

Cookie-сессия: httpOnly + Secure + SameSite=Lax, срок 30 дней, ротация при входе. Пароль — Argon2id. Ограничение попыток входа по IP.

`middleware.ts` закрывает всё под `/admin` и `/api/admin`. Страницы админки — `noindex, nofollow`, путь закрыт в `robots.txt`.

**Почему не JWT в localStorage,** как в исходном контракте: токен в localStorage читается любым XSS. Для админки на одном домене cookie-сессия и проще, и безопаснее. Контракт в этой части сознательно изменён — зафиксировано в [API.md](API.md).

## 9. Файлы

Загрузки (фото моделей, обложки статей, фото к отзывам и заявкам) — на диск VPS в том, что смонтировано как volume, вне директории приложения. Имя генерирует сервер, оригинальное не используется. Проверяется реальный тип изображения, а не расширение. Ограничение 5 МБ. Сервер пережимает до ~1200px по большей стороне.

**Почему не S3.** Объём — сотни файлов. Volume + бэкап проще и дешевле. Если каталог вырастет, переезд на S3-совместимое хранилище (Selectel, VK Cloud) — точечный, за интерфейсом хранилища.

🔴 EXIF из загруженных фото вырезается: снимок квартиры клиента с GPS-координатами — утечка персданных.

## 10. Антиспам

Публичные `POST` (`/api/leads`, `/api/reviews`): rate-limit по IP (счётчик в БД или в памяти процесса), honeypot-поле, минимальное время заполнения формы, ограничение размера тела.

Капча — только если пойдёт реальный спам, и тогда российская (Yandex SmartCaptcha). Капча снижает конверсию заявок, ставить её заранее — стрелять себе в ногу.

## 12. Бэкапы

`pg_dump` по cron ежедневно, хранение 30 дней, плюс копия загруженных файлов. Бэкап лежит **не на том же диске**, что БД.

Раз в квартал — учебное восстановление. Непроверенный бэкап бэкапом не является.

## 13. Наблюдаемость

Логи приложения — в stdout, собираются Docker с ротацией. Ошибки уведомлений видны в админке (`Notification.status = failed`) — это важнее любой внешней системы мониторинга: владелец должен видеть, что заявка не доставлена.

Health-эндпоинт `/api/health` проверяет БД и отвечает `200`.

Внешний аптайм-мониторинг домена — бесплатным сервисом, с оповещением в тот же Telegram.

## 14. CI

GitHub Actions: линт → типы → тесты → сборка. Деплой — вручную с сервера (`git pull` + `docker compose up -d --build`) либо по тегу. Автодеплой в прод с каждого пуша на проекте одного разработчика создаёт больше рисков, чем экономит времени.

## 15. Данные компании — настройки, а не код

**Решение.** Всё, что относится к организации, хранится в `Setting` и правится в разделе «Компания» админки: название, слоган, телефоны, мессенджеры, адрес по частям, координаты, часы, регион обслуживания, реквизиты, гарантия, оплата, соцсети, метаданные главной.

**Почему.** В прототипе это было выдумано и зашито в разметку — включая координаты в JSON-LD и название бренда. Любой такой факт, оставшийся в коде, означает: (а) правка телефона требует разработчика и выкладки, (б) рано или поздно телефон в шапке разойдётся с телефоном в разметке. Второе — прямой удар по локальному ранжированию: Яндекс сверяет NAP-данные с Яндекс.Бизнесом.

**Как хранится.** JSON по группам, у каждой группы своя Zod-схема. Адрес — по частям (город, улица, дом, офис, индекс): `PostalAddress` требует отдельных полей, из частей строку собрать можно, из строки части — нет.

**Исключение.** Канонический домен остаётся в `SITE_URL` (ENV): смена домена — переезд с редиректами и переиндексацией, а не правка поля.

**Защита от заглушек.** Сиды содержат явно видимые «ЗАПОЛНИТЕ В АДМИНКЕ», а не правдоподобные выдумки, плюс эндпоинт готовности показывает, что осталось незаполненным. Правдоподобный `+7 (4872) 00-00-00` уезжает в прод незаметно и живёт там год; заметная заглушка — нет.

→ ADR-009

## 16. Скидки

**Решение.** У товара `salePrice` (конечная цена), `saleFrom`/`saleTo` (период), `saleLabel` (подпись). Процент вычисляется. Активность скидки считает единственная функция `getActivePrice(product)`, её результат (`currentPrice`, `oldPrice`, `discountPercent`, `saleActive`) отдаётся в API уже посчитанным.

**Почему конечная цена.** Владелец мыслит витриной: «поставлю 34 900» даёт круглую цифру, «поставлю 12%» даёт 33 880. Процент — производная, а не ввод.

**Почему период.** Скидка снимается сама, без участия владельца, и даёт `priceValidUntil` для разметки `Offer`.

**Эксплуатационное следствие.** Страницы товаров ревалидируются не реже раза в сутки, даже без правок: иначе истёкшая скидка останется висеть на статической странице.

🔴 Перечёркивается только реально действовавшая цена — см. красные линии в [CLAUDE.md](CLAUDE.md).

→ ADR-011

## 17. Решения фиксируются в репозитории

**Решение.** Каждое принятое решение попадает в [DECISIONS.md](DECISIONS.md) в день принятия: контекст, решение, следствия, что отвергнуто.

**Почему.** Работа идёт сессиями, и контекст сессии не переживает сессию. Решение, принятое в переписке и нигде не записанное, через месяц неотличимо от произвола — его начинают переигрывать, тратя время на возврат к тому же выводу. Отдельно фиксируется отвергнутое: иначе следующая сессия честно переизобретёт отвергнутый вариант.

**Как переигрывать.** Новым ADR со ссылкой «отменяет ADR-NNN», а не правкой старой записи. История решений ценнее её аккуратности.

→ ADR-016

## 18. Разработка — в Docker, как на проде

**Решение.** Локальная разработка ведётся **только** через `docker compose -f docker-compose.dev.yml`. Запуск `pnpm dev` на хосте не поддерживается.

**Почему.** Классы багов, которые ловятся только так: другая мажорная версия Node на macOS и на сервере; расхождение версии Postgres (поведение сортировок, `citext`, генерация миграций); файловая система хоста без учёта регистра — импорт `Button` вместо `button` работает на Mac и падает в Linux-сборке; пути к volume с загрузками; заголовки и сжатие, которые в деве раздаёт Next напрямую, а на проде — Caddy. Каждый из них обнаруживается при деплое, то есть в худший возможный момент.

**Как устроено.** Один `Dockerfile` с несколькими стадиями (`deps → dev → build → runner`) — дев и прод собираются из общего базового слоя, а не из двух разных описаний, которые расходятся через месяц.

`docker-compose.dev.yml` повторяет продовый состав:

| Сервис   | Дев                                                       | Прод                                       |
| -------- | --------------------------------------------------------- | ------------------------------------------ |
| `web`    | стадия `dev`, `next dev` с hot reload                     | стадия `runner`, `next start` (standalone) |
| `worker` | тот же образ, воркер уведомлений                          | то же                                      |
| `db`     | Postgres **той же мажорной версии**, порт наружу для psql | без публичного порта                       |
| `caddy`  | тот же Caddyfile, локальный сертификат                    | Let's Encrypt                              |

**Детали, без которых теряется смысл:**

- Исходники — bind-mount, `node_modules` — именованный volume: иначе бинарные зависимости, собранные под macOS, ломают контейнер Linux.
- Caddy поднимается и в деве, на локальном домене: заголовки, сжатие и проксирование проверяются здесь, а не на проде.
- Миграции, сиды и `npm` выполняются **внутри контейнера** (`docker compose exec web …`), никогда с хоста.
- Версии Node и Postgres заданы в одном месте и одинаковы в обоих файлах. Расхождение версий между дев и прод — баг, а не мелочь.
- `.env.dev` отдельный, с заведомо небоевыми значениями; уведомления по умолчанию в режиме «в лог», а не в реальный Telegram владельца.

**Цена.** Hot reload через bind-mount на macOS медленнее нативного, старт тяжелее. Это осознанный размен: несколько секунд на итерацию против сюрпризов при выкладке.

→ ADR-017 · практика запуска в [DEPLOY.md](DEPLOY.md)
